## Objetivo del Despliegue

### ¿Qué vamos a añadir?

1. **DIM Wallet Stub**: Servicio que gestiona identidades y credenciales verificables
2. **EDC Provider** (TestCompany1): Conector para publicar/compartir datos
3. **EDC Consumer** (Ikerlan): Conector para consumir datos de otros participantes

### ¿Por qué necesitamos los EDCs?

Los EDC (Eclipse Dataspace Connector) son **esenciales** para el intercambio de datos en Catena-X:
- Permiten **negociación de contratos** entre participantes
- Implementan **políticas de acceso** a los datos
- Gestionan la **transferencia segura** de información
- Resuelven **identidades** (BPN → DID) mediante BDRS
- Validan **credenciales verificables** del wallet

#### 2.4. BDRS Seeding (CRÍTICO - Actualizado)
```yaml
# BDRS (BPN-DID Resolution Service)
bdrs-server-memory:
  seeding:
    bpnList:
      - bpn: "BPNL00000003CRHK"
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK"
      - bpn: "BPNL000000000065"  # ← AÑADIDO: TestCompany1
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL000000000065"
      - bpn: "BPNL00000000015G"  # ← AÑADIDO: Ikerlan
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000015G"
  server:
    trustedIssuers:
      - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK
    env:
      EDC_IAM_DID_WEB_USE_HTTPS: false
    ingresses:
      - enabled: true
        hostname: "bdrs-server.51.178.94.25.nip.io"
        endpoints:
          - directory
          - management
        className: "nginx"
        tls:
          enabled: false
```

**Función del seeding:**
- BDRS es un servicio **in-memory** (sin BD persistente)
- Al arrancar, carga estos mappings BPN→DID en memoria
- Los EDCs consultan BDRS para resolver identidades

#### Detalles de Configuración de EDCs

**Campos clave:**

1. **`participant.id`**: BPN del participante
   - TestCompany1: `BPNL000000000065`
   - Ikerlan: `BPNL00000000015G`

2. **`iatp.id`**: DID (Decentralized Identifier) del participante
   - Formato: `did:web:{host}:{bpn}`
   - Ejemplo: `did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL000000000065`

3. **`trustedIssuers`**: Lista de emisores confiables de credenciales
   - Solo CX-Operator: `BPNL00000003CRHK`
   - Los EDCs solo confían en credenciales emitidas por CX-Operator

4. **URLs de Servicios Internos:**
   - **Wallet Stub**: `http://portal-ssi-dim-wallet-stub` (sin puerto, usa 80 por defecto)
   - **BDRS**: `http://bdrs-server:8080` (puerto explícito 8080)

**⚠️ IMPORTANTE: Nombres de Servicios**

Los nombres de servicios internos en Kubernetes siguen patrones específicos:

| Componente | Nombre en values | Nombre del Service K8s | Observación |
|------------|------------------|------------------------|-------------|
| Wallet Stub | `ssi-dim-wallet-stub` | `portal-ssi-dim-wallet-stub` | Con prefijo `portal-` |
| BDRS | `bdrs-server-memory` | `bdrs-server` | **Sin** prefijo `portal-` |
| BPDM Pool | `bpdm-pool` | `portal-bpdm-pool` | Con prefijo `portal-` |

Esto se debe a cómo cada subchart define el `fullname` template.

```bash
  -n portal
```

### Explicación del Comando

```bash
helm upgrade RELEASE_NAME CHART_LOCATION -f VALUES_FILE -n NAMESPACE
```

- **`helm upgrade`**: Actualiza un release existente (o lo crea si no existe con `--install`)
- **`portal`**: Nombre del release de Helm
- **`charts/umbrella`**: Ubicación del Chart.yaml (el chart principal)
- **`-f archivo.yaml`**: Añade un archivo de valores (se pueden usar múltiples `-f`)
- **`-n portal`**: Namespace de Kubernetes donde desplegar

**Orden de los archivos:**
El orden de los `-f` importa: **el último prevalece** en caso de conflicto.

## Troubleshooting

### Problema 1: Wallet Stub no se despliega

**Síntoma:**
```bash
kubectl get pods -n portal | grep wallet
# Salida: vacío
```

**Causa:**
Falta `enabled: true` en el subchart `ssi-dim-wallet-stub`

**Solución:**
```yaml
# En values-ovh-hosts-portal.yaml
identity-and-trust-bundle:
  ssi-dim-wallet-stub:
    enabled: true  # ← AÑADIR
```

### Problema 2: EDC no puede resolver BPNs

**Síntoma en logs:**
```
ERROR: Failed to resolve BPN BPNL000000000065 to DID
```

**Causas posibles:**

1. **BPN no está en BDRS seeding**
   ```yaml
   # Verificar en values-ovh-hosts-portal.yaml
   bdrs-server-memory:
     seeding:
       bpnList:
         - bpn: "BPNL000000000065"  # ← Debe estar aquí
   ```

2. **URL de BDRS incorrecta en EDC**
   ```yaml
   # Debe ser (con puerto):
   url: http://bdrs-server:8080/api/v1/directory
   
   # NO:
   url: http://portal-bdrs-server-memory/api/v1/directory
   ```

3. **BDRS no se ha reiniciado**
   ```bash
   # Forzar reinicio del pod BDRS
   kubectl delete pod -n portal -l app.kubernetes.io/name=bdrs-server-memory
   ```

### Problema 3: EDC no puede conectar al Wallet

**Síntoma en logs:**
```
ERROR: Failed to connect to wallet at http://portal-ssi-dim-wallet-stub
```

**Causas posibles:**

1. **Wallet stub no está corriendo**
   ```bash
   kubectl get pods -n portal | grep wallet
   ```

2. **Nombre de servicio incorrecto**
   - Correcto: `http://portal-ssi-dim-wallet-stub`
   - Incorrecto: `http://ssi-dim-wallet-stub`

3. **Wallet stub no tiene puerto abierto**
   ```bash
   kubectl get svc -n portal portal-ssi-dim-wallet-stub
   # Verificar que tiene puerto 80/TCP
   ```

### Problema 4: trustedIssuers no configurado

**Síntoma:**
```
ERROR: Credential issuer did:web:...:BPNL00000003CRHK is not trusted
```

**Solución:**
Verificar que `trustedIssuers` está en **TRES lugares**:
1. Wallet stub (`values-ovh-test-data-exchange.yaml`)
2. BDRS (`values-ovh-hosts-portal.yaml`)
3. Cada EDC (`values-ovh-test-data-exchange.yaml`)

### Problema 5: Helm upgrade falla

**Error común:**
```
Error: UPGRADE FAILED: unable to build kubernetes objects from release manifest
```

**Soluciones:**

1. **Verificar sintaxis YAML**
   ```bash
   yamllint charts/values-ovh-test-data-exchange.yaml
   ```

2. **Verificar template rendering**
   ```bash
   helm template portal charts/umbrella \
     -f charts/umbrella/values-adopter-portal-for-onboarding.yaml \
     -f charts/umbrella/values-ovh-hosts-portal.yaml \
     -f charts/values-ovh-test-data-exchange.yaml \
     -n portal > /tmp/rendered.yaml
   
   # Revisar errores en /tmp/rendered.yaml
   ```

3. **Verificar dependencias del chart**
   ```bash
   cd charts/umbrella
   helm dependency update
   ```

### Problema 6: Operación Helm en Progreso

**Síntoma:**
```
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

**Causa:**
Una operación anterior de Helm quedó en estado `pending-upgrade` o `pending-install`.

**Diagnóstico:**
```bash
helm list -n portal -a
# Buscar STATUS: pending-upgrade
```

**Solución:**
```bash
# Hacer rollback a la última revisión exitosa
helm rollback portal <REVISION> -n portal

# Ejemplo: si la última versión buena era la 3
helm rollback portal 3 -n portal
```

### Problema 7: Vault Post-Install Hook Timeout (CRÍTICO)

**Síntoma:**
```
Error: UPGRADE FAILED: post-upgrade hooks failed: 1 error occurred:
        * timed out waiting for the condition
```

**Diagnóstico:**
```bash
# Ver jobs fallidos
kubectl get jobs -n portal --sort-by=.metadata.creationTimestamp | tail -10

# Ver logs del job fallido
kubectl logs -n portal job/portal-dataconsumer-1-post-install-vault-setup
```

**Salida típica del error:**
```
wget: bad address 'portal-edc-dataconsumer-1-vault:8200'
```

## Servicios de Descubrimiento (Discovery Services)

### 🔍 ¿Qué son BPN Discovery y Discovery Finder?

Son servicios esenciales para que los conectores EDC puedan encontrarse entre sí en el dataspace de Catena-X.

#### BPN Discovery

**Propósito:** Descubrir qué EDC connector posee un BPN específico basándose en **type numbers** (números de pieza, números de serie, etc.)

**Flujo típico:**
```
Número de Pieza → BPN Discovery → BPN del Proveedor → EDC del Proveedor
```

**Ejemplo de uso:**
1. Una empresa tiene un número de pieza: `"VIN-123456789"`
2. BPN Discovery busca qué BPN (Business Partner Number) tiene ese número de pieza
3. Devuelve: `BPNL000000000065` (TestCompany1)
4. Ahora se puede buscar el EDC de TestCompany1 para obtener datos de esa pieza

#### Discovery Finder

**Propósito:** Descubrir **endpoints de discovery services** en el dataspace. Es el "directorio de directorios".

**Flujo típico:**
```
BPN → Discovery Finder → URL del EDC Connector → Catálogo de Assets
```

**Ejemplo de uso:**
1. Tengo el BPN: `BPNL000000000065`
2. Discovery Finder me dice: "El EDC de ese BPN está en `http://dataprovider-controlplane.tx.test`"
3. Ahora puedo consultar el catálogo de ese EDC para ver qué datos ofrece

### 📊 Arquitectura de Descubrimiento

```
┌─────────────────────────────────────────────┐
│          Consumer (Ikerlan)                 │
│  "Quiero datos de la pieza VIN-123456789"  │
└────────────────┬────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────────────┐
│      1. BPN Discovery                      │
│  "¿Qué BPN tiene VIN-123456789?"          │
│  → Respuesta: BPNL000000000065            │
└────────────────┬───────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────────────┐
│      2. Discovery Finder                   │
│  "¿Dónde está el EDC de BPNL000000000065?"│
│  → Respuesta: http://provider-edc.tx.test │
└────────────────┬───────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────────────┐
│      3. EDC Provider (TestCompany1)        │
│  Consultar catálogo → Negociar contrato   │
│  → Transferir datos                        │
└────────────────────────────────────────────┘
```

```yaml
bpndiscovery:

    ingress:
      enabled: false  # ⚠️ Requiere configuración manual (ver sección más abajo)

    discoveryfinderClient:
      baseUrl: "http://semantics.51.178.94.25.nip.io/discoveryfinder"

# Discovery Finder
discoveryfinder:
  discoveryfinder:
    host: "semantics.51.178.94.25.nip.io"
    properties:
      discoveryfinder:
        initialEndpoints:
          - type: bpn
            endpointAddress: "http://portal-backend.51.178.94.25.nip.io/api/administration/Connectors/discovery"
            description: Service to discover connector endpoints based on bpns
```

**Función:**
- El Portal backend implementa el endpoint `/api/administration/Connectors/discovery`
- Discovery Finder consulta este endpoint para resolver BPNs a EDC URLs
- BPN Discovery permite búsquedas por números de pieza/serie

### 🛠️ Configuración Manual de Ingress (Requerido)

Los subcharts de bpndiscovery y discoveryfinder usan `pathType: Prefix` hardcodeado, incompatible con rutas regex. Debe aplicarse manualmente después del helm upgrade:

```bash
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: portal-bpndiscovery
  namespace: portal
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /\$2
spec:
  ingressClassName: nginx
  rules:
  - host: semantics.51.178.94.25.nip.io
    http:
      paths:
      - path: /bpndiscovery(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: portal-bpndiscovery
            port:
              number: 8080
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: portal-discoveryfinder
  namespace: portal
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /\$2
spec:
  ingressClassName: nginx
  rules:
  - host: semantics.51.178.94.25.nip.io
    http:
      paths:
      - path: /discoveryfinder(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: portal-discoveryfinder
            port:
              number: 8080
EOF
```

**Verificar acceso:**
```bash
curl http://semantics.51.178.94.25.nip.io/bpndiscovery/swagger-ui/index.html
curl http://semantics.51.178.94.25.nip.io/discoveryfinder/swagger-ui/index.html
```

**⚠️ Nota:** Estos servicios son CRÍTICOS para data exchange - sin ellos, los conectores EDC no pueden encontrarse entre sí.

## Notas Finales

### Conceptos Importantes

1. **Deep Merge de Helm**: Los valores de múltiples archivos `-f` se combinan, prevaleciendo los últimos en caso de conflicto.

2. **Nombres de Servicios**: Varían según cómo cada subchart define su `fullname` template. Siempre verificar con `kubectl get svc`.

3. **BDRS In-Memory**: No persiste datos, se recarga desde seeding en cada reinicio del pod.

4. **trustedIssuers**: Debe estar en cada componente que valida credenciales (Wallet, BDRS, EDCs).

5. **DIDs**: Formato `did:web:{host}:{bpn}` - el host debe coincidir con el `didHost` del wallet stub.

### Lecciones Aprendidas

1. ❌ **Error común**: Olvidar `enabled: true` en subcharts como `ssi-dim-wallet-stub`
2. ✅ **Buena práctica**: Siempre verificar pods y servicios después del despliegue
3. ✅ **Buena práctica**: Usar nombres de archivo descriptivos (ej: `-for-onboarding`, `-portal`)
4. ✅ **Buena práctica**: Documentar cambios en archivos de configuración con comentarios
