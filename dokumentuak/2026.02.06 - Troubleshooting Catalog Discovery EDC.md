## 2. Cronología de Problemas y Soluciones

### 2.1 Problema #1: DNS Resolution Error en DIM Wallet
**Síntoma:**
```bash
curl -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request"
# Respuesta: HTTP 502 Bad Gateway
```

**Log del controlplane IKLN:**
```
java.net.UnknownHostException: portal-ssi-dim-wallet-stub.portal.svc.cluster.local
```

**Causa Raíz:**  
El nombre del servicio configurado estaba incorrecto. El servicio real en Kubernetes se llama `ssi-dim-wallet-service`, no `portal-ssi-dim-wallet-stub`.

**Solución Implementada:**
```yaml
# charts/values-ikln-connector.yaml (líneas 46-48, 62)
env:
  TX_IAM_IATP_CREDENTIALSERVICE_URL: http://ssi-dim-wallet-service.portal.svc.cluster.local/api
sts:
  oauth:
    token_url: http://ssi-dim-wallet-service.portal.svc.cluster.local/oauth/token
```

**Comando:**
```bash
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella
./deploy-ikln-connector.sh  # Actualizado a Revision 7
```

**Resultado:**  
✅ DNS resolution exitoso, pero aparece nuevo error de timeout.

### 2.2 Problema #2: Connection Timeout por Puerto Faltante
**Síntoma:**
```
org.eclipse.edc.spi.EdcException: Error during token validation
Caused by: java.net.SocketTimeoutException: Connect timed out
```

**Causa Raíz:**  
Las URLs del DIM wallet no incluían el puerto `:8080`. El servicio escucha en puerto 8080 pero Kubernetes necesita que se especifique explícitamente en las URLs.

**Solución Implementada:**
```yaml
# charts/values-ikln-connector.yaml
# Agregado puerto :8080 en 4 ubicaciones (líneas 46, 48, 62, variable adicional)
sts:
  oauth:
    url: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api/sts
    token_url: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/oauth/token
env:
  TX_IAM_IATP_CREDENTIALSERVICE_URL: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api
```

**Resultado:**  
✅ OAuth token request exitoso, pero catálogo sigue vacío con nuevo error.

### 2.3 Problema #3: BDRS BPN Resolution Failure (404)
**Síntoma:**
```json
{
  "message": "Could not obtain data from BDRS server: code: 404, message: ...",
  "type": "BadGateway"
}
```

**Log detallado:**
```
Request Method: GET
Request URL: http://bdrs-server.portal.svc.cluster.local:8080/api/v1/directory/api/management/bpn-directory/BPNL00000000MASS
Response: HTTP 404
```

**Diagnóstico Inicial:**  
El conector IKLN intentaba resolver el DID del BPN `BPNL00000000MASS` pero BDRS devolvía 404.

#### 2.3.1 Investigación de BDRS Seeding
**Verificación del seeding configurado:**
```yaml
# charts/umbrella/values-ovh-hosts-portal.yaml
bdrs-server-memory:
  seeding:
    bpnList:
      - bpn: "BPNL00000003CRHK"  # Base operator
      - bpn: "BPNL000000000065"  # TestCompany1
      - bpn: "BPNL00000000015G"  # Existing test
```

**Problema encontrado:**  
Los BPNs de MASS e IKLN no estaban en la lista de seeding.

**Solución #1: Actualizar seeding en values**
```yaml
# Agregado a values-ovh-hosts-portal.yaml (líneas 346-349)
- bpn: "BPNL00000000MASS"
  did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS"
- bpn: "BPNL00000000IKLN"
  did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000IKLN"
```

**Limitación descubierta:**  
El Helm chart de BDRS usa hook `post-install` únicamente. No se ejecuta en `post-upgrade`.

```yaml
# templates/post-install-bdrs-setup.yaml
annotations:
  helm.sh/hook: post-install  # ← Solo en instalación inicial
```

**Solución #2: Registro manual via Management API**
Primero intentamos via ingress externo:
```bash
curl -X POST "http://bdrs-server.51.178.94.25.nip.io/api/management/bpn-directory" \
  -H "Content-Type: application/json" \
  -H "x-api-key: TEST" \
  -d '{"bpn":"BPNL00000000MASS","did":"did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS"}'
# Respuesta: HTTP 204 No Content ✅
```

Pero al consultar el directorio, seguía devolviendo 404:
```bash
curl "http://bdrs-server.51.178.94.25.nip.io/api/directory/bpn-directory/BPNL00000000MASS"
# Respuesta: HTTP 404 ❌
```

**Solución #3: Job de Kubernetes para seeding desde cluster interno**
Creamos un Job manual para registrar todos los BPNs:
```bash
kubectl apply -f - <<EOF
apiVersion: batch/v1
kind: Job
metadata:
  name: bdrs-manual-seeding
  namespace: portal
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: seeder
        image: alpine:3.19
        command:
        - /bin/sh
        - -c
        - |
          apk add --no-cache wget
          # Registrar cada BPN
          for bpn_data in \
            "BPNL00000003CRHK:CRHK" \
            "BPNL000000000065:0065" \
            "BPNL00000000015G:015G" \
            "BPNL00000000MASS:MASS" \
            "BPNL00000000IKLN:IKLN"; do
            bpn=\${bpn_data%%:*}
            wget --post-data='{"bpn":"'"\$bpn"'","did":"did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:'"\$bpn"'"}' \
              --header='Content-Type: application/json' \
              --header='x-api-key: TEST' \
              -O- \
              http://bdrs-server.portal.svc.cluster.local:8081/api/management/bpn-directory
          done
EOF
```

**Ejecución:**
```bash
kubectl wait --for=condition=complete job/bdrs-manual-seeding -n portal --timeout=120s
kubectl logs job/bdrs-manual-seeding -n portal
```

**Resultado del Job:**
```
HTTP request sent, awaiting response... HTTP/1.1 204 No Content
[Repetido 5 veces para cada BPN - todos exitosos] ✅
```

**Verificación post-seeding:**
```bash
curl "http://bdrs-server.51.178.94.25.nip.io/api/directory/bpn-directory/BPNL00000000MASS"
# Respuesta: HTTP 404 ❌ (!!!)
```

El error 404 persistía incluso después del seeding exitoso.

### 2.4 Problema #4: BDRS URL Endpoint Incorrecto en EDC
**Descubrimiento Crítico:**  
Al investigar por qué el seeding no funcionaba, extrajimos la documentación del chart BDRS:

```bash
tar -xzOf charts/umbrella/charts/bdrs-server-memory-0.5.7.tgz bdrs-server-memory/README.md | grep -A5 "ports"
```

**Documentación encontrada:**
```
BDRS expone 3 puertos diferentes:
- 8080: Default API (/api) - Observability
- 8081: Management API (/api/management) - Para registro de BPNs (requiere x-api-key)
- 8082: Directory API (/api/directory) - Para consultas públicas desde EDCs
```

**Configuración incorrecta en conectores:**
```yaml
# charts/values-ikln-connector.yaml (línea 68) - ANTES
bdrs:
  server:
    url: http://bdrs-server.portal.svc.cluster.local:8080/api/v1/directory
    #                                                ^^^^ Puerto incorrecto
    #                                                         ^^^^^^^^^ Path incorrecto
```

**Causa Raíz:**  
Los EDCs estaban consultando:
- Puerto **8080** (Default API) en lugar de **8082** (Directory API)
- Path `/api/v1/directory` (inexistente) en lugar de `/api/directory`

**Solución Implementada:**
```yaml
# charts/values-ikln-connector.yaml (línea 68) - DESPUÉS
bdrs:
  server:
    url: http://bdrs-server.portal.svc.cluster.local:8082/api/directory
    #                                                ^^^^ Correcto
    #                                                     ^^^^^^^^^^^^^ Correcto

# charts/values-mass-connector.yaml (línea 68) - DESPUÉS
bdrs:
  server:
    url: http://bdrs-server.portal.svc.cluster.local:8082/api/directory
```

**Deploy:**
```bash
./deploy-ikln-connector.sh  # Revision 7 → 8
./deploy-mass-connector.sh  # Revision 5 → 6
```

**Resultado:**  
✅ Configuración BDRS corregida, pero aparece nuevo error de certificados SSL.

### 2.5 Problema #5: SSL Certificate Validation Error
**Síntoma:**
```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -H "X-Api-Key: ikln-api-key-change-in-production" \
  -H "Content-Type: application/json" \
  -d '{
    "@context": {"@vocab": "https://w3id.org/edc/v0.0.1/ns/"},
    "counterPartyAddress": "https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS",
    "protocol": "dataspace-protocol-http"
  }'
```

**Respuesta:**
```json
{
  "message": "org.eclipse.edc.http.spi.EdcHttpClientException: (certificate_unknown) PKIX path building failed: sun.security.provider.certpath.SunCertPathBuilderException: unable to find valid certification path to requested target",
  "type": "BadGateway"
}
```

**Causa Raíz:**  
Los ingress de ambos conectores usan certificados self-signed generados automáticamente por nginx. Los EDCs no confían en estos certificados durante la comunicación DSP.

#### 2.5.1 Intento #1: Variable EDC_JSONLD_HTTPS_ENFORCE
```yaml
# charts/values-ikln-connector.yaml y values-mass-connector.yaml
controlplane:
  env:
    EDC_JSONLD_HTTPS_ENFORCE: "false"
```

**Deploy:**
```bash
./deploy-ikln-connector.sh  # Revision 8 → 9
./deploy-mass-connector.sh  # Revision 6 → 7
```

**Resultado:**  
❌ Error persiste. Esta variable solo afecta a JSON-LD context loading, no al HTTP client.

#### 2.5.2 Intento #2: Java Trust Store Options
```yaml
# charts/values-ikln-connector.yaml y values-mass-connector.yaml
controlplane:
  env:
    JAVA_TOOL_OPTIONS: "-Djavax.net.ssl.trustAll=true -Djdk.tls.client.protocols=TLSv1.2"
```

**Deploy:**
```bash
./deploy-ikln-connector.sh  # Revision 9 → 10
./deploy-mass-connector.sh  # Revision 7 → 8
```

**Resultado:**  
❌ Error persiste. La opción `-Djavax.net.ssl.trustAll=true` no es estándar de Java.

#### 2.5.3 Intento #3: Usar HTTP en lugar de HTTPS
**Test con HTTP en counterPartyAddress:**
```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -d '{
    "counterPartyAddress": "http://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp"
  }'
```

**Resultado:**  
❌ Mismo error de certificado. Esto indica que el problema no está en el DSP endpoint directo, sino probablemente en alguna llamada HTTPS interna del flujo IATP (DID resolution, credential verification, etc.)

#### 2.5.4 Intento #4: URL Interna de Kubernetes
**Test usando servicio interno (sin Ingress):**
```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -d '{
    "counterPartyAddress": "http://mass-edc-tractusx-connector-controlplane.mass-connector.svc.cluster.local:8084/api/v1/dsp"
  }'
```

**Resultado:**  
🟡 Error diferente: `401 Unauthorized`
```json
{
  "message": "{\"@type\":\"dspace:CatalogError\",\"dspace:code\":\"401\",\"dspace:reason\":\"Unauthorized\"}",
  "type": "BadGateway"
}
```

Esto confirma que:
- ✅ La comunicación interna funciona
- ✅ BDRS está siendo consultado (no hay error 404)
- ❌ Hay un problema de autenticación IATP

**Nota importante sobre formato de URL:**  
El formato correcto usado desde la UI es:
```
https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp
```

NO la URL interna de Kubernetes (que era solo para testing):
```
http://mass-edc-tractusx-connector-controlplane.mass-connector.svc.cluster.local:8084/api/v1/dsp
```

### 3.3 Problema Actual Sin Resolver
**Descripción:**  
SSL/TLS certificate validation failure en comunicación DSP entre conectores.

**Error:**
```

```

**Contexto:**

- Esto sugiere que el problema está en alguna llamada HTTPS interna del flujo IATP
- Posibles puntos de fallo:
  1. DIM wallet verification durante IATP handshake
  2. DID document resolution (did:web puede intentar HTTPS)
  3. Credential service validation
  4. Alguna verificación de trusted issuer

**Intentos de solución sin éxito:**
- ✗ EDC_JSONLD_HTTPS_ENFORCE=false (solo afecta JSON-LD contexts)
- ✗ JAVA_TOOL_OPTIONS con trustAll (opción no estándar/no soportada)
- ✗ Usar HTTP en lugar de HTTPS para DSP endpoint (error persiste)

## 4. Flujo IATP/DCP Completo (Referencia)

Para entender dónde puede estar fallando el certificado, este es el flujo completo:

```
1. Consumer (IKLN) inicia catalog request
   ↓
2. IKLN obtiene OAuth token del DIM Wallet
   → POST http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/oauth/token
   [✅ Funciona - configurado con HTTP]
   ↓
3. IKLN consulta BDRS para resolver BPN → DID del Provider
   → GET http://bdrs-server.portal.svc.cluster.local:8082/api/directory/bpn-directory/BPNL00000000MASS
   [✅ Funciona - BDRS URL corregido]
   ↓
4. IKLN obtiene DID Document del Provider
   → GET did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS
   [❓ Puede intentar HTTPS por convención did:web]
   ↓
5. IKLN obtiene SI Token (Self-Issued token) del DIM Wallet
   → POST http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api/sts
   [✅ Configurado con HTTP]
   ↓
6. IKLN envía DSP catalog request al Provider
   → POST https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp
   [❌ FALLA AQUÍ - certificate_unknown]
   ↓
7. Provider valida SI token con DIM Wallet
8. Provider resuelve DID del Consumer via BDRS
9. Provider devuelve catalog
```

**Punto crítico identificado:**  
El error ocurre en el paso 6, pero la causa raíz puede estar en:
- Paso 4: DID document resolution (did:web por defecto intenta HTTPS)
- Paso 6: DSP HTTPS handshake con certificado self-signed

## 7. Próximos Pasos Recomendados para el Lunes

### 7.1 Opción A: Solución SSL Certificados (Recomendada para Producción)
**Objetivo:** Configurar certificados confiables o trust store personalizado.

**Pasos:**
1. **Generar certificado CA interno:**
   ```bash
   # Crear CA autofirmado
   openssl req -x509 -new -nodes -keyout ca-key.pem -out ca-cert.pem -days 3650 \
     -subj "/CN=Catena-X Dev CA"
   
   # Crear certificados para cada servicio firmados por el CA
   ```

2. **Configurar Java trust store en EDCs:**
   ```yaml
   # values-ikln-connector.yaml
   controlplane:
     volumes:
       - name: truststore
         configMap:
           name: edc-truststore
     volumeMounts:
       - name: truststore
         mountPath: /opt/truststore
     env:
       JAVA_TOOL_OPTIONS: >-
         -Djavax.net.ssl.trustStore=/opt/truststore/cacerts
         -Djavax.net.ssl.trustStorePassword=changeit
   ```

3. **Aplicar certificados a Ingress:**
   ```yaml
   ingresses:
     - tls:
         enabled: true
   ```

### 🎯 Problema Central
**SSL Certificate Validation Failure** en algún punto del flujo IATP/DSP. El error ocurre independientemente de si el DSP endpoint usa HTTP o HTTPS, lo que sugiere que hay una llamada HTTPS interna (probablemente DID resolution o credential verification) que está fallando.
