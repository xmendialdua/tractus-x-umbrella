# Despliegue Portal Catena-X con Persistencia PostgreSQL - 2 Febrero 2026

## 📋 Resumen Ejecutivo

Este documento describe el proceso completo de despliegue del Portal Catena-X con persistencia habilitada en todas las bases de datos PostgreSQL, incluyendo los problemas encontrados y sus soluciones.

### 🔴 Problemas Críticos Resueltos:

1. **BPDM PostgreSQL sin persistencia** (Sección 3)
   - StatefulSet con EmptyDir en lugar de PVC

   - Ver sección 4.4 para análisis completo y alternativas de automatización

3. **Pods BPDM en CrashLoopBackOff** (Sección 4)
   - Causado por ConfigMaps con URLs incorrectas
   - Requiere corrección manual de 4 ConfigMaps + reinicio de pods

## 3. ⚠️ PROBLEMA 1: BPDM PostgreSQL Sin Persistencia

### 3.1. Identificación del Problema

Al verificar los PVCs creados:
```bash
kubectl get pvc -n portal
```

**Resultado:** No existía PVC para `bpdm-postgres`

Al verificar el StatefulSet de BPDM:
```bash
kubectl describe statefulset bpdm-postgres -n portal | grep -A10 "Volume Claims"
```

**Resultado:**
```
Volume Claims:     <none>
```

Al verificar los volúmenes del pod:
```bash
kubectl describe pod bpdm-postgres-0 -n portal | grep -A15 "Volumes:"
```

**Resultado:**
```
Volumes:
  dshm:
    Type:       EmptyDir (a temporary directory that shares a pod's lifetime)
  data:
    Type:       EmptyDir (a temporary directory that shares a pod's lifetime)
```

### 3.2. Causa Raíz

**Problema:** Configuración incorrecta de persistencia en el archivo values.

**Configuración incorrecta inicial:**
```yaml
bpdm:
  enabled: true
  bpdm-postgres:  # ❌ Nombre incorrecto
    primary:
      persistence:
        enabled: true
        size: 3Gi
```

**Explicación:** 
- El chart BPDM usa internamente la clave `postgres:` (no `bpdm-postgres:`)
- Al inspeccionar el chart BPDM (`bpdm-6.1.0.tgz`), se encontró la estructura correcta en `bpdm/values.yaml`:

```yaml
postgres:
  enabled: true
  image:
    repository: bitnamilegacy/postgresql
    tag: 15-debian-11
  fullnameOverride: bpdm-postgres
  auth:
    database: bpdm
    username: bpdm
    password: bpdm
```

### 3.3. Solución Aplicada

#### Paso 1: Corregir el archivo de configuración
```yaml
bpdm:
  enabled: true
  postgres:  # ✅ Nombre correcto
    primary:
      persistence:
        enabled: true
        size: 3Gi
```

**Archivo modificado:** `values-adopter-portal-for-onboarding-with-persistence.yaml`

#### Paso 2: Eliminar el StatefulSet existente

**Problema adicional:** Los StatefulSets no permiten modificar los `volumeClaimTemplates` después de la creación.

**Error al intentar helm upgrade:**
```
Error: UPGRADE FAILED: cannot patch "bpdm-postgres" with kind StatefulSet: 
StatefulSet.apps "bpdm-postgres" is invalid: spec: Forbidden: updates to 
statefulset spec for fields other than 'replicas', 'ordinals', 'template', 
'updateStrategy', 'revisionHistoryLimit', 'persistentVolumeClaimRetentionPolicy' 
and 'minReadySeconds' are forbidden
```

**Solución:**
```bash
# Eliminar el StatefulSet sin persistencia
kubectl delete statefulset bpdm-postgres -n portal
```

#### Paso 3: Recrear con persistencia
```bash

  -f values-adopter-portal-for-onboarding-with-persistence.yaml \
  -f values-ovh-hosts-portal.yaml \
  -n portal
```


## ⚠️ 4.4. PROBLEMA CRÍTICO: ConfigMaps de BPDM No se Generan Correctamente

### 4.4.1. ¿Qué son los ConfigMaps de BPDM?

Los **ConfigMaps** son objetos de Kubernetes que almacenan configuración en formato clave-valor. En el caso de BPDM, cada microservicio (Gate, Pool, Orchestrator, Cleaning Service) tiene su propio ConfigMap que contiene:

- **Archivo `deployment.yml`**: Configuración de Spring Boot en formato YAML
- **URLs de servicios**: Direcciones de otros microservicios BPDM y del servidor de autenticación (Keycloak)
- **Configuración de base de datos**: Host del PostgreSQL compartido
- **Configuración de seguridad**: URLs de Keycloak, client IDs, realms

**Ejemplo de estructura del ConfigMap `portal-bpdm-gate`:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: portal-bpdm-gate
data:
  deployment.yml: |-
    bpdm:
      client:
        orchestrator:
          base-url: http://portal-bpdm-orchestrator:80  # URL interna para comunicación
        pool:
          base-url: http://portal-bpdm-pool:80           # URL interna para comunicación
      datasource:
        host: bpdm-postgres                              # Host de PostgreSQL
      security:
        auth-server-url: http://centralidp.51.178.94.25.nip.io/auth  # Keycloak
        client-id: Cl16-CX-BPDMGate
        realm: CX-Central
    server:
      forward-headers-strategy: FRAMEWORK
```

**Los 4 ConfigMaps que requieren corrección manual:**
1. **`portal-bpdm-gate`** - Configuración del servicio Gate (API pública)
2. **`portal-bpdm-pool`** - Configuración del servicio Pool (gestor de datos maestros)
3. **`portal-bpdm-orchestrator`** - Configuración del orquestador (coordinador de servicios)
4. **`portal-bpdm-cleaning-service-dummy`** - Configuración del servicio de limpieza de datos

### 4.4.2. ¿Por qué no se generan correctamente desde el Helm Chart?

#### Causa 1: Valores por Defecto Hardcodeados en el Subchart

El subchart BPDM (versión 6.1.0) tiene valores por defecto hardcodeados en `/charts/bpdm-gate/templates/configMap.yaml`:

```yaml
{{- define "bpdm-gate.configmapDefaults" -}}
bpdm:
  datasource:
    host: {{ include "bpdm.postgresDependency" . }}
  client:
    pool:
      base-url: http://{{ include "bpdm.toReleaseName" (list . "bpdm-pool") }}
    orchestrator:
      base-url: http://{{ include "bpdm.toReleaseName" (list . "bpdm-orchestrator") }}
  security:
    auth-server-url: http://{{ include "bpdm.centralidpDependency" . }}/auth
{{- end -}}
```

La función `include "bpdm.centralidpDependency"` devuelve **`bpdm-centralidp`** por defecto, que se resuelve como **`centralidp.tx.test`** en los valores del subchart BPDM (`/charts/bpdm/values.yaml`):

```yaml
bpdm-gate:
  enabled: true
  applicationConfig:
    bpdm:
      datasource:
        host: bpdm-postgres
      security:
        auth-server-url: "http://bpdm-centralidp/auth"  # ← Valor por defecto del subchart
```

#### Causa 2: Merging Incompleto entre Umbrella y Subchart

El template que genera los ConfigMaps (`bpdm-common/templates/_configMap.tpl`) usa la función `mergeOverwrite`:

```yaml
{{- $defaultValues := fromYaml (include $defaultTemplate $) | default (dict )  -}}
{{- $override := .context.Values.applicationConfig | default (dict ) -}}
{{- $finalValues := mergeOverwrite $defaultValues $override -}}
```

**Problema:** El merge **NO funciona recursivamente** en todas las claves anidadas. Si el parent chart (umbrella) define:

```yaml
bpdm:
  bpdm-gate:
    applicationConfig:
      bpdm:
        security:
          auth-server-url: "http://centralidp.51.178.94.25.nip.io/auth"
```

Y el subchart tiene valores por defecto en múltiples niveles (`bpdm.client.pool.base-url`, `bpdm.security.auth-server-url`), el merge puede:
1. No sobrescribir correctamente los valores anidados profundos
2. Preferir los valores del template por defecto sobre los del values.yaml

#### Causa 3: Referencia a Keycloak Inexistente

El subchart BPDM espera que exista un Keycloak llamado **`bpdm-centralidp`**, pero en el despliegue del Portal:
- El Keycloak central se llama **`centralidp`** (no `bpdm-centralidp`)
- La URL accesible es `http://centralidp.51.178.94.25.nip.io/auth`
- No existe ningún servicio `bpdm-centralidp` en el namespace

**Resultado:** Los ConfigMaps se generan con `http://bpdm-centralidp/auth`, que al no existir, se traduce a `http://centralidp.tx.test/auth` (valor por defecto del dominio).

### 4.4.3. ¿Hay alguna forma de generarlos correctamente desde el origen?

**Respuesta corta: ❌ NO con la versión actual del subchart BPDM 6.1.0**

**Opciones evaluadas:**

**Factible pero NO recomendado:**

- Introduce complejidad en el ciclo de vida del despliegue

#### Opción 4: **Post-Install Hook con Job de Kubernetes** ✅ (Solución Viable)

**Descripción:** Crear un Job de Kubernetes que se ejecute **después** del `helm install/upgrade` para corregir los ConfigMaps automáticamente.

**Ventajas:**
- ✅ No requiere modificar el subchart BPDM
- ✅ Se puede versionar junto con el chart principal
- ✅ Se ejecuta automáticamente después del despliegue
- ✅ Idempotente (se puede ejecutar múltiples veces)

**Implementación:**

Crear archivo `charts/umbrella/templates/bpdm-configmap-fix-job.yaml`:

```yaml
{{- if .Values.bpdm.enabled }}
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-bpdm-configmap-fix
  namespace: {{ .Release.Namespace }}
  annotations:
    "helm.sh/hook": post-install,post-upgrade
    "helm.sh/hook-weight": "5"
    "helm.sh/hook-delete-policy": before-hook-creation
spec:
  template:
    spec:
      serviceAccountName: {{ .Release.Name }}-bpdm-configmap-fix
      restartPolicy: OnFailure
      containers:
      - name: fix-configmaps
        image: bitnami/kubectl:latest
        command:
        - /bin/bash
        - -c
        - |
          set -e
          
          NAMESPACE="{{ .Release.Namespace }}"
          EXTERNAL_IP="{{ .Values.global.domainSuffix | replace ".nip.io" "" }}"
          CENTRALIDP_URL="http://centralidp.${EXTERNAL_IP}.nip.io/auth"
          
          echo "Corrigiendo ConfigMaps de BPDM..."
          
          # Gate
          kubectl get configmap {{ .Release.Name }}-bpdm-gate -n $NAMESPACE -o json | \
            jq --arg url "$CENTRALIDP_URL" \
               '.data."deployment.yml" |= gsub("http://.*centralidp.*/auth"; $url) | 
                .data."deployment.yml" |= gsub("http://business-partners.tx.test/orchestrator"; "http://{{ .Release.Name }}-bpdm-orchestrator:80") |
                .data."deployment.yml" |= gsub("http://business-partners.tx.test/pool"; "http://{{ .Release.Name }}-bpdm-pool:80")' | \
            kubectl apply -f -
          
          # Pool
          kubectl get configmap {{ .Release.Name }}-bpdm-pool -n $NAMESPACE -o json | \
            jq --arg url "$CENTRALIDP_URL" \
               '.data."deployment.yml" |= gsub("http://.*centralidp.*/auth"; $url) | 
                .data."deployment.yml" |= gsub("http://business-partners.tx.test/orchestrator"; "http://{{ .Release.Name }}-bpdm-orchestrator:80")' | \
            kubectl apply -f -
          
          # Orchestrator
          kubectl get configmap {{ .Release.Name }}-bpdm-orchestrator -n $NAMESPACE -o json | \
            jq --arg url "$CENTRALIDP_URL" \
               '.data."deployment.yml" |= gsub("http://.*centralidp.*/auth"; $url)' | \
            kubectl apply -f -
          
          # Cleaning Service
          kubectl get configmap {{ .Release.Name }}-bpdm-cleaning-service-dummy -n $NAMESPACE -o json | \
            jq --arg url "$CENTRALIDP_URL" \
               '.data."deployment.yml" |= gsub("http://.*centralidp.*/auth"; $url) | 
                .data."deployment.yml" |= gsub("http://business-partners.tx.test/orchestrator"; "http://{{ .Release.Name }}-bpdm-orchestrator:80")' | \
            kubectl apply -f -
          
          echo "✅ ConfigMaps corregidos exitosamente"
          
          # Reiniciar pods BPDM para aplicar cambios
          echo "Reiniciando pods BPDM..."
          kubectl delete pod -n $NAMESPACE -l app.kubernetes.io/name=bpdm-gate || true
          kubectl delete pod -n $NAMESPACE -l app.kubernetes.io/name=bpdm-pool || true
          kubectl delete pod -n $NAMESPACE -l app.kubernetes.io/name=bpdm-orchestrator || true
          kubectl delete pod -n $NAMESPACE -l app.kubernetes.io/name=bpdm-cleaning-service-dummy || true
          
          echo "✅ Corrección de BPDM completada"
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: {{ .Release.Name }}-bpdm-configmap-fix
  namespace: {{ .Release.Namespace }}
  annotations:
    "helm.sh/hook": post-install,post-upgrade
    "helm.sh/hook-weight": "1"
    "helm.sh/hook-delete-policy": before-hook-creation
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: {{ .Release.Name }}-bpdm-configmap-fix
  namespace: {{ .Release.Namespace }}
  annotations:
    "helm.sh/hook": post-install,post-upgrade
    "helm.sh/hook-weight": "2"
    "helm.sh/hook-delete-policy": before-hook-creation
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "patch", "update"]
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: {{ .Release.Name }}-bpdm-configmap-fix
  namespace: {{ .Release.Namespace }}
  annotations:
    "helm.sh/hook": post-install,post-upgrade
    "helm.sh/hook-weight": "3"
    "helm.sh/hook-delete-policy": before-hook-creation
subjects:
- kind: ServiceAccount
  name: {{ .Release.Name }}-bpdm-configmap-fix
  namespace: {{ .Release.Namespace }}
roleRef:
  kind: Role
  name: {{ .Release.Name }}-bpdm-configmap-fix
  apiGroup: rbac.authorization.k8s.io
{{- end }}
```

**Uso:**

1. Agregar el archivo al chart umbrella
2. Ejecutar `helm upgrade portal . -f values.yaml`
3. El Job se ejecuta automáticamente después del upgrade
4. Los ConfigMaps se corrigen y los pods se reinician

**Verificación:**

```bash
kubectl get job -n portal | grep bpdm-configmap-fix
kubectl logs -n portal job/portal-bpdm-configmap-fix
```

### 4.6. Arquitectura y Dependencias de BPDM

#### 4.6.1. Arquitectura de Base de Datos

```
bpdm-postgres-0 (StatefulSet único con PVC de 3Gi)
    └─ Base de datos PostgreSQL compartida
        ├─ Schema: bpdm_pool        ← Datos de BPDM Pool
        ├─ Schema: bpdm_gate        ← Datos de BPDM Gate  
        └─ Schema: bpdm_orchestrator ← Compartido
```

**Importante:** 
- Solo hay **1 StatefulSet** para todos los servicios BPDM
- Solo hay **1 PVC** compartido (no 3 separados)
- Los 3 servicios (pool, gate, orchestrator) comparten el mismo PostgreSQL

#### 4.6.2. Dependencias entre Servicios BPDM

```
┌─────────────────────────────────────────────┐
│          BPDM Orchestrator                  │
```

## 6. Lecciones Aprendidas

### 6.1. Sobre StatefulSets y PVCs

**Problema:** Los `volumeClaimTemplates` de un StatefulSet son inmutables.

**Solución:** 
- Para agregar persistencia a un StatefulSet existente, hay que eliminarlo y recrearlo
- Usar `kubectl delete statefulset <name>` sin eliminar los pods (`--cascade=orphan`) si se quieren preservar datos temporales

**Recomendación:** Configurar persistencia desde el primer despliegue.

### 6.2. Sobre Configuración de Subcharts

**Problema:** Los valores configurados en el parent chart (umbrella) no siempre se propagan correctamente a los subcharts.

**Solución:** 
- Inspeccionar el `values.yaml` del subchart para conocer la estructura exacta
- En caso de BPDM: usar `postgres:` en lugar de `bpdm-postgres:`
- Verificar los ConfigMaps generados después del deployment

**Herramientas útiles:**
```bash
# Extraer y revisar subchart
tar -xzf charts/bpdm-6.1.0.tgz
cat bpdm/values.yaml | grep -A20 "^postgres:"

# Verificar ConfigMaps generados
kubectl get configmap <name> -n portal -o yaml
```

### 6.3. Sobre ConfigMaps vs Base de Datos

**Importante distinción:**
- **Job fix-keycloak-urls:** Corrige URLs en las **bases de datos** de Keycloak (PostgreSQL)
- **Corrección de ConfigMaps:** Necesaria para servicios que leen configuración de ConfigMaps (como BPDM)

**Flujo correcto:**
1. Desplegar con helm
2. Ejecutar job de corrección de URLs en BD (fix-keycloak-urls)
3. Corregir ConfigMaps manualmente (si el chart no los genera correctamente)
4. Reiniciar pods afectados

### 6.4. Sobre Dependencias entre Servicios

**Orden de inicio es crítico:**
- Servicios con dependencias fallarán en CrashLoopBackOff si sus dependencias no están listas
- BPDM requiere iniciar en orden: Orchestrator → Pool → Gate/Cleaning

**Solución:**
- Eliminar todos los pods del grupo para forzar recreación simultánea
- Los pods con init containers y health checks manejarán el orden automáticamente

## 10. Lecciones Aprendidas y Recomendaciones

### 10.1. Sobre Configuración de Persistencia

#### ✅ Lección 1: Verificar la estructura de claves del subchart
- **Problema:** Usar `bpdm.bpdm-postgres` en lugar de `bpdm.postgres`
- **Solución:** Extraer y revisar el subchart antes de configurar persistencia
- **Comando:** `tar -xzf charts/bpdm-*.tgz && cat bpdm/values.yaml`

#### ✅ Lección 2: StatefulSet volumeClaimTemplates son inmutables
- **Implicación:** No se puede cambiar persistencia sin eliminar el StatefulSet
- **Proceso requerido:** Delete StatefulSet → Helm upgrade → PVC se crea
- **Riesgo:** Pérdida de datos si el StatefulSet ya contenía datos importantes

### 10.2. 🔴 Sobre ConfigMaps de Subcharts CRÍTICO

#### ⚠️ Lección 3: Los valores de umbrella chart NO siempre se propagan correctamente

**Problema identificado:**
- Los subcharts BPDM generan ConfigMaps con valores por defecto hardcodeados
- La función `mergeOverwrite` de Helm no sobrescribe correctamente valores anidados profundos
- Los templates del subchart referencian `bpdm-centralidp` que no existe en el deployment

**Impacto:**
- **CRÍTICO:** Sin corrección manual, los pods BPDM fallan con `UnknownHostException`
- Los 4 ConfigMaps (gate, pool, orchestrator, cleaning-service) quedan incorrectos
- Requiere intervención manual después de CADA `helm upgrade`

**Alternativas evaluadas:**
1. ❌ Sobrescribir `applicationConfig` en values - NO funciona por estructura de claves
2. ❌ Deshabilitar `centralidp` del subchart - Los templates ignoran el override
3. ⚠️ Fork del subchart - Posible pero requiere mantenimiento continuo
4. ✅ Post-Install Hook con Job - **SOLUCIÓN RECOMENDADA** (ver sección 4.4.3)

**Acción recomendada:**
- **Corto plazo:** Usar script `fix-bpdm-configmaps.sh` después de cada despliegue
- **Medio plazo:** Implementar Post-Install Hook como template del umbrella chart
- **Largo plazo:** Contribuir fix al repositorio upstream del subchart BPDM

📖 **Ver Sección 4.4 para análisis técnico completo**

### 10.3. Sobre Orden de Inicio de Servicios

#### ✅ Lección 4: Las dependencias entre microservicios deben respetarse
- **Orden correcto:** Orchestrator → Pool → Gate/Cleaning
- **Beneficio de eliminar todos juntos:** Los init containers y health checks manejan el orden
- **Evitar:** Reiniciar solo un pod cuando las dependencias han cambiado
