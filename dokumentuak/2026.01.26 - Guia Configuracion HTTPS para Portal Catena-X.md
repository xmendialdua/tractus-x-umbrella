## Introducción

### ¿Por qué HTTPS?

HTTPS (HTTP Secure) proporciona:
- **Encriptación**: Protege datos en tránsito
- **Autenticación**: Verifica la identidad del servidor
- **Integridad**: Previene manipulación de datos
- **Conformidad**: Requerido por estándares de seguridad
- **SEO y Confianza**: Mejor posicionamiento y confianza del usuario

### ¿Cuándo usar HTTPS?

- ✅ **SIEMPRE en producción**
- ✅ Entornos de staging/pre-producción
- ✅ Cuando se manejan datos sensibles
- ⚠️ Opcional en desarrollo local (pero recomendado)

### Diferencias con HTTP

En el despliegue HTTP actual documentado en [2026.01.26 - Solucion Errores Keycloak - Cookie y HTTPS.md](./2026.01.26%20-%20Solucion%20Errores%20Keycloak%20-%20Cookie%20y%20HTTPS.md), se requirió:
- Modificar `ssl_required = 'NONE'` en la base de datos
- Configurar `KC_HOSTNAME_STRICT_HTTPS = false`
- Permitir `KC_HTTP_ENABLED = true`

Con HTTPS, estos cambios **NO son necesarios**. Keycloak funciona con su configuración segura por defecto.

## Opción 1: HTTPS con nip.io

### ¿Qué es nip.io?

[nip.io](https://nip.io) es un servicio DNS wildcard gratuito que resuelve IPs en formato:
```
centralidp.51.68.114.44.nip.io → 51.68.114.44
cualquier-subdomain.IP.nip.io → IP
```

### Ventajas de HTTPS con nip.io

- ✅ **No necesitas dominio propio**
- ✅ **Certificados gratuitos** con Let's Encrypt
- ✅ **Automático** con cert-manager
- ✅ **Rápido de configurar** (< 15 minutos)
- ✅ **Ideal para desarrollo/pruebas** con seguridad real
- ✅ **Fácil de migrar** a dominio propio después

### Limitaciones

- ⚠️ Dependes del servicio nip.io
- ⚠️ No es "profesional" para clientes
- ⚠️ Límites de Let's Encrypt (50 certs/semana por dominio base)

### Configuración Paso a Paso

#### 1. Instalar cert-manager

```bash
# Instalar cert-manager v1.13.0

# Verificar instalación
kubectl get pods -n cert-manager

# cert-manager-webhook-xxxxx      1/1     Running
```

#### 2. Crear ClusterIssuer para Let's Encrypt

**Archivo:** `charts/umbrella/cluster-issuer-letsencrypt.yaml`

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # Servidor de Let's Encrypt (producción)
    server: https://acme-v02.api.letsencrypt.org/directory
    
    # Tu email (recibirás notificaciones de expiración)
    email: tu-email@ejemplo.com
    
    # Secret donde se guarda la clave privada de la cuenta ACME
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    
    # Solvers: cómo validar que controlas el dominio
    solvers:
    - http01:
        ingress:
          class: nginx
```

**Aplicar:**
```bash
kubectl apply -f charts/umbrella/cluster-issuer-letsencrypt.yaml

# Verificar
kubectl get clusterissuer
# NAME                READY   AGE
# letsencrypt-prod    True    10s
```

## Configuración de Ingress para TLS

### Estructura de un Ingress con TLS

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ejemplo-ingress
  annotations:
    # Solicitar certificado automáticamente
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    
    # Forzar redirección HTTP → HTTPS
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    
    # Configuraciones de seguridad adicionales
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/ssl-protocols: "TLSv1.2 TLSv1.3"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - ejemplo.dominio.com
      secretName: ejemplo-tls  # cert-manager creará este secret
  rules:
    - host: ejemplo.dominio.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ejemplo-service
                port:
                  number: 8080
```

### Proceso de Emisión de Certificados

1. **cert-manager detecta el Ingress** con la anotación `cert-manager.io/cluster-issuer`
2. **Crea un Certificate resource** automáticamente
3. **Solicita el certificado** a Let's Encrypt vía protocolo ACME
4. **Let's Encrypt valida** que controlas el dominio (HTTP-01 challenge)
5. **cert-manager recibe** el certificado firmado
6. **Almacena** el certificado en el Secret especificado
7. **El Ingress** usa el certificado para TLS

### Anotaciones Útiles para Ingress con TLS

```yaml
annotations:
  # Emisor de certificados
  cert-manager.io/cluster-issuer: "letsencrypt-prod"
  
  # Redirección SSL
  nginx.ingress.kubernetes.io/ssl-redirect: "true"
  nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
  
  # Protocolos TLS permitidos
  nginx.ingress.kubernetes.io/ssl-protocols: "TLSv1.2 TLSv1.3"
  
  # Ciphers seguros
  nginx.ingress.kubernetes.io/ssl-ciphers: "HIGH:!aNULL:!MD5"
  
  # HSTS (HTTP Strict Transport Security)
  nginx.ingress.kubernetes.io/hsts: "true"
  nginx.ingress.kubernetes.io/hsts-max-age: "31536000"
  nginx.ingress.kubernetes.io/hsts-include-subdomains: "true"
  
  # Configuración de proxy para backends
  nginx.ingress.kubernetes.io/backend-protocol: "HTTP"
  nginx.ingress.kubernetes.io/proxy-body-size: "8m"
```

## Configuración de Keycloak para HTTPS

### Variables de Entorno Críticas

| Variable | HTTP | HTTPS | Descripción |
|----------|------|-------|-------------|
| `KEYCLOAK_FRONTEND_URL` | `http://...` | `https://...` | URL pública de Keycloak |
| `KEYCLOAK_PRODUCTION` | `false` | `true` | Modo producción |
| `KC_HTTP_ENABLED` | `true` | `false` | Habilitar HTTP interno |
| `KC_HOSTNAME_STRICT` | `false` | `true` | Validación estricta de hostname |
| `KC_HOSTNAME_STRICT_HTTPS` | `false` | `true` | Requerir HTTPS |
| `KC_PROXY` | `edge` | `edge` | Tipo de proxy (sin cambio) |
| `KC_HOSTNAME` | dominio | dominio | Hostname público |

### Configuración Completa de Central IDP para HTTPS

```yaml
centralidp:
  keycloak:
    ingress:
      enabled: true
      ingressClassName: "nginx"
      hostname: "centralidp.example.com"
      annotations:
        # Certificado TLS
        cert-manager.io/cluster-issuer: "letsencrypt-prod"
        nginx.ingress.kubernetes.io/ssl-redirect: "true"
        nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
        
        # CORS para HTTPS
        nginx.ingress.kubernetes.io/cors-allow-origin: "https://*.example.com"
        nginx.ingress.kubernetes.io/enable-cors: "true"
        
        # Configuración de sesión
        nginx.ingress.kubernetes.io/affinity: "cookie"
        nginx.ingress.kubernetes.io/session-cookie-name: "route"
        nginx.ingress.kubernetes.io/session-cookie-hash: "sha1"
        nginx.ingress.kubernetes.io/session-cookie-secure: "true"
        
        # Tamaño de buffer para headers grandes
        nginx.ingress.kubernetes.io/proxy-buffer-size: "128k"
        
        # Seguridad adicional
        nginx.ingress.kubernetes.io/hsts: "true"
        nginx.ingress.kubernetes.io/hsts-max-age: "31536000"
      
      tls: true
      tlsSecrets:
        - "centralidp-tls"
    
    extraEnvVars:
      # URL frontend con HTTPS
      - name: KEYCLOAK_FRONTEND_URL
        value: "https://centralidp.example.com/auth/"
      
      # Forwarding de direcciones de proxy
      - name: KEYCLOAK_PROXY_ADDRESS_FORWARDING
        value: "true"
      
      # No adjuntar ruta en cookies de sesión
      - name: KC_SPI_STICKY_SESSION_ENCODER_INFINISPAN_SHOULD_ATTACH_ROUTE
        value: "false"
      
      # MODO PRODUCCIÓN HABILITADO
      - name: KEYCLOAK_PRODUCTION
        value: "true"
      
      # HTTP DESHABILITADO (solo escucha internamente)
      - name: KC_HTTP_ENABLED
        value: "false"
      
      # HOSTNAME ESTRICTO HABILITADO
      - name: KC_HOSTNAME_STRICT
        value: "true"
      
      # HTTPS ESTRICTO HABILITADO
      - name: KC_HOSTNAME_STRICT_HTTPS
        value: "true"
      
      # Tipo de proxy (edge = termina TLS en el ingress)
      - name: KC_PROXY
        value: "edge"
      
      # Hostname público
      - name: KC_HOSTNAME
        value: "centralidp.example.com"
      
      # Path base
      - name: KC_HOSTNAME_PATH
        value: "/auth/"
    
    # Recursos recomendados para producción
    resources:
      requests:
        memory: "1024Mi"
        cpu: "500m"
      limits:
        memory: "2048Mi"
        cpu: "1000m"
    
    # Replicas para alta disponibilidad
    replicaCount: 2
```

### Configuración de Base de Datos

**IMPORTANTE:** Con HTTPS correctamente configurado, **NO necesitas** modificar `ssl_required` en la base de datos.

Los realms mantendrán sus valores por defecto seguros:
- `ssl_required = 'EXTERNAL'` (recomendado)
- `ssl_required = 'ALL'` (más estricto)

### Diferencias Clave: HTTP vs HTTPS

#### Con HTTP (configuración actual)
```yaml
extraEnvVars:
  - name: KEYCLOAK_FRONTEND_URL
    value: "http://centralidp.51.68.114.44.nip.io/auth/"
  - name: KEYCLOAK_PRODUCTION
    value: "false"  # ← Modo desarrollo
  - name: KC_HTTP_ENABLED
    value: "true"   # ← HTTP habilitado
  - name: KC_HOSTNAME_STRICT_HTTPS
    value: "false"  # ← No requiere HTTPS

# Y además necesitas:
# - Ejecutar Job para cambiar ssl_required a 'NONE' en DB
# - Reiniciar pods después del Job
```

#### Con HTTPS (producción)
```yaml
extraEnvVars:
  - name: KEYCLOAK_FRONTEND_URL
    value: "https://centralidp.example.com/auth/"
  - name: KEYCLOAK_PRODUCTION
    value: "true"   # ← Modo producción
  - name: KC_HTTP_ENABLED
    value: "false"  # ← Solo HTTPS
  - name: KC_HOSTNAME_STRICT_HTTPS
    value: "true"   # ← Requiere HTTPS

# NO necesitas:
# - Job para modificar ssl_required
# - Cambios en la base de datos
# Los valores por defecto de Keycloak son seguros
```

## Migración de HTTP a HTTPS

### Planificación

1. **Tiempo estimado**: 30-60 minutos
2. **Downtime**: 5-10 minutos (durante el upgrade)
3. **Reversible**: Sí (hacer downgrade a HTTP si es necesario)

### Checklist Pre-Migración

- [ ] cert-manager instalado y funcionando
- [ ] ClusterIssuer creado y READY
- [ ] Archivo de valores HTTPS preparado
- [ ] DNS configurado (si usas dominio propio)
- [ ] Backup de valores actuales
- [ ] Backup de base de datos (opcional pero recomendado)
- [ ] Usuarios notificados del mantenimiento

### Procedimiento Paso a Paso

#### 1. Backup

```bash
# Backup de la configuración actual
helm get values portal -n portal > backup-values-http.yaml

# Backup de base de datos (opcional)
kubectl exec -n portal portal-centralidp-postgresql-0 -- \
  pg_dump -U kccentral iamcentralidp > backup-centralidp.sql
```

#### 2. Instalar cert-manager (si no está)

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.0/cert-manager.yaml

# Esperar a que esté listo
kubectl wait --for=condition=available --timeout=300s \
  deployment/cert-manager -n cert-manager
```

#### 3. Crear ClusterIssuer

```bash
kubectl apply -f charts/umbrella/cluster-issuer-letsencrypt.yaml

# Verificar
kubectl get clusterissuer letsencrypt-prod
```

#### 4. Preparar archivo de valores HTTPS

Copia tu archivo actual y modifica:
- Cambiar todas las URLs de `http://` a `https://`
- Agregar `tls: true` en todos los ingress
- Agregar `tlsSecrets` en ingress
- Modificar extraEnvVars de Keycloak

```bash
cp values-ovh-hosts-portal.yaml values-ovh-hosts-portal-https.yaml
# Editar manualmente las diferencias
```

#### 5. Aplicar upgrade

```bash
cd ~/projects/assembly/tractus-x-umbrella/charts/umbrella

helm upgrade portal . \
  -f values-adopter-portal.yaml \
  -f values-ovh-hosts-portal-https.yaml \
  -n portal
```

#### 6. Monitorear emisión de certificados

```bash
# Ver progreso
watch kubectl get certificates -n portal

# Ver logs de cert-manager
kubectl logs -f -n cert-manager deployment/cert-manager

# Ver challenges (validaciones ACME)
kubectl get challenges -n portal
```

**Nota:** La primera emisión de certificados puede tardar 2-5 minutos.

#### 7. Verificar pods

```bash
# Ver que los pods se reinician correctamente
kubectl get pods -n portal -w

# Verificar logs de Keycloak
kubectl logs -n portal portal-centralidp-0 | grep -i "started in"
```

#### 8. Probar acceso

```bash
# Probar HTTPS
curl -I https://centralidp.51.68.114.44.nip.io/auth/

# Verificar que HTTP redirige a HTTPS
curl -I http://centralidp.51.68.114.44.nip.io/auth/
# Debe mostrar: Location: https://...
```

#### 9. Verificar Keycloak

1. Acceder a: https://centralidp.51.68.114.44.nip.io/auth/
2. Login con usuario admin
3. Verificar que no hay errores
4. Revisar Master realm → Realm Settings → General
   - SSL Required debe mostrar "external requests" o "all requests"

### Rollback (si es necesario)

```bash
# Volver a HTTP
helm upgrade portal . \
  -f values-adopter-portal.yaml \
  -f values-ovh-hosts-portal.yaml \
  -n portal

# Aplicar Job para deshabilitar SSL en realms
kubectl apply -f charts/umbrella/fix-https-requirement-job.yaml

# Reiniciar Keycloak
kubectl delete pod -n portal -l app.kubernetes.io/name=centralidp
kubectl delete pod -n portal -l app.kubernetes.io/name=sharedidp
```

### Problemas Comunes y Soluciones

#### Problema 1: Certificado no se emite

**Síntomas:**
```bash
kubectl get certificates -n portal
# NAME             READY   SECRET           AGE
# centralidp-tls   False   centralidp-tls   5m
```

**Diagnóstico:**
```bash
# Ver detalles
kubectl describe certificate centralidp-tls -n portal

# Ver challenges
kubectl get challenges -n portal

# Ver orders
kubectl get orders -n portal
```

**Causas comunes:**
- DNS no resuelve correctamente
- Puerto 80 no accesible para validación HTTP-01
- ClusterIssuer mal configurado
- Email inválido en ClusterIssuer
- Rate limit de Let's Encrypt alcanzado

**Solución:**
```bash
# Verificar DNS
nslookup centralidp.51.68.114.44.nip.io

# Verificar accesibilidad
curl http://centralidp.51.68.114.44.nip.io/.well-known/acme-challenge/test

# Ver logs de cert-manager
kubectl logs -n cert-manager deployment/cert-manager --tail=50

# Eliminar y recrear certificado
kubectl delete certificate centralidp-tls -n portal
# El ingress lo recreará automáticamente
```

#### Problema 2: Error "HTTPS required" sigue apareciendo

**Causa:** Variables de entorno no actualizadas en Keycloak

**Solución:**
```bash
# Verificar variables
kubectl describe pod portal-centralidp-0 -n portal | grep -A 5 KC_HOSTNAME

# Si están mal, actualizar values y hacer upgrade
helm upgrade portal . \
  -f values-adopter-portal.yaml \
  -f values-ovh-hosts-portal-https.yaml \
  -n portal

# Forzar recreación de pods
kubectl delete pod portal-centralidp-0 -n portal
```

#### Problema 3: Redirección infinita HTTP ↔ HTTPS

**Causa:** Configuración incorrecta de proxy

**Solución:**
```bash
# Verificar que KC_PROXY esté en "edge"
kubectl get pod portal-centralidp-0 -n portal -o yaml | grep KC_PROXY

# Verificar anotaciones del ingress
kubectl get ingress portal-centralidp -n portal -o yaml | grep ssl-redirect
```

#### Problema 4: Certificado autofirmado o inválido

**Causa:** cert-manager no funcionó correctamente

**Solución:**
```bash
# Ver el certificado actual
kubectl get secret centralidp-tls -n portal -o jsonpath='{.data.tls\.crt}' | \
  base64 -d | openssl x509 -text -noout | grep "Issuer:"

# Debe decir: Issuer: C=US, O=Let's Encrypt, CN=R3
# Si dice: Issuer: CN=Kubernetes Ingress Controller Fake Certificate
# Entonces cert-manager no está funcionando

# Eliminar secret y certificado
kubectl delete secret centralidp-tls -n portal
kubectl delete certificate centralidp-tls -n portal

# Esperar recreación automática
kubectl get certificates -n portal -w
```

#### Problema 5: Rate limit de Let's Encrypt

**Síntomas:**
```
Error: too many certificates already issued for: nip.io
```

**Causa:** Superaste el límite de 50 certificados por semana para nip.io

**Soluciones:**
1. **Esperar una semana** (no ideal)
2. **Usar staging** temporalmente:
   ```yaml
   # En ClusterIssuer
   server: https://acme-staging-v02.api.letsencrypt.org/directory
   ```
3. **Usar dominio propio** (recomendado para producción)

#### Problema 6: Pods no inician después del upgrade

**Diagnóstico:**
```bash
kubectl get pods -n portal
kubectl describe pod portal-centralidp-0 -n portal
kubectl logs portal-centralidp-0 -n portal
```

**Causas comunes:**
- Variables de entorno inválidas
- Recursos insuficientes
- Problemas de conectividad con PostgreSQL

**Solución:**
```bash
# Ver eventos
kubectl get events -n portal --sort-by='.lastTimestamp' | tail -20

# Rollback si es necesario
helm rollback portal -n portal
```

### Recomendaciones por Entorno

#### Desarrollo Local
- **Opción:** HTTP o HTTPS con nip.io
- **Razón:** Rápido de configurar, menor complejidad
- **Consideración:** Si trabajas con OAuth/OIDC, HTTPS es mejor

#### Testing/Staging
- **Opción:** HTTPS con nip.io
- **Razón:** Similar a producción, certificados reales, sin costo de dominio
- **Consideración:** Ideal para validar antes de producción

#### Pre-Producción
- **Opción:** HTTPS con dominio propio
- **Razón:** Idéntico a producción, pruebas finales
- **Consideración:** Usar subdominio de staging (ej: staging.example.com)

#### Producción
- **Opción:** HTTPS con dominio propio
- **Razón:** Profesional, confiable, cumple normativas
- **Consideración:** Configurar monitoring y alertas de certificados

## Configuraciones Avanzadas

### HSTS (HTTP Strict Transport Security)

Fuerza a los navegadores a usar siempre HTTPS:

```yaml
ingress:
  annotations:
    nginx.ingress.kubernetes.io/hsts: "true"
    nginx.ingress.kubernetes.io/hsts-max-age: "31536000"  # 1 año
    nginx.ingress.kubernetes.io/hsts-include-subdomains: "true"
    nginx.ingress.kubernetes.io/hsts-preload: "true"
```

### Configuración de Ciphers Seguros

```yaml
ingress:
  annotations:
    nginx.ingress.kubernetes.io/ssl-protocols: "TLSv1.2 TLSv1.3"
    nginx.ingress.kubernetes.io/ssl-ciphers: "ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384"
    nginx.ingress.kubernetes.io/ssl-prefer-server-ciphers: "true"
```

### Certificados Wildcard

Un solo certificado para todos los subdominios:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: wildcard-certificate
  namespace: portal
spec:
  secretName: wildcard-tls
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - "*.example.com"
    - "example.com"
```

**Nota:** Requiere validación DNS-01 en lugar de HTTP-01.

### Monitoring de Certificados

```bash
# Ver estado de todos los certificados
kubectl get certificates -A

# Crear alerta para certificados próximos a expirar
# (cert-manager renueva automáticamente, pero es bueno monitorear)
kubectl get certificates -n portal -o json | \
  jq '.items[] | {name: .metadata.name, ready: .status.conditions[0].status, notAfter: .status.notAfter}'
```

## Mejores Prácticas

### 1. Usar cert-manager con Helm

Más control y fácil de actualizar:

```bash
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set installCRDs=true
```

### 2. Separar ClusterIssuer de Staging y Producción

```yaml
# Staging (para pruebas)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    ...

# Producción
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    ...
```

### 3. Mantener Contraseñas Seguras en Secrets

No incluir contraseñas en values.yaml, usar secrets:

```bash
kubectl create secret generic keycloak-admin \
  --from-literal=password='TuPasswordSeguro' \
  -n portal
```

### 4. Configurar Recursos Adecuados

Para producción, aumentar recursos de Keycloak:

```yaml
centralidp:
  keycloak:
    resources:
      requests:
        memory: "1024Mi"
        cpu: "500m"
      limits:
        memory: "2048Mi"
        cpu: "1000m"
    replicaCount: 2  # Alta disponibilidad
```

### 5. Habilitar Logging y Monitoring

```yaml
centralidp:
  keycloak:
    extraEnvVars:
      - name: KC_LOG_LEVEL
        value: "INFO"
      - name: KC_METRICS_ENABLED
        value: "true"
      - name: KC_HEALTH_ENABLED
        value: "true"
```

### 6. Backup Regular

```bash
# Script de backup automático
#!/bin/bash
DATE=$(date +%Y%m%d_%H%M%S)

# Backup de configuración
helm get values portal -n portal > backup_${DATE}_values.yaml

# Backup de base de datos
kubectl exec -n portal portal-centralidp-postgresql-0 -- \
  pg_dump -U kccentral iamcentralidp | \
  gzip > backup_${DATE}_centralidp.sql.gz
```
