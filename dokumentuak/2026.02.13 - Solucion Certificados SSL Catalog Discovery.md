# Solución: Catalog Discovery con Certificados SSL Autofirmados

**Fecha:** 13 de febrero de 2026  
**Problema:** Los conectores EDC Tractus-X no pueden realizar catalog discovery entre ellos debido a que no confían en los certificados SSL autofirmados  
**Estado:** ✅ **RESUELTO**

## Contexto del Problema

### Infraestructura Desplegada

- **Cluster:** OVH Kubernetes (microk8s)
- **Namespace:** `umbrella`
- **Conectores EDC:**
  - IKLN Connector (BPNL00000002IKLN) - Consumer
  - MASS Connector (BPNL00000000MASS) - Provider
- **Dominio:** `51.178.94.25.nip.io`
- **Endpoints HTTPS:**
  - `https://edc-ikln-control.51.178.94.25.nip.io`
  - `https://edc-mass-control.51.178.94.25.nip.io`
  - `https://edc-ikln-data.51.178.94.25.nip.io`
  - `https://edc-mass-data.51.178.94.25.nip.io`

### Certificados SSL Desplegados

Se creó una infraestructura de certificados SSL usando **cert-manager** con una CA interna:

1. **ClusterIssuer:** `selfsigned-issuer` (crea el certificado raíz)
2. **Certificate:** `my-selfsigned-ca` (CN: 51.178.94.25.nip.io)
3. **ClusterIssuer:** `my-ca-issuer` (firma certificados para los endpoints)
4. **Certificates:** 4 certificados TLS para los 4 endpoints EDC

**Problema identificado:**
- Los certificados están firmados por una CA interna (autofirmada)
- El sistema operativo local confía en ellos (después de instalar el CA root)
- Los navegadores confían en ellos (después de instalar el CA root)
- **PERO** los pods Java de los EDC connectors NO confían en ellos por defecto

## Análisis del Error

### Error Inicial

Al intentar hacer catalog query desde IKLN a MASS:

```bash
curl -X POST https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: ikln-api-key-change-in-production" \
  -d '{
    "@context": {"@vocab": "https://w3id.org/edc/v0.0.1/ns/"},
    "@type": "CatalogRequest",
    "counterPartyAddress": "https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS",
    "protocol": "dataspace-protocol-http"
  }'
```

**Respuesta:**
```json
[{
  "message": "org.eclipse.edc.http.spi.EdcHttpClientException: (certificate_unknown) PKIX path building failed: sun.security.provider.certpath.SunCertPathBuilderException: unable to find valid certification path to requested target",
  "type": "BadGateway",
  "path": null,
  "invalidValue": null
}]
```

### Diagnóstico

1. **Error SSL/TLS:** El cliente HTTP en Java (JVM) no confía en el certificado del servidor MASS
2. **Causa:** El truststore de Java por defecto (`$JAVA_HOME/lib/security/cacerts`) no contiene nuestro certificado CA interno
3. **Impacto:** Comunicación DSP (Dataspace Protocol) entre conectores bloqueada

## Soluciones Intentadas

### ❌ Intento #1: ConfigMap Separado + extraVolumes/extraVolumeMounts

**Enfoque:**
Crear un ConfigMap con el certificado CA y montarlo en los pods usando `extraVolumes` y `extraVolumeMounts`.

**Implementación:**

```yaml
# charts/dataspace-connector-bundle/values-ikln-connector.yaml
tractusx-connector:
  controlplane:
    extraVolumes:
      - name: truststore
        configMap:
          name: edc-truststore
    extraVolumeMounts:
      - name: truststore
        mountPath: /opt/java/truststore
        readOnly: true
    env:
      JAVA_TOOL_OPTIONS: "-Djavax.net.ssl.trustStore=/opt/java/truststore/cacerts -Djavax.net.ssl.trustStorePassword=changeit"
```

**Script creado:** `create-java-truststore.sh`
- Usaba Docker para crear un truststore Java con el certificado CA importado
- Generaba ConfigMap `edc-truststore` con el archivo `cacerts`

**Resultado:** ❌ **FALLÓ**

**Razón del fallo:**
El chart `tractusx-connector` **NO soporta** los parámetros `extraVolumes` y `extraVolumeMounts`. Helm aplicó la configuración pero no la pasó al deployment subyacente.

Verificación:
```bash
kubectl exec -n umbrella ikln-edc-controlplane-xxx -- ls -la /opt/java/truststore/
# ls: cannot access '/opt/java/truststore/': No such file or directory
```

### ❌ Intento #2: initContainers Personalizados

**Enfoque:**
Usar `initContainers` para copiar el truststore de Java por defecto y añadirle el certificado CA.

**Implementación:**

```yaml
tractusx-connector:
  controlplane:
    initContainers:
      - name: import-ca-cert
        image: eclipse-temurin:17-jre-alpine
        command:
          - sh
          - -c
          - |
            cp $JAVA_HOME/lib/security/cacerts /tmp/truststore/cacerts
            chmod 644 /tmp/truststore/cacerts
            keytool -importcert -noprompt -trustcacerts \
              -alias tractus-x-ca \
              -file /tmp/ca-certificates/ca.crt \
              -keystore /tmp/truststore/cacerts \
              -storepass changeit
        volumeMounts:
          - name: ca-cert
            mountPath: /tmp/ca-certificates
            readOnly: true
          - name: truststore
            mountPath: /tmp/truststore
```

**Resultado:** ❌ **FALLÓ**

**Error:**
```
Error: UPGRADE FAILED: cannot patch "ikln-edc-controlplane" with kind Deployment: 
Deployment.apps "ikln-edc-controlplane" is invalid: 
[spec.template.spec.initContainers[0].volumeMounts[0].name: Not found: "ca-cert", 
spec.template.spec.initContainers[0].volumeMounts[1].name: Not found: "truststore"]
```

**Razón del fallo:**
Los volúmenes referenciados en `volumeMounts` no existen porque `extraVolumes` no se aplica. La configuración es circular: necesitamos volúmenes para los initContainers, pero los volúmenes no se crean.

### ⚠️ Intento #3: Deshabilitar Verificación SSL (RECHAZADO)

**Enfoque:**
Configurar Java para que no verifique certificados SSL usando `JAVA_TOOL_OPTIONS`.

**Implementación:**

```yaml
tractusx-connector:
  controlplane:
    env:
      JAVA_TOOL_OPTIONS: "-Djdk.internal.httpclient.disableHostnameVerification=true"
```

**Estado:** ⚠️ **FUNCIONARÍA PERO RECHAZADO**

**Razón del rechazo:**
Esta solución deshabilita completamente la verificación SSL, lo cual es una mala práctica de seguridad. Solo es aceptable en entornos de desarrollo muy controlados, pero:
- Expone a ataques man-in-the-middle
- No es apropiado ni para pre-producción
- No es la forma correcta de resolver el problema
- El usuario rechazó esta aproximación buscando una solución más robusta

## Solución Final Exitosa

### ✅ Solución: Parámetro `customCaCerts` del Chart

**Descubrimiento:**
Investigando el repositorio upstream `eclipse-tractusx/tractusx-edc`, se descubrió que el chart `tractusx-connector` tiene soporte nativo para añadir certificados CA personalizados mediante el parámetro **`customCaCerts`**.

**Cómo funciona:**

1. **Template ConfigMap:** El chart crea automáticamente un ConfigMap con los certificados proporcionados
   ```yaml
   # charts/tractusx-connector/templates/configmap-customcacerts.yaml
   apiVersion: v1
   kind: ConfigMap
   metadata:
     name: {{ include "txdc.fullname" . }}-custom-cacerts
   data:
     {{- .Values.customCaCerts | toYaml | nindent 2 }}
   ```

2. **InitContainer automático:** El chart genera un initContainer que:
   - Copia el truststore Java por defecto: `/opt/java/openjdk/lib/security/cacerts`
   - Itera sobre todos los archivos `.crt` o `.pem` en el ConfigMap
   - Importa cada certificado al truststore usando `keytool`
   - Guarda el truststore modificado en un volumen compartido

3. **Montaje en contenedor principal:** El truststore modificado se monta en:
   ```
   /opt/java/openjdk/lib/security/cacerts
   ```
   Reemplazando el truststore por defecto.

## Lecciones Aprendidas

### 1. **Usar Características Nativas del Chart**

❌ **Error:** Intentar implementar soluciones personalizadas con parámetros genéricos como `extraVolumes`  
✅ **Correcto:** Investigar primero la documentación y valores del chart para encontrar características nativas

**Cómo investigar:**
```bash
# Ver todos los valores disponibles del chart
helm show values tractusx-dev/tractusx-connector | less

# Buscar parámetros específicos
helm show values tractusx-dev/tractusx-connector | grep -i "cert\|trust\|ca"

# Ver los templates del chart
git clone https://github.com/eclipse-tractusx/tractusx-edc.git
cd tractusx-edc/charts/tractusx-connector/templates
grep -r "customCaCerts" .
```

### 2. **Verificar Soporte de Parámetros en el Deployment Real**

Cuando configures valores de Helm, verifica que realmente se aplican:

```bash
# Ver el deployment generado
kubectl get deployment <name> -o yaml

# Buscar volúmenes configurados
kubectl get deployment <name> -o yaml | grep -A 20 "volumes:"

# Verificar dentro del pod
kubectl exec -n <namespace> <pod-name> -- ls -la <path>
```

### 3. **Entender el Ciclo de Vida de InitContainers**

Los `initContainers` en `customCaCerts`:
1. Se ejecutan **antes** del contenedor principal
2. Comparten volúmenes (`emptyDir`) con el contenedor principal
3. Preparan el entorno (truststore) para el contenedor principal
4. Si fallan, el pod no arranca

**Ventajas:**
- Separación de responsabilidades (preparación vs ejecución)
- Reutilizable para múltiples certificados
- No requiere modificar la imagen del contenedor

### 4. **Diferencia entre ConfigMap como Volumen vs Init**

| Enfoque | Cuándo Usar | Limitaciones |
|---------|-------------|--------------|
| **ConfigMap montado directamente** | Archivos de configuración estáticos (properties, yaml) | No permite procesamiento, solo lectura |
| **InitContainer + ConfigMap** | Cuando necesitas procesar/modificar archivos antes de usarlos | Requiere soporte del chart |
| **customCaCerts (nuestro caso)** | Certificados CA que deben importarse a truststore Java | Específico para certificados, automatizado |

### 5. **Debugging de Problemas SSL en Java**

Comandos útiles para diagnosticar problemas de certificados:

```bash
# Ver certificados en el truststore
keytool -list -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit

# Ver detalles de un certificado específico
keytool -list -v -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit -alias tractus-x-ca

# Verificar logs del EDC
kubectl logs -n umbrella <pod-name> | grep -i "ssl\|certificate\|trust"

# Habilitar debug SSL en Java (si es necesario)
JAVA_TOOL_OPTIONS: "-Djavax.net.debug=ssl:handshake:verbose"
```

### 6. **Secuencia de Resolución de Problemas Recomendada**

Para problemas de certificados SSL en Kubernetes:

1. **Verificar que el certificado existe y es válido**
   ```bash
   openssl x509 -in cert.crt -text -noout
   ```

2. **Verificar que el secret/configmap está creado**
   ```bash
   kubectl get secret/configmap -n <namespace>
   ```

3. **Verificar que el volumen se monta correctamente**
   ```bash
   kubectl describe pod <pod-name>
   kubectl exec <pod-name> -- ls -la <mount-path>
   ```

4. **Verificar que la aplicación lee el certificado**
   ```bash
   # Ver variables de entorno
   kubectl exec <pod-name> -- env | grep -i java

   # Ver certificados en truststore
   kubectl exec <pod-name> -- keytool -list -keystore <path>
   ```

5. **Probar conectividad SSL desde el pod**
   ```bash
   kubectl exec <pod-name> -- openssl s_client -connect <host>:<port>
   ```

### 7. **Documentación para Producción**

Para desplegar en producción, considera:

1. **Certificados de CA Comercial:** Usar Let's Encrypt o CA comercial en lugar de certificados autofirmados
2. **Renovación Automática:** cert-manager renueva automáticamente, pero `customCaCerts` requiere actualización manual del values
3. **Múltiples Entornos:** Extraer el certificado a un archivo separado y referenciarlo:
   ```yaml
   customCaCerts:
     {{- .Files.Get "certs/ca.crt" | nindent 4 }}
   ```
4. **Secretos vs ConfigMaps:** Para certificados privados, usar Secrets en lugar de ConfigMaps
5. **Monitoreo:** Alertas cuando certificados están próximos a expirar

### 8. **Alternativas para Producción**

En lugar de usar `customCaCerts` en producción:

**Opción A: Let's Encrypt + cert-manager**
```yaml
ingresses:
  - enabled: true
    tls:
      enabled: true
      secretName: edc-tls  # cert-manager lo gestiona automáticamente
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
```

**Opción B: Certificados Comerciales**
```bash
kubectl create secret tls edc-tls \
  --cert=cert.crt \
  --key=cert.key \
  -n namespace
```

**Opción C: PKI Corporativa**
- Distribuir el certificado CA corporativo mediante ConfigMap global
- Usar un DaemonSet para inyectarlo en todos los nodos
- Los pods confiarán automáticamente
