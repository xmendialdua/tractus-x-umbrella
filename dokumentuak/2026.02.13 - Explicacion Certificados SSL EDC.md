## Conceptos Fundamentales

### 1. Certificado Público vs Clave Privada

#### Certificado Público (Public Certificate)

Es el archivo que contiene:
- Información sobre el propietario (Common Name, Organization, etc.)
- Clave pública
- Firma digital de la Certificate Authority (CA) que lo emitió
- Período de validez

**Formato típico:**
```
-----BEGIN CERTIFICATE-----
MIIDZjCCAk6gAwIBAgIQQ1Ar6jsciDa8xi9p5lJI5jAN...
-----END CERTIFICATE-----
```

**Características:**
- ✅ Se puede compartir públicamente
- ✅ Se distribuye a todos los que necesiten verificar tu identidad
- ✅ Va en el `customCaCerts` para que otros confíen en ti
- ❌ NO es secreto

#### Clave Privada (Private Key)

Es el archivo secreto que:
- Corresponde matemáticamente a la clave pública del certificado
- Se usa para firmar y descifrar
- NUNCA debe compartirse

**Formato típico:**
```
-----BEGIN PRIVATE KEY-----
MIIEvQIBADANBgkqhkiG9w0BAQEFAASCBKcwggSjAgEA...
-----END PRIVATE KEY-----
```

**Características:**
- ❌ NUNCA se comparte
- ❌ NUNCA va en `customCaCerts`
- ✅ Se almacena en Secrets de Kubernetes (ej: `edc-ikln-control-tls`)
- ✅ Solo la necesita el servidor para sus propios endpoints

### 2. Certificate Authority (CA)

Una **CA (Certificate Authority)** es una entidad que:
- Emite certificados digitales
- Firma certificados con su clave privada
- Proporciona su certificado público para que otros lo confíen

**Tipos de CA:**

| Tipo | Ejemplo | Usado en |
|------|---------|----------|
| **CA Pública Comercial** | DigiCert, GlobalSign, Let's Encrypt | Internet público, producción |
| **CA Interna/Corporativa** | cert-manager con CA autofirmada | Desarrollo, redes internas |
| **CA Root** | Incluidas en SO y navegadores | Validación de cadenas de certificados |

### 3. Truststore de Java

El **truststore** es un almacén de certificados CA en el que Java confía.

**Ubicación por defecto:**
```
$JAVA_HOME/lib/security/cacerts
```

**Función:**
Cuando un cliente Java (EDC connector) se conecta por HTTPS a un servidor:
1. El servidor presenta su certificado
2. Java busca en el truststore si tiene la CA que firmó ese certificado
3. Si encuentra la CA → ✅ Confía y establece conexión
4. Si NO encuentra la CA → ❌ Error: `unable to find valid certification path`

**Password por defecto:** `changeit`

**Comandos útiles:**
```bash
# Listar certificados en el truststore
keytool -list -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit

# Ver detalles de un certificado específico
keytool -list -v -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit -alias my-ca

# Importar un certificado
keytool -import -noprompt -trustcacerts -alias my-ca \
  -file ca.crt -keystore cacerts -storepass changeit
```

### Componentes y sus Certificados

```
┌─────────────────────────────────────────────────────┐
│           CONECTOR EDC (IKLN)                       │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. CERTIFICADOS PROPIOS (Kubernetes Secrets)      │
│     ┌─────────────────────────────────────────┐   │
│     │ Secret: edc-ikln-control-tls            │   │
│     │  - tls.crt (certificado público propio) │   │
│     │  - tls.key (clave privada - SECRETO)    │   │
│     └─────────────────────────────────────────┘   │
│                                                     │
│     ┌─────────────────────────────────────────┐   │
│     │ Secret: edc-ikln-data-tls               │   │
│     │  - tls.crt (certificado público propio) │   │
│     │  - tls.key (clave privada - SECRETO)    │   │
│     └─────────────────────────────────────────┘   │
│                                                     │
│  2. TRUSTSTORE (Certificados CA de OTROS)          │
│     ┌─────────────────────────────────────────┐   │
│     │ customCaCerts (en values.yaml)          │   │
│     │  - mass-ca.crt     (CA de MASS)         │   │
│     │  - partner2-ca.crt (CA de Partner 2)    │   │
│     │  - partner3-ca.crt (CA de Partner 3)    │   │
│     └─────────────────────────────────────────┘   │
│           ↓                                         │
│     ┌─────────────────────────────────────────┐   │
│     │ /opt/java/openjdk/lib/security/cacerts │   │
│     │ (Truststore Java en runtime)            │   │
│     └─────────────────────────────────────────┘   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### Flujo de Uso de Certificados

**Cuando IKLN actúa como SERVIDOR (recibe peticiones):**
```
Cliente → HTTPS → IKLN Ingress
                    ↓
          Presenta: edc-ikln-control-tls
                    ↓
          Cliente verifica con su truststore
```

**Cuando IKLN actúa como CLIENTE (hace peticiones):**
```
IKLN → HTTPS → MASS Ingress
  ↓
Usa: Truststore Java (/opt/java/.../cacerts)
  ↓
Verifica certificado de MASS con CAs en customCaCerts
```

## Funcionamiento de customCaCerts

### Parámetro en values.yaml

```yaml
tractusx-connector:
  customCaCerts:
    nombre-archivo.crt: |
      -----BEGIN CERTIFICATE-----
      [contenido del certificado]
      -----END CERTIFICATE-----
```

### Proceso Automático del Chart

#### 1. Creación de ConfigMap

El template `configmap-customcacerts.yaml` crea automáticamente:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ikln-edc-custom-cacerts
  namespace: umbrella
data:
  nombre-archivo.crt: |
    -----BEGIN CERTIFICATE-----
    [contenido del certificado]
    -----END CERTIFICATE-----
```

#### 2. InitContainer Automático

El chart genera un initContainer que:

```yaml
initContainers:
  - name: custom-cacerts
    image: tractusx/edc-controlplane-postgresql-hashicorp-vault:0.11.1
    command:
      - /bin/sh
      - -c
      - |
        # Copiar truststore Java por defecto
        cp /opt/java/openjdk/lib/security/cacerts /workdir/
        
        # Buscar todos los archivos .crt o .pem
        find /cacerts -type f \( -iname \*.crt -o -iname \*.pem \) -exec echo "{}" \; | while read PEM_FILE_PATH; do
          PEM_FILE=${PEM_FILE_PATH##*/}
          ALIAS=${PEM_FILE%.*}
          echo "adding ${PEM_FILE} with alias ${ALIAS} to cacerts ..."
          keytool -import -noprompt -trustcacerts -alias ${ALIAS} \
            -file ${PEM_FILE_PATH} -keystore /workdir/cacerts -storepass changeit
        done
    volumeMounts:
      - name: custom-cacertificates
        mountPath: /cacerts
      - name: custom-cacerts
        mountPath: /workdir
```

**Lo que hace:**
1. Copia el truststore Java con todos los certificados CA públicos conocidos
2. Itera sobre TODOS los archivos `.crt` o `.pem` del ConfigMap
3. Para cada archivo:
   - Extrae el nombre (sin extensión) como alias
   - Importa el certificado al truststore con ese alias
4. Guarda el truststore modificado en un volumen compartido

#### 3. Montaje en Contenedor Principal

```yaml
containers:
  - name: edc-controlplane
    volumeMounts:
      - name: custom-cacerts
        mountPath: /opt/java/openjdk/lib/security/cacerts
        subPath: cacerts
```

El truststore modificado se monta **reemplazando** el truststore por defecto.

### Extensiones Soportadas

El initContainer busca específicamente:
- ✅ `.crt` - Recomendado
- ✅ `.pem` - También funciona
- ❌ `.cert` - NO funciona
- ❌ `.cer` - NO funciona

**Usa siempre `.crt` o `.pem`.**

## Escenarios de Despliegue

### Escenario 1: Mismo Cluster, Mismo cert-manager

**Arquitectura:**
```
┌──────────────────────────────────────────────┐
│          Cluster Kubernetes (OVH)            │
│                                              │
│  ┌────────────────────────────────────────┐ │
│  │  cert-manager (namespace: umbrella)    │ │
│  │  CA Root: my-selfsigned-ca             │ │
│  └────────────────────────────────────────┘ │
│            │ firma                 │ firma   │
│            ↓                       ↓         │
│  ┌─────────────────┐    ┌─────────────────┐ │
│  │ IKLN Connector  │    │ MASS Connector  │ │
│  │ (namespace:     │    │ (namespace:     │ │
│  │  umbrella)      │    │  umbrella)      │ │
│  │                 │    │                 │ │
│  │ Certificados:   │    │ Certificados:   │ │
│  │ - edc-ikln-*    │    │ - edc-mass-*    │ │
│  │   (firmados por │    │   (firmados por │ │
│  │    my-selfsigned│    │    my-selfsigned│ │
│  │    -ca)         │    │    -ca)         │ │
│  └─────────────────┘    └─────────────────┘ │
│                                              │
└──────────────────────────────────────────────┘
```

**Configuración:**

Ambos conectores usan el **mismo certificado CA** en `customCaCerts`:

```yaml
# values-ikln-connector.yaml
tractusx-connector:
  customCaCerts:
    ovh-internal-ca.crt: |
      -----BEGIN CERTIFICATE-----
      [Certificado de my-selfsigned-ca]
      -----END CERTIFICATE-----
```

```yaml
# values-mass-connector.yaml
tractusx-connector:
  customCaCerts:
    ovh-internal-ca.crt: |
      -----BEGIN CERTIFICATE-----
      [Certificado de my-selfsigned-ca]
      -----END CERTIFICATE-----
```

**Por qué funciona:**
- Ambos certificados de endpoints están firmados por la misma CA
- Ambos conectores confían en esa CA
- IKLN → verifica certificado de MASS ✅
- MASS → verifica certificado de IKLN ✅

**Comando para exportar el certificado CA:**
```bash
kubectl get secret root-secret -n umbrella \
  -o jsonpath='{.data.ca\.crt}' | base64 -d
```

### Escenario 2: Clusters Distribuidos, CAs Diferentes

**Arquitectura:**
```
┌────────────────────────────┐    ┌────────────────────────────┐
│   Cloud A (AWS)            │    │   Cloud B (OVH)            │
│                            │    │                            │
│  ┌──────────────────────┐ │    │  ┌──────────────────────┐ │
│  │ cert-manager A       │ │    │  │ cert-manager B       │ │
│  │ CA Root: CA-A        │ │    │  │ CA Root: CA-B        │ │
│  └──────────────────────┘ │    │  └──────────────────────┘ │
│           │ firma          │    │           │ firma          │
│           ↓                │    │           ↓                │
│  ┌──────────────────────┐ │    │  ┌──────────────────────┐ │
│  │ IKLN Connector       │ │    │  │ MASS Connector       │ │
│  │                      │ │    │  │                      │ │
│  │ Certificados IKLN    │ │    │  │ Certificados MASS    │ │
│  │ firmados por CA-A    │ │    │  │ firmados por CA-B    │ │
│  └──────────────────────┘ │    │  └──────────────────────┘ │
│                            │    │                            │
└────────────────────────────┘    └────────────────────────────┘
         ↕ HTTPS                            ↕ HTTPS
         └────────────────────────────────────┘
```

**Configuración:**

❌ **INCORRECTO (lo que NO debes hacer):**
```yaml
# values-ikln-connector.yaml
tractusx-connector:
  customCaCerts:
    ikln-ca.crt: |  # ❌ Tu propia CA - NO sirve
      -----BEGIN CERTIFICATE-----
      [Certificado de CA-A]
      -----END CERTIFICATE-----
```

✅ **CORRECTO:**
```yaml
# values-ikln-connector.yaml (desplegado en Cloud A)
tractusx-connector:
  customCaCerts:
    mass-ca.crt: |  # ✅ CA del partner (Cloud B)
      -----BEGIN CERTIFICATE-----
      [Certificado de CA-B]
      -----END CERTIFICATE-----
```

```yaml
# values-mass-connector.yaml (desplegado en Cloud B)
tractusx-connector:
  customCaCerts:
    ikln-ca.crt: |  # ✅ CA del partner (Cloud A)
      -----BEGIN CERTIFICATE-----
      [Certificado de CA-A]
      -----END CERTIFICATE-----
```

**Explicación del flujo:**

**Cuando IKLN se conecta a MASS:**
1. IKLN (cliente) → HTTPS → MASS (servidor)
2. MASS presenta su certificado (firmado por CA-B)
3. IKLN busca CA-B en su truststore
4. IKLN encuentra CA-B (porque está en `customCaCerts`) ✅
5. IKLN confía en el certificado de MASS
6. Conexión establecida

**Cuando MASS se conecta a IKLN:**
1. MASS (cliente) → HTTPS → IKLN (servidor)
2. IKLN presenta su certificado (firmado por CA-A)
3. MASS busca CA-A en su truststore
4. MASS encuentra CA-A (porque está en `customCaCerts`) ✅
5. MASS confía en el certificado de IKLN
6. Conexión establecida

### Escenario Real: IKLN conectándose a 4 partners

**Topología:**
```
                    ┌─────────────────┐
                    │  IKLN Connector │
                    │   (Cloud OVH)   │
                    └────────┬────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
            ↓                ↓                ↓
    ┌───────────────┐  ┌───────────────┐  ┌───────────────┐
```

```yaml
      MIIDZjCCAk6gAwIBAgIQQ1Ar6jsciDa8xi9p5lJI5jAN...

    # CA de BOSCH en Azure
    bosch-azure-ca.crt: |
      -----BEGIN CERTIFICATE-----
      MIIDXTCCAkWgAwIBAgIJAKL3lk2nQx... (certificado de CA de BOSCH)

    siemens-aws-ca.crt: |
      -----BEGIN CERTIFICATE-----
      MIIEkjCCA3qgAwIBAgIQCgFBQgA... (certificado de CA de SIEMENS)
      -----END CERTIFICATE-----
    
    # CA de BMW en Google Cloud
```

## Flujo TLS Cliente-Servidor

### Handshake TLS Completo

```
CLIENTE (IKLN)                    SERVIDOR (MASS)
    │                                    │
    │  1. ClientHello                    │
    │───────────────────────────────────>│
    │  - Versiones TLS soportadas        │
    │  - Cipher suites                   │
    │                                    │
    │  2. ServerHello                    │
    │<───────────────────────────────────│
    │  - Versión TLS seleccionada        │
    │  - Cipher suite seleccionado       │
    │                                    │
    │  3. Server Certificate             │
    │<───────────────────────────────────│
    │  - Certificado de MASS             │
    │    (firmado por CA-B)              │
    │                                    │
    │  4. VERIFICACIÓN en CLIENTE        │
    │  ┌────────────────────────────┐   │
    │  │ a) Extraer firma del cert  │   │
    │  │ b) Buscar CA-B en truststore│  │
    │  │ c) Verificar firma con CA-B│   │
    │  │ d) ✅ Si válido → continuar│   │
    │  │    ❌ Si no → abortar       │   │
    │  └────────────────────────────┘   │
    │                                    │
    │  5. ClientKeyExchange              │
    │───────────────────────────────────>│
    │  - Clave sesión cifrada            │
    │                                    │
    │  6. ChangeCipherSpec               │
    │<──────────────────────────────────>│
    │                                    │
    │  7. Finished                       │
    │<──────────────────────────────────>│
    │                                    │
    │  8. Comunicación cifrada           │
    │<══════════════════════════════════>│
```

### Puntos Críticos

**Paso 4: Verificación del Certificado**

Este es donde `customCaCerts` entra en juego:

```java
// Pseudocódigo de lo que hace Java internamente

Certificate serverCert = receivedFromServer();
String issuerDN = serverCert.getIssuerDN();

// Buscar CA que firmó el certificado
for (Certificate trustedCA : truststore.getCertificates()) {
    if (trustedCA.getSubjectDN().equals(issuerDN)) {
        // Verificar firma
        if (serverCert.verify(trustedCA.getPublicKey())) {
            return VALID; // ✅ Conectar
        }
    }
}

throw new CertPathBuilderException("unable to find valid certification path");
// ❌ Error que vimos antes
```

**Si CA-B NO está en el truststore:**
```
❌ Error: org.eclipse.edc.http.spi.EdcHttpClientException: 
PKIX path building failed: unable to find valid certification path to requested target
```

**Si CA-B SÍ está en el truststore:**
```
✅ Conexión establecida
✅ Catalog query exitoso
✅ Transferencia de datos posible
```

## Ejemplos Prácticos

### Ejemplo 1: Obtener Certificado CA de un Partner

**Opción A: El partner te lo envía**

El partner ejecuta en su cluster:
```bash
# Exportar certificado CA raíz
kubectl get secret root-secret -n namespace-partner \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > partner-ca.crt

# Enviar partner-ca.crt por email o método seguro
```

**Opción B: Descargarlo del endpoint HTTPS**

```bash
# Obtener cadena de certificados del servidor
openssl s_client -showcerts -connect edc-partner-control.ejemplo.com:443 </dev/null 2>/dev/null | \
  openssl x509 -outform PEM > partner-endpoint.crt

# IMPORTANTE: Esto te da el certificado del endpoint, NO el CA root
# Necesitas extraer el CA root de la cadena:
openssl s_client -showcerts -connect edc-partner-control.ejemplo.com:443 </dev/null 2>/dev/null | \
  sed -n '/BEGIN CERTIFICATE/,/END CERTIFICATE/p' | \
  tail -n +$(echo "$(openssl s_client -showcerts -connect edc-partner-control.ejemplo.com:443 </dev/null 2>/dev/null | grep -n 'BEGIN CERTIFICATE' | tail -1 | cut -d: -f1)") | \
  head -n 100 > partner-ca.crt
```

**Opción C: Usar cert-manager (si aplica)**

```bash
# Si el partner usa cert-manager
kubectl get certificate -n namespace-partner
kubectl get secret partner-ca-secret -n namespace-partner \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > partner-ca.crt
```

### Ejemplo 3: Migrar de Autofirmado a Let's Encrypt

**Situación inicial:**
- Certificados autofirmados con cert-manager
- CA interna en `customCaCerts`

**Objetivo:**
- Usar Let's Encrypt para certificados válidos públicamente
- Eliminar necesidad de `customCaCerts` entre partners

**Pasos:**

1. **Instalar cert-manager con Let's Encrypt:**
```bash
# Ya tienes cert-manager, solo agregar ClusterIssuer

cat <<EOF | kubectl apply -f -
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@tu-empresa.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
    - http01:
        ingress:
          class: nginx
EOF
```

2. **Actualizar ingress para usar Let's Encrypt:**
```yaml
# values-ikln-connector.yaml
tractusx-connector:
  controlplane:
    ingresses:
      - enabled: true
        hostname: "edc-ikln-control.tu-dominio-real.com"
        annotations:
          cert-manager.io/cluster-issuer: "letsencrypt-prod"
        tls:
          enabled: true
          secretName: "edc-ikln-control-tls"
```

3. **Eliminar customCaCerts (ya no necesario):**
```yaml
# values-ikln-connector.yaml
tractusx-connector:
  # customCaCerts: {}  # ← Eliminar o dejar vacío
```

**Por qué funciona:**
- Let's Encrypt es una CA pública reconocida
- Todos los truststores de Java ya incluyen Let's Encrypt por defecto
- No necesitas distribuir certificados CA manualmente

## Preguntas Frecuentes

### ❓ ¿Necesito incluir mi propio certificado CA en customCaCerts?

**Respuesta: NO.**

Tu propio certificado CA no necesita estar en tu truststore porque:
- Tu truststore es para verificar certificados de OTROS
- Tu certificado propio está en el Secret de Kubernetes (ej: `edc-ikln-control-tls`)
- Ese Secret se monta en el Ingress, no en el truststore

**Analogía:**
Es como tu carnet de identidad:
- No necesitas guardarlo en tu lista de contactos
- Lo usas para identificarte TÚ
- La lista de contactos (truststore) es para identificar a OTROS

### ❓ ¿Qué pasa si olvido añadir la CA de un partner?

**Error que verás:**
```json
{
  "message": "org.eclipse.edc.http.spi.EdcHttpClientException: PKIX path building failed: unable to find valid certification path to requested target",
  "type": "BadGateway"
}
```

**Solución:**
1. Obtener certificado CA del partner
2. Añadirlo a `customCaCerts`
3. Redesplegar el conector

### ❓ ¿Puedo usar el mismo nombre de archivo para diferentes CAs?

**NO.** Cada archivo debe tener un nombre único:

❌ **Incorrecto:**
```yaml
customCaCerts:
  ca.crt: |
    [CA de MASS]
  ca.crt: |  # ❌ Duplicado, YAML solo tomará el último
    [CA de BOSCH]
```

✅ **Correcto:**
```yaml
customCaCerts:
  mass-ca.crt: |
    [CA de MASS]
  bosch-ca.crt: |
    [CA de BOSCH]
```

### ❓ ¿Los certificados en customCaCerts tienen fecha de expiración?

**SÍ.** Los certificados CA también expiran.

**Consecuencias:**
- Si la CA expira, todos los certificados firmados por ella son inválidos
- Necesitas actualizar el certificado CA en `customCaCerts` cuando se renueve

**Verificar expiración:**
```bash
# Extraer certificado del values.yaml y verificar
echo "-----BEGIN CERTIFICATE-----
[contenido]
-----END CERTIFICATE-----" | openssl x509 -text -noout | grep "Not After"
```

**Salida:**
```
Not After : May 14 11:18:13 2026 GMT
```

**Renovación:**
Cuando el partner renueve su CA root, te enviará el nuevo certificado y necesitarás actualizar `customCaCerts` y redesplegar.

### ❓ ¿Puedo tener certificados de Let's Encrypt Y customCaCerts al mismo tiempo?

**SÍ, es perfectamente válido.**

**Caso de uso:**
- Tus propios endpoints usan Let's Encrypt (públicamente válidos)
- Pero te conectas a partners que usan CAs internas

```yaml
# values-ikln-connector.yaml
tractusx-connector:
  # Mis endpoints con Let's Encrypt
  controlplane:
    ingresses:
      - enabled: true
        hostname: "edc-ikln-control.mi-empresa.com"
        annotations:
          cert-manager.io/cluster-issuer: "letsencrypt-prod"
        tls:
          enabled: true
          secretName: "edc-ikln-control-tls"
  
  # Pero confío en CAs internas de partners
  customCaCerts:
    partner1-internal-ca.crt: |
      -----BEGIN CERTIFICATE-----
      [CA interna de partner]
      -----END CERTIFICATE-----
```

### ❓ ¿Qué pasa con los certificados CA públicos ya incluidos en Java?

**Se mantienen.** El initContainer:
1. Copia el truststore por defecto (con ~100 CAs públicas)
2. **AÑADE** tus CAs personalizadas
3. No elimina nada

**Por tanto:**
- ✅ Sigues confiando en Let's Encrypt
- ✅ Sigues confiando en DigiCert, GlobalSign, etc.
- ✅ Ahora TAMBIÉN confías en tus CAs custom

## Troubleshooting

### Problema: Certificado no se importa al truststore

**Síntomas:**
```bash
kubectl exec -n umbrella pod-name -- \
  keytool -list -keystore /opt/java/openjdk/lib/security/cacerts -storepass changeit -alias my-ca
# keytool error: java.lang.Exception: Alias <my-ca> does not exist
```

**Causas posibles:**

1. **Extensión incorrecta:**
```yaml
# ❌ Incorrecto
customCaCerts:
  my-ca.cert: |  # .cert no es reconocido
    [certificado]
```

**Solución:** Usar `.crt` o `.pem`

2. **Formato de certificado incorrecto:**
```yaml
# ❌ Falta pipe | y salto de línea
customCaCerts:
  my-ca.crt: -----BEGIN CERTIFICATE-----...
```

**Solución:**
```yaml
# ✅ Correcto
customCaCerts:
  my-ca.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

3. **InitContainer falló:**
```bash
# Ver logs del initContainer
kubectl logs -n umbrella pod-name -c custom-cacerts
```

### Problema: Certificado expira pronto

**Verificar expiración de certificados en truststore:**

```bash
POD_NAME=$(kubectl get pods -n umbrella -l app.kubernetes.io/instance=ikln-edc,app.kubernetes.io/component=controlplane -o jsonpath='{.items[0].metadata.name}')

# Listar todos los custom CA con detalles
kubectl exec -n umbrella $POD_NAME -- \
  keytool -list -v -keystore /opt/java/openjdk/lib/security/cacerts -storepass changeit | \
  grep -A 10 "Alias name: tractus-x-ca"
```

**Buscar:**
```
Valid from: Thu Feb 13 11:18:13 UTC 2026 until: Wed May 14 11:18:13 UTC 2026
```

**Acción preventiva:**
- Configurar alertas 30 días antes de expiración
- Obtener nuevo certificado CA del partner
- Actualizar `customCaCerts` y redesplegar

### Problema: Error de certificado pero customCaCerts está configurado

**Debugging paso a paso:**

1. **Verificar que el ConfigMap se creó:**
```bash
kubectl get configmap -n umbrella | grep custom-cacerts
# Debe mostrar: ikln-edc-custom-cacerts
```

2. **Ver contenido del ConfigMap:**
```bash
kubectl get configmap ikln-edc-custom-cacerts -n umbrella -o yaml
```

3. **Verificar que el initContainer se ejecutó:**
```bash
kubectl logs -n umbrella $POD_NAME -c custom-cacerts
```

**Salida esperada:**
```
adding tractus-x-ca.crt with alias tractus-x-ca to cacerts ...
Certificate was added to keystore
```

4. **Verificar que el volumen se montó:**
```bash
kubectl describe pod -n umbrella $POD_NAME | grep -A 20 "Volumes:"
```

**Debe mostrar:**
```
  custom-cacerts:
    Type:       EmptyDir (a temporary directory that shares a pod's lifetime)
  custom-cacertificates:
    Type:      ConfigMap (a volume populated by a ConfigMap)
    Name:      ikln-edc-custom-cacerts
```

5. **Verificar el certificado en el truststore:**
```bash
kubectl exec -n umbrella $POD_NAME -- \
  keytool -list -keystore /opt/java/openjdk/lib/security/cacerts -storepass changeit | \
  grep "tractus-x-ca"
```

6. **Obtener detalles completos del certificado:**
```bash
kubectl exec -n umbrella $POD_NAME -- \
  keytool -list -v -keystore /opt/java/openjdk/lib/security/cacerts -storepass changeit -alias tractus-x-ca
```

**Verificar que el Subject/Issuer coincide con el certificado del partner.**

### Problema: Certificado correcto pero sigue fallando

**Causa posible:** El certificado del partner cambió pero el CA es el mismo.

**Escenario:**
- Partner renovó su certificado de endpoint
- El nuevo certificado está firmado por la misma CA
- Pero tu customCaCerts tiene una versión antigua de la CA

**Solución:**
Solicitar al partner el certificado CA actualizado y actualizar `customCaCerts`.

## Resumen de Mejores Prácticas

### ✅ DO (Hacer)

1. **Usa nombres descriptivos para archivos:**
   ```yaml
   customCaCerts:
     partner-company-environment-ca.crt: |
   ```

2. **Documenta la procedencia de cada CA:**
   ```yaml
   customCaCerts:
     # CA de MASS Connector en OVH (obtenida el 2026-02-13)
     # Expira: 2026-05-14
     # Contacto: admin@mass.com
     mass-ovh-ca.crt: |
   ```

3. **Verifica antes de desplegar:**
   ```bash
   # Validar que es un certificado válido
   openssl x509 -in ca.crt -text -noout
   ```

4. **Mantén un registro de expiraciones:**
   Crea un documento o hoja de cálculo con:
   - Nombre del partner
   - Fecha de expiración de su CA
   - Contacto para renovación

5. **Usa extensión .crt o .pem:**
   ```yaml
   ✅ tractus-x-ca.crt
   ✅ partner-ca.pem
   ❌ partner-ca.cert
   ```

### ❌ DON'T (No hacer)

1. **No incluyas tu propio certificado CA si estás en mismo cluster:**
   Si todos usan la misma CA, un solo certificado es suficiente.

2. **No uses claves privadas en customCaCerts:**
   ```yaml
   ❌ customCaCerts:
        my-private-key.key: |  # ¡NUNCA!
          -----BEGIN PRIVATE KEY-----
   ```

3. **No uses nombres duplicados:**
   ```yaml
   ❌ customCaCerts:
        ca.crt: |
          [CA 1]
        ca.crt: |  # Duplicado - solo se usa el último
          [CA 2]
   ```

4. **No confíes en CAs no verificadas:**
   Siempre obtén el certificado directamente del partner por canal seguro.

5. **No olvides actualizar cuando expire:**
   Los certificados CA pueden expirar. Planifica renovaciones.
