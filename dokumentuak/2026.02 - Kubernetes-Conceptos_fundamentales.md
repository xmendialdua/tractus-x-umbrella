## Introducción

Kubernetes (K8s) es una plataforma de código abierto para automatizar el despliegue, escalado y gestión de aplicaciones en contenedores. Organiza los contenedores en unidades lógicas para facilitar su gestión y descubrimiento.

---

## Arquitectura Básica

### Componentes del Control Plane
- **API Server**: Punto de entrada para todas las operaciones REST
- **etcd**: Almacén de datos distribuido para el estado del cluster
- **Scheduler**: Asigna pods a nodos según recursos disponibles
- **Controller Manager**: Ejecuta controladores (Deployment, ReplicaSet, etc.)

### Componentes de los Nodos
- **kubelet**: Agente que ejecuta en cada nodo y gestiona los pods
- **kube-proxy**: Gestiona las reglas de red en cada nodo
- **Container Runtime**: Motor de contenedores (Docker, containerd, CRI-O)

## Conceptos Fundamentales

### 1. **Pod**

**Definición**: Es la unidad más pequeña y básica de despliegue en Kubernetes. Un Pod representa uno o más contenedores que comparten almacenamiento y red.

**Características**:
- Comparten dirección IP y puerto
- Comparten volúmenes
- Se despliegan juntos en el mismo nodo
- Son efímeros por naturaleza

**Ejemplo**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mi-aplicacion
  labels:
    app: backend
spec:
  containers:
  - name: app-container
    image: nginx:1.21
    ports:
    - containerPort: 80
    env:
    - name: ENV_VAR
      value: "production"
```

### 2. **ReplicaSet**

**Definición**: Garantiza que un número específico de réplicas de un Pod estén ejecutándose en todo momento.

**Características**:
- Mantiene la disponibilidad de los Pods
- Escala automáticamente según configuración
- Rara vez se usa directamente (se usa Deployment)

**Ejemplo**:
```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: mi-replicaset
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: app
        image: mi-app:1.0
```

### 3. **Deployment**

**Definición**: Proporciona actualizaciones declarativas para Pods y ReplicaSets. Es el recurso más común para desplegar aplicaciones stateless.

**Características**:
- Gestiona ReplicaSets automáticamente
- Permite rolling updates y rollbacks
- Estrategias de despliegue (RollingUpdate, Recreate)
- Control de versiones

**Ejemplo**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mi-deployment
  labels:
    app: frontend
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: web
        image: nginx:1.21
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
          limits:
            memory: "128Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /health
            port: 80
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5
```

### 4. **Service (svc)**

**Definición**: Abstracción que define un conjunto lógico de Pods y una política para acceder a ellos. Proporciona un endpoint estable (IP y DNS).

**Tipos**:

#### ClusterIP (por defecto)
Expone el servicio en una IP interna del cluster.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-servicio-interno
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
```

#### NodePort
Expone el servicio en cada IP del nodo en un puerto estático.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-servicio-nodeport
spec:
  type: NodePort
  selector:
    app: backend
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
    nodePort: 30080  # Puerto entre 30000-32767
```

#### LoadBalancer
Expone el servicio externamente usando un balanceador de carga del proveedor cloud.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-servicio-lb
spec:
  type: LoadBalancer
  selector:
    app: frontend
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
```

#### Headless Service
Para acceso directo a los Pods (sin balanceo de carga).
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-servicio-headless
spec:
  clusterIP: None
  selector:
    app: database
  ports:
  - protocol: TCP
    port: 5432
```

### 5. **Ingress**

**Definición**: Gestiona el acceso externo a servicios HTTP/HTTPS en el cluster. Proporciona balanceo de carga, terminación SSL y virtual hosting basado en nombres.

**Características**:
- Enrutamiento basado en rutas y hosts
- Terminación TLS/SSL
- Requiere un Ingress Controller (nginx, traefik, etc.)

**Ejemplo**:
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mi-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls-secret
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: backend-service
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
```

### 6. **ConfigMap**

**Definición**: Almacena datos de configuración no confidenciales en pares clave-valor. Permite desacoplar la configuración del código de la aplicación.

**Usos**:
- Variables de entorno
- Archivos de configuración
- Arguments de línea de comandos

**Ejemplo**:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  # Propiedades simples
  database.host: "postgres.default.svc.cluster.local"
  database.port: "5432"
  log.level: "INFO"
  
  # Archivo de configuración completo
  app.properties: |
    server.port=8080
    server.host=0.0.0.0
    spring.datasource.url=jdbc:postgresql://postgres:5432/mydb
    spring.datasource.username=admin
```

**Uso en Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mi-pod
spec:
  containers:
  - name: app
    image: mi-app:1.0
    # Como variables de entorno
    env:
    - name: DB_HOST
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: database.host
    # Como volumen
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
  volumes:
  - name: config-volume
    configMap:
      name: app-config
```

### 7. **Secret**

**Definición**: Similar a ConfigMap pero diseñado para almacenar información confidencial (contraseñas, tokens, claves SSH).

**Tipos**:
- `Opaque`: Datos arbitrarios (por defecto)
- `kubernetes.io/tls`: Certificados TLS
- `kubernetes.io/dockerconfigjson`: Credenciales de registro Docker
- `kubernetes.io/basic-auth`: Credenciales básicas

**Ejemplo**:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  # Valores en base64
  username: YWRtaW4=      # admin
  password: cGFzc3dvcmQ=  # password
stringData:
  # Valores en texto plano (se codifican automáticamente)
  connection-string: "postgresql://admin:password@postgres:5432/mydb"
```

**Uso en Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mi-pod
spec:
  containers:
  - name: app
    image: mi-app:1.0
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: password
```

### 8. **PersistentVolume (PV)**

**Definición**: Representa un recurso de almacenamiento en el cluster, aprovisionado por un administrador o dinámicamente usando Storage Classes.

**Ejemplo**:
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-data
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  hostPath:
    path: /mnt/data
```

### 9. **PersistentVolumeClaim (PVC)**

**Definición**: Solicitud de almacenamiento por parte de un usuario. Se vincula a un PV que satisfaga los requisitos.

**Access Modes**:
- `ReadWriteOnce` (RWO): Montable como lectura-escritura por un solo nodo
- `ReadOnlyMany` (ROX): Montable como solo-lectura por múltiples nodos
- `ReadWriteMany` (RWX): Montable como lectura-escritura por múltiples nodos

**Ejemplo**:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
```

**Uso en Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-con-storage
spec:
  containers:
  - name: app
    image: postgres:14
    volumeMounts:
    - name: data-volume
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: data-volume
    persistentVolumeClaim:
      claimName: data-pvc
```

### 10. **StatefulSet**

**Definición**: Gestiona el despliegue y escalado de un conjunto de Pods con identidades únicas y persistentes. Ideal para aplicaciones stateful (bases de datos, sistemas de mensajería).

**Características**:
- Identidades de red estables y únicas
- Almacenamiento persistente estable
- Orden de despliegue y escalado controlado
- Orden de actualización controlado

**Ejemplo**:
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres-statefulset
spec:
  serviceName: postgres-headless
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:14
        ports:
        - containerPort: 5432
          name: postgres
        env:
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 10Gi
---
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
  - port: 5432
    name: postgres
```

### 11. **DaemonSet**

**Definición**: Garantiza que todos (o algunos) nodos ejecuten una copia de un Pod. Útil para agentes de monitoreo, logs o networking.

**Casos de uso**:
- Agentes de monitoreo (Prometheus node exporter)
- Recolectores de logs (Fluentd, Filebeat)
- Networking (CNI plugins, kube-proxy)

**Ejemplo**:
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd-daemonset
spec:
  selector:
    matchLabels:
      app: fluentd
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      containers:
      - name: fluentd
        image: fluent/fluentd:v1.14
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
```

### 12. **Job**

**Definición**: Crea uno o más Pods y garantiza que un número específico de ellos termine exitosamente. Para tareas batch o procesamiento único.

**Ejemplo**:
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  template:
    spec:
      containers:
      - name: migrator
        image: migration-tool:1.0
        command: ["python", "migrate.py"]
      restartPolicy: OnFailure
```

### 13. **CronJob**

**Definición**: Ejecuta Jobs en un horario programado (similar a cron de Unix).

**Ejemplo**:
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cronjob
spec:
  schedule: "0 2 * * *"  # Cada día a las 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: backup-tool:1.0
            command: ["/bin/sh", "-c", "backup.sh"]
          restartPolicy: OnFailure
```

### 14. **Namespace**

**Definición**: Proporciona un mecanismo para aislar grupos de recursos dentro de un cluster. Útil para múltiples equipos o proyectos.

**Namespaces por defecto**:
- `default`: namespace por defecto
- `kube-system`: recursos del sistema Kubernetes
- `kube-public`: recursos públicos accesibles por todos
- `kube-node-lease`: objetos de lease para heartbeats de nodos

**Ejemplo**:
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: desarrollo
  labels:
    environment: dev
```

### 15. **ResourceQuota**

**Definición**: Proporciona restricciones que limitan el consumo de recursos agregado por namespace.

**Ejemplo**:
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: desarrollo
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"
```

### 16. **HorizontalPodAutoscaler (HPA)**

**Definición**: Escala automáticamente el número de Pods basándose en métricas (CPU, memoria o métricas personalizadas).

**Ejemplo**:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: mi-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

### 17. **NetworkPolicy**

**Definición**: Define reglas de tráfico de red para Pods. Proporciona control de firewall a nivel de aplicación.

**Ejemplo**:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-netpol
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

### 18. **ServiceAccount**

**Definición**: Proporciona una identidad para los procesos que se ejecutan en un Pod y define qué permisos tiene ese Pod.

**Ejemplo**:
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-serviceaccount
  namespace: default
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
subjects:
- kind: ServiceAccount
  name: app-serviceaccount
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

## Definición de Aplicaciones

### Estructura de un Manifiesto YAML

Todos los recursos de Kubernetes se definen mediante manifiestos YAML con esta estructura básica:

```yaml
apiVersion: <group>/<version>
kind: <ResourceType>
metadata:
  name: <name>
  namespace: <namespace>
  labels:
    key: value
  annotations:
    key: value
spec:
  # Especificación del recurso
```

### Componentes Clave

#### Labels y Selectors
Los labels son pares clave-valor que se adjuntan a objetos. Los selectors permiten filtrar objetos por labels.

```yaml
metadata:
  labels:
    app: mi-app
    tier: frontend
    environment: production
    version: v1.2.0
```

#### Annotations
Metadatos adicionales no identificativos (para herramientas, configuración, etc.).

```yaml
metadata:
  annotations:
    description: "Aplicación principal del frontend"
    prometheus.io/scrape: "true"
    prometheus.io/port: "9090"
```

### Helm Charts

Helm es un gestor de paquetes para Kubernetes que facilita la definición, instalación y actualización de aplicaciones complejas.

**Estructura de un Chart**:
```
my-chart/
  Chart.yaml         # Información sobre el chart
  values.yaml        # Valores de configuración por defecto
  templates/         # Plantillas de manifiestos
    deployment.yaml
    service.yaml
    ingress.yaml
  charts/            # Charts dependientes
```

## Despliegue de Aplicaciones

### 1. Usando kubectl

#### Aplicar manifiestos individuales
```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f ingress.yaml
```

#### Aplicar un directorio completo
```bash
kubectl apply -f ./k8s-manifests/
```

#### Aplicar desde una URL
```bash
kubectl apply -f https://example.com/manifests/app.yaml
```

### 2. Usando Helm

#### Instalar un chart
```bash
helm install mi-release ./my-chart
helm install mi-release ./my-chart -f custom-values.yaml
```

#### Actualizar un release
```bash
helm upgrade mi-release ./my-chart
helm upgrade --install mi-release ./my-chart  # Instala si no existe
```

#### Rollback
```bash
helm rollback mi-release 1  # Volver a la revisión 1
```

### 3. Usando Kustomize

Kustomize permite personalizar manifiestos sin modificar los originales.

```bash
kubectl apply -k ./kustomize/overlays/production/
```

### 4. Verificación del Despliegue

```bash
# Ver todos los recursos
kubectl get all -n <namespace>

# Ver pods
kubectl get pods
kubectl get pods -o wide

# Ver logs
kubectl logs <pod-name>
kubectl logs -f <pod-name>  # Seguir logs en tiempo real
kubectl logs <pod-name> -c <container-name>  # Si hay múltiples contenedores

# Describir recursos
kubectl describe pod <pod-name>
kubectl describe service <service-name>

# Ver eventos
kubectl get events --sort-by='.lastTimestamp'

# Estado del deployment
kubectl rollout status deployment/<deployment-name>
kubectl rollout history deployment/<deployment-name>
```

## Acceso a Aplicaciones

### 1. Acceso Interno (ClusterIP)

Desde dentro del cluster, los servicios son accesibles mediante:

**DNS interno**:
- `<service-name>` (mismo namespace)
- `<service-name>.<namespace>` (diferente namespace)
- `<service-name>.<namespace>.svc.cluster.local` (FQDN completo)

```bash
# Desde un pod en el mismo namespace
curl http://backend-service:8080

# Desde un pod en otro namespace
curl http://backend-service.production:8080
```

### 2. Acceso mediante Port-Forward

Para desarrollo y debugging local:

```bash
# Forward de un pod
kubectl port-forward pod/<pod-name> 8080:80

# Forward de un servicio
kubectl port-forward service/<service-name> 8080:80

# Forward de un deployment
kubectl port-forward deployment/<deployment-name> 8080:80

# Acceso desde localhost
curl http://localhost:8080
```

### 3. Acceso mediante NodePort

Acceso directo a través de la IP del nodo:

```bash
# Obtener NodePort
kubectl get service <service-name>

# Acceso: http://<node-ip>:<node-port>
curl http://192.168.1.100:30080
```

### 4. Acceso mediante LoadBalancer

En clouds públicos (AWS, GCP, Azure):

```bash
# Obtener IP externa
kubectl get service <service-name>

# Acceso: http://<external-ip>
curl http://35.123.45.67
```

### 5. Acceso mediante Ingress

La forma más común para aplicaciones en producción:

```bash
# Verificar ingress
kubectl get ingress

# Acceso mediante nombre de host
curl https://app.example.com/api/users
```

**Configuración de DNS**:
- Apuntar el dominio a la IP del Ingress Controller o LoadBalancer
- Configurar certificados TLS (cert-manager + Let's Encrypt)

### 6. Acceso mediante kubectl proxy

Crea un proxy local al API server:

```bash
kubectl proxy --port=8001

# Acceso a la API
curl http://localhost:8001/api/v1/namespaces/default/services/backend-service/proxy/
```

### 7. Acceso mediante kubectl exec

Para acceso interactivo a un pod:

```bash
# Shell interactivo
kubectl exec -it <pod-name> -- /bin/bash

# Ejecutar un comando
kubectl exec <pod-name> -- curl http://backend-service:8080/health
```

```yaml
apiVersion: v1

  name: webapp
```

```yaml
apiVersion: v1
```

```yaml
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
```

#### 5. ConfigMap para la aplicación
```yaml
apiVersion: v1
kind: ConfigMap
```

## Resumen

Kubernetes proporciona un conjunto robusto de abstracciones para definir, desplegar y gestionar aplicaciones containerizadas:

1. **Pods**: Unidad básica de ejecución
2. **Deployments/StatefulSets**: Gestión de aplicaciones stateless/stateful
3. **Services**: Descubrimiento y balanceo de carga
4. **Ingress**: Acceso HTTP/HTTPS desde el exterior
5. **ConfigMaps/Secrets**: Gestión de configuración
6. **PVC**: Almacenamiento persistente

El flujo típico es:
1. **Definir** aplicación en manifiestos YAML
2. **Desplegar** usando `kubectl apply` o Helm
3. **Acceder** mediante Services e Ingress
4. **Monitorear** y **escalar** según necesidad

Kubernetes abstrae la infraestructura subyacente, permitiendo despliegues consistentes en cualquier entorno (on-premise, cloud, híbrido).

## Kustomize - Gestión de Configuraciones por Entorno

### ¿Qué es Kustomize?

**Kustomize** es una herramienta nativa de Kubernetes (integrada en kubectl desde v1.14) para **personalizar manifiestos YAML sin modificar los archivos originales**. Funciona mediante **capas de overlays** que aplican transformaciones sobre una base común.

### Problema que Resuelve

Imagina que tienes una aplicación que despliegas en 3 entornos: desarrollo, staging y producción.

**Sin Kustomize**, tendrías que:
- ❌ Duplicar todos los manifiestos YAML para cada entorno
- ❌ Gestionar manualmente las diferencias (imágenes, réplicas, recursos, dominios)
- ❌ Copiar y modificar archivos cada vez que cambias algo común
- ❌ Alto riesgo de inconsistencias entre entornos

**Con Kustomize**:
- ✅ Mantienes **una sola base** con la configuración común
- ✅ Creas **overlays** específicos por entorno con solo las diferencias
- ✅ Kustomize combina base + overlay automáticamente
- ✅ Configuración DRY (Don't Repeat Yourself)

### Conceptos Clave

#### 1. Base (Configuración Común)

La base contiene la configuración compartida por todos los entornos.

**Estructura**:
```
base/
├── kustomization.yaml
├── deployment.yaml
├── service.yaml
└── configmap.yaml
```

**base/deployment.yaml**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mi-app
spec:
  replicas: 1  # Valor por defecto
  selector:
    matchLabels:
      app: mi-app
  template:
    metadata:
      labels:
        app: mi-app
    spec:
      containers:
      - name: app
        image: mi-app:latest  # Será sobrescrito en overlays
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
```

**base/service.yaml**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-app
spec:
  selector:
    app: mi-app
  ports:
  - port: 80
    targetPort: 8080
```

**base/kustomization.yaml**:
```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml

commonLabels:
  app: mi-app
  managed-by: kustomize
```

#### 2. Overlays (Personalizaciones por Entorno)

Los overlays contienen las diferencias específicas de cada entorno.

**Estructura**:
```
overlays/
├── dev/
│   ├── kustomization.yaml
│   └── dev-patches.yaml
├── staging/
│   ├── kustomization.yaml

    └── ingress-tls.yaml
```

```yaml

  - ../../base

# Namespace para desarrollo
namespace: development

# Prefijo para nombres
namePrefix: dev-

# Cambiar tag de imagen
images:
  - name: mi-app
    newTag: latest

# ConfigMap específico de dev
configMapGenerator:
  - name: app-config
    literals:
      - ENV=development
      - DEBUG=true
      - LOG_LEVEL=debug
      - API_URL=http://dev-api.internal

# Labels adicionales
commonLabels:
  environment: dev

# Annotations adicionales
commonAnnotations:
  maintainer: "dev-team@company.com"
```

### Transformaciones Principales

#### 1. Cambiar Imágenes de Contenedor

```yaml
images:
  - name: nginx                    # Nombre en manifiestos
    newName: nginx                 # Nuevo nombre (opcional)
    newTag: 1.21.0                 # Nueva versión
  - name: mi-app
    newName: registry.company.com/mi-app
    newTag: v2.0.0
  - name: postgres
    newTag: 14-alpine
```

#### 2. Añadir Prefijos/Sufijos a Nombres

```yaml
# Prefijo para todos los recursos
namePrefix: dev-

# Sufijo para todos los recursos
nameSuffix: -v2

# Resultado: dev-mi-app-v2
```

#### 3. Cambiar Namespace

```yaml
namespace: staging
# Todos los recursos se desplegarán en 'staging'
```

#### 4. Escalar Réplicas

```yaml
replicas:
  - name: frontend-deployment
    count: 5
  - name: backend-deployment
    count: 3
```

#### 5. Labels y Annotations Comunes

```yaml
commonLabels:
  team: backend
  managed-by: kustomize
  environment: production
  cost-center: engineering

commonAnnotations:
  owner: "team@company.com"
  documentation: "https://wiki.company.com/app"
  prometheus.io/scrape: "true"
  prometheus.io/port: "9090"
```

#### 6. Generadores de ConfigMap y Secret

**ConfigMap desde literales**:
```yaml
configMapGenerator:
  - name: app-config
    literals:
      - DATABASE_HOST=postgres.default
      - DATABASE_PORT=5432
      - LOG_LEVEL=info
      - CACHE_TIMEOUT=3600
```

**ConfigMap desde archivos**:
```yaml
configMapGenerator:
  - name: app-config
    files:
      - application.properties
      - config.json
      - nginx.conf
```

**ConfigMap combinado**:
```yaml
configMapGenerator:
  - name: app-config
    files:
      - app.properties
    literals:
      - FEATURE_FLAG=enabled
```

**Secret Generator**:
```yaml
secretGenerator:
  - name: db-credentials
    literals:
      - username=admin
      - password=secretpass123
    type: Opaque
  
  - name: tls-cert
    files:
      - tls.crt
      - tls.key
    type: kubernetes.io/tls
```

**Comportamiento de Generadores**:
```yaml
configMapGenerator:
  - name: app-config
    behavior: create   # Default: crea nuevo (falla si existe)
    # behavior: replace  # Reemplaza existente
    # behavior: merge    # Fusiona con existente
    literals:
      - KEY=value
```

#### 7. Parches (Patches)

**Strategic Merge Patch** (más common, fusiona YAML):
```yaml
patchesStrategicMerge:
  - patch-replicas.yaml
  - patch-resources.yaml
  - patch-env-vars.yaml
```

Ejemplo de patch:
```yaml
# patch-resources.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mi-app
spec:
  template:
    spec:
      containers:
      - name: app
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
```

**JSON Patch (RFC 6902)** - más preciso y quirúrgico:
```yaml
patchesJson6902:
  - target:
      group: apps
      version: v1
      kind: Deployment
      name: mi-app
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 3
      - op: add
        path: /spec/template/spec/containers/0/env/-
        value:
          name: NEW_VAR
          value: "new_value"
      - op: remove
        path: /spec/template/spec/containers/0/env/0
```

**Patch inline**:
```yaml
patches:
  - target:
      kind: Deployment
      name: mi-app
    patch: |-
      - op: add
        path: /spec/template/spec/tolerations
        value:
          - key: "node-role"
            operator: "Equal"
            value: "production"
            effect: "NoSchedule"
```

### Comandos de Kustomize

#### Ver YAML Generado (sin aplicar)

```bash
# Ver resultado para desarrollo
kubectl kustomize overlays/dev/

# Ver resultado para staging
kubectl kustomize overlays/staging/

# Ver resultado para producción
kubectl kustomize overlays/prod/

# Guardar en archivo
kubectl kustomize overlays/prod/ > prod-manifests.yaml
```

#### Aplicar al Cluster

```bash
# Desarrollo
kubectl apply -k overlays/dev/

# Staging
kubectl apply -k overlays/staging/

# Producción
kubectl apply -k overlays/prod/

# Con dry-run para verificar
kubectl apply -k overlays/prod/ --dry-run=client

# Ver diferencias antes de aplicar
kubectl diff -k overlays/prod/
```

#### Eliminar Recursos

```bash
# Eliminar todos los recursos de un overlay
kubectl delete -k overlays/dev/

# Eliminar con confirmación
kubectl delete -k overlays/prod/ --wait=true
```

#### Validar Configuración

```bash
# Validar sintaxis sin aplicar
kubectl kustomize overlays/prod/ | kubectl apply --dry-run=client -f -

# Validar con servidor
kubectl kustomize overlays/prod/ | kubectl apply --dry-run=server -f -
```

### Funciones Avanzadas

#### 1. Componentes Reutilizables

Los componentes son piezas opcionales de configuración:

```
components/
├── monitoring/
│   ├── kustomization.yaml
│   ├── servicemonitor.yaml
│   └── prometheusrule.yaml
└── service-mesh/
    ├── kustomization.yaml
    └── virtualservice.yaml
```

**components/monitoring/kustomization.yaml**:
```yaml
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component

resources:
  - servicemonitor.yaml
  - prometheusrule.yaml

labels:
  - pairs:
      monitoring: enabled
```

**Usar componente en overlay**:
```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

bases:
  - ../../base

components:
  - ../../components/monitoring
  - ../../components/service-mesh
```

#### 2. Generadores Personalizados

```yaml
generators:
  - ./custom-generator.yaml
```

#### 3. Transformadores

```yaml
transformers:
  - ./custom-transformer.yaml
```

#### 4. Configuraciones de Fusión

```yaml
configurations:
  - kustomizeconfig.yaml
```

#### 5. Vars (Variables entre recursos)

```yaml
vars:
  - name: SERVICE_NAME
    objref:
      kind: Service
      name: backend
      apiVersion: v1
    fieldref:
      fieldpath: metadata.name
```

### Ventajas de Kustomize

| Ventaja | Descripción |
|---------|-------------|
| ✅ **Sin Plantillas** | Usa YAML puro de Kubernetes, sin lenguajes de templating |
| ✅ **Nativo** | Integrado en kubectl, no requiere instalación adicional |
| ✅ **Declarativo** | Describe transformaciones, no ejecuta código |
| ✅ **Composable** | Overlays pueden tener overlays (multi-capa) |
| ✅ **Git-friendly** | Fácil de versionar, revisar y auditar |
| ✅ **Reutilizable** | Una base, múltiples entornos |
| ✅ **Sin estado** | No gestiona releases como Helm |
| ✅ **Curva de aprendizaje baja** | Solo YAML, sin sintaxis compleja |

### Kustomize vs Helm

| Característica | Kustomize | Helm |
|----------------|-----------|------|
| **Lenguaje** | YAML puro | Templates Go |
| **Integración kubectl** | ✅ Nativa | ❌ Herramienta separada |
| **Complejidad** | Baja | Media-Alta |
| **Gestión de releases** | ❌ No | ✅ Sí (historial, rollback) |
| **Packages públicos** | ❌ Limitado | ✅ Helm Hub con miles de charts |
| **Hooks de ciclo de vida** | ❌ No | ✅ Pre/post install/upgrade |
| **Dependencias** | Manual | ✅ Gestión automática |
| **Testing** | Manual | ✅ helm test |
| **Secrets management** | Básico | ✅ Más opciones (Vault, etc.) |
| **Mejor para** | Propias apps, multi-entorno | Apps de terceros, distribución |

### Cuándo Usar Cada Uno

**Usa Kustomize cuando**:
- ✅ Gestionas tus propias aplicaciones
- ✅ Necesitas múltiples entornos (dev, staging, prod)
- ✅ Quieres mantener YAML simple y legible
- ✅ Prefieres GitOps puro
- ✅ No necesitas gestión de releases compleja

**Usa Helm cuando**:
- ✅ Instalas aplicaciones de terceros (PostgreSQL, Redis, Nginx)
- ✅ Necesitas gestión de releases con historial
- ✅ Requieres hooks de ciclo de vida
- ✅ Quieres distribuir aplicaciones empaquetadas
- ✅ Necesitas lógica condicional compleja

**Combina ambos**:
```bash
# Instalar chart de Helm con Kustomize
helm template my-release bitnami/postgresql > base/postgres.yaml

# Luego personalizar con Kustomize
kubectl kustomize overlays/prod/ | kubectl apply -f -
```

### Workflow Típico con Kustomize

1. **Crear base con configuración común**:
```bash
mkdir -p base
cd base
# Crear manifiestos base
kubectl create deployment webapp --image=webapp:latest --dry-run=client -o yaml > deployment.yaml
# Crear kustomization.yaml
kustomize create --autodetect
```

2. **Crear overlay para desarrollo**:
```bash
mkdir -p ../overlays/dev
cd ../overlays/dev
kustomize create --namespace dev
# Editar kustomization.yaml para referenciar base
```

3. **Visualizar resultado**:
```bash
kubectl kustomize overlays/dev/
```

4. **Aplicar**:
```bash
kubectl apply -k overlays/dev/
```

5. **Verificar**:
```bash
kubectl get all -n dev
```

6. **Iterar**: Modificar overlays según necesidad y reaplicar

### Mejores Prácticas

1. **Estructura de directorios clara**:
   - Base para configuración común
   - Overlays por entorno/región/cliente

2. **Usar generadores para ConfigMaps/Secrets**:
   - Kustomize añade hash al nombre para forzar rolling updates

3. **Versionado en Git**:
   ```
   base/          → branch: main
   overlays/dev/  → branch: develop
   overlays/prod/ → branch: production
   ```

4. **No modificar la base en overlays**:
   - Base debe ser estable
   - Todas las personalizaciones en overlays

5. **Documentar transformaciones**:
   ```yaml
   # kustomization.yaml
   # Purpose: Production overlay for webapp
   # Maintainer: ops-team@company.com
   # Last updated: 2026-02-06
   ```

6. **Testing antes de producción**:
   ```bash
   # Ver diferencias
   kubectl diff -k overlays/prod/
   
   # Dry-run
   kubectl apply -k overlays/prod/ --dry-run=server
   ```

7. **Usar componentes para features opcionales**:
   - Monitoring (Prometheus)
   - Service Mesh (Istio)
   - Backups (Velero)

### Resumen Kustomize

Kustomize permite gestionar configuraciones de Kubernetes de forma eficiente mediante:

1. **Base única** con configuración común
2. **Overlays** para personalizaciones por entorno
3. **Transformaciones declarativas** sin modificar originales
4. **Integración nativa** en kubectl
5. **YAML puro** sin templating complejo

**Flujo típico**:
```bash
# Crear estructura
kustomize create --autodetect

# Ver resultado
kubectl kustomize overlays/prod/

# Aplicar
kubectl apply -k overlays/prod/

# Verificar
kubectl get all -n production
```

Es ideal para equipos que necesitan gestionar múltiples entornos manteniendo DRY (Don't Repeat Yourself) y trazabilidad completa en Git.
