# Resolución de Problemas: Catalog Discovery y Contract Negotiation

**Fecha:** 9 de febrero de 2026  
**Conectores:** MondragonAssembly (MASS) ↔ Ikerlan (IKLN)  
**Objetivo:** Habilitar consulta de catálogos y negociación de contratos entre conectores EDC  
**Estado Final:** ✅ Catalog Discovery funcionando | ⚠️ Contract Negotiation bloqueado por STS

---

## 📋 Resumen Ejecutivo

### Contexto Inicial
Tras el despliegue de los conectores EDC de MASS e IKLN, las consultas de catálogo retornaban respuestas vacías a pesar de tener assets configurados. El problema se atribuyó inicialmente a tokens DIM expirados.

### Problemas Identificados y Resueltos
1. ✅ **Token Expiry**: DIM tokens expiraban en 5 minutos → Configurado a 60 minutos
2. ✅ **Trusted Issuers**: Configuración bidireccional de DIDs confiables
3. ✅ **BusinessPartnerStore**: Registro manual de BPNs entre conectores
4. ✅ **Access Policy**: Creación de política simplificada sin validación VC
5. ✅ **UI Configuration**: Corrección de endpoints en EDC UI
6. ✅ **Catalog Discovery**: Catálogos ahora visibles correctamente

### Problema Crítico Pendiente
❌ **Contract Negotiation**: Bloqueado por endpoint STS (`/api/sts`) no implementado en dim-wallet-proxy

## 🛠️ Soluciones Implementadas

### 1. Extensión de Token Expiry (5 → 60 minutos)

#### **Problema**
El DIM Wallet Proxy tenía configurado `TOKEN_EXPIRY_TIME=5` (minutos), causando expiración prematura de tokens IATP.

#### **Solución Aplicada**
```bash
# Modificar ConfigMap
kubectl edit configmap dim-wallet-proxy-config -n portal

# Cambio:
TOKEN_EXPIRY_TIME=60  # De 5 a 60 minutos

# Reiniciar proxy
kubectl rollout restart deployment/dim-wallet-proxy -n portal
```

#### **¿Es la forma correcta?**
- ✅ **Temporal/Testing**: Sí, es válido para desarrollo
- ⚠️ **Producción**: Debería revisarse la duración óptima según requisitos de seguridad
- 📝 **Alternativa**: En producción, el DIM oficial gestiona tokens con renovación automática

#### **Verificación**
```bash
# Obtener token y decodificar
TOKEN=$(curl -X POST "http://dim-wallet-proxy.../oauth/token" ...)
echo $TOKEN | jwt decode -

# Verificar:
"exp": 1770656872,  # +3600 segundos = 60 minutos ✅
```

### 2. Configuración Bidireccional de Trusted Issuers

#### **Problema**
Los conectores solo confiaban en el DID del CX-Operator (`BPNL00000003CRHK`), no entre sí.

```yaml
# Configuración inicial (INCOMPLETA)
iatp:
  trustedIssuers:
    - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK
    # ❌ Faltaba IKLN en MASS y viceversa
```

#### **Solución Aplicada**

**MASS Connector** ([values-mass-connector.yaml](values-mass-connector.yaml#L43)):
```yaml
iatp:
  trustedIssuers:
    - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK  # CX-Operator
    - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000002IKLN  # ← AÑADIDO
```

**IKLN Connector** ([values-ikln-connector.yaml](values-ikln-connector.yaml#L43)):
```yaml
iatp:
  trustedIssuers:
    - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK  # CX-Operator
    - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS  # ← AÑADIDO
```

#### **¿Es la forma correcta?**
✅ **Sí, completamente correcto**

- Los `trustedIssuers` definen qué DIDs pueden emitir credenciales verificables válidas
- En Catena-X, para relaciones B2B, ambos partners deben confiar mutuamente
- Esta configuración es **declarativa** y se gestiona en el despliegue Helm

#### **Conceptos Clave**

**Trusted Issuers vs BusinessPartnerStore:**
```
┌──────────────────────────────────────────────────────────────┐
│  Trusted Issuers (Nivel Criptográfico)                      │
│  ────────────────────────────────────────────────────────   │
│  "¿Confío en las credenciales firmadas por este DID?"       │
│                                                              │
│  Ejemplo:                                                    │
│  MASS confía en VCs firmados por:                           │
│    - CX-Operator (MembershipCredential)                     │
│    - IKLN (puede presentar VCs autoemitidos)                │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  BusinessPartnerStore (Nivel Aplicación)                    │
│  ────────────────────────────────────────────────────────   │
│  "¿Con qué BPNs quiero hacer negocios?"                     │
│                                                              │
│  Ejemplo:                                                    │
│  MASS permite negociaciones con:                            │
│    - BPNL00000002IKLN (trusted-partner group)               │
└──────────────────────────────────────────────────────────────┘
```

**Ambos niveles son necesarios y complementarios.**

### 3. Registro en BusinessPartnerStore (⚠️ Manual)

#### **Problema Descubierto**
El BusinessPartnerStore de cada conector estaba vacío. Aunque MASS e IKLN estaban registrados en el Portal y tenían BPNs asignados, **cada conector EDC mantiene su propia whitelist local** de partners autorizados.

#### **Flujo de Negociación Bidireccional**
```
Consumer (IKLN)                  Provider (MASS)
     │                                │
     │ 1. Contract Request            │
     │───────────────────────────────>│
     │                                │
     │                          Valida:
     │                          - ¿IKLN en mi BusinessPartnerStore? ✅
     │                          - ¿Policy cumplida? ✅
     │                                │
     │ 2. Contract Agreement          │
     │<───────────────────────────────│
     │                                │
  Valida:                             │
  - ¿MASS en mi BusinessPartnerStore? ✅
  - ¿Agreement válido? ✅
     │                                │
```

**Para que funcione, AMBAS direcciones necesitan registro:**
- MASS debe tener a IKLN en su BusinessPartnerStore

### Causa Raíz: Endpoint STS No Implementado

**¿Qué es STS?**

**STS = Secure Token Service**  
Servicio que implementa el protocolo **IATP (Identity and Trust Protocol)** de Catena-X mediante **token exchange** (intercambio de tokens).

**Flujo IATP completo:**
```
┌────────────────────────────────────────────────────────────────┐
│  IATP Authentication Flow                                      │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  1. OAuth Token (Autenticación básica)                        │
│     Consumer → DIM Wallet: POST /oauth/token                  │
│     Response: access_token (JWT estándar)                     │
│                                                                │
│  2. SI Token Exchange (Self-Issued Token con VCs)             │
│     Consumer → STS: POST /api/sts                             │
│     Request:                                                   │
│       - grant_type: urn:ietf:params:oauth:grant-type:token-exchange
│       - subject_token: {OAuth Token}                          │
│       - audience: {Provider DID}                              │
│     Response: SI Token (JWT con VCs embebidos)                │
│                                                                │
│  3. DSP Message con SI Token                                  │
│     Consumer → Provider: Contract Request + SI Token          │
│     Provider valida:                                           │
│       - Firma del SI Token                                     │
│       - VCs incluidos (Membership, BPN, Framework)            │
│       - Audience (token destinado para mí)                    │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**Diferencia OAuth Token vs SI Token:**

| Aspecto | OAuth Token | SI Token (IATP) |
|---------|-------------|-----------------|
| **Endpoint** | `/oauth/token` | `/api/sts` |
| **Propósito** | Autenticación básica | Autenticación + Autorización |
| **Contenido** | Subject, exp, scope | Subject + Verifiable Credentials |
| **Firmado por** | DIM Wallet | Consumer (self-issued) |
| **Audience** | Genérico | Provider específico |

**Estructura de SI Token:**
```json
{
  "header": {
    "alg": "EdDSA",
    "kid": "did:web:...BPNL00000002IKLN#key-1"
  },
  "payload": {
    "iss": "did:web:...BPNL00000002IKLN",
    "sub": "did:web:...BPNL00000002IKLN",
    "aud": "did:web:...BPNL00000000MASS",
    "exp": 1770656872,
    "vcs": [
      {
        "@type": "MembershipCredential",
        "holderIdentifier": "BPNL00000002IKLN",
```

### Análisis del Problema

**Configuración en conectores:**
```yaml
# values-mass-connector.yaml y values-ikln-connector.yaml
iatp:
  sts:
    dim:
      url: http://dim-wallet-proxy.portal.svc.cluster.local:8080/api/sts
    oauth:
      token_url: http://dim-wallet-proxy.portal.svc.cluster.local:8080/oauth/token
```

**Verificación de implementación:**

```bash

# Resultado:
Proxying POST /oauth/token  ✅ (funciona)
Proxying POST /oauth/token  ✅ (funciona)
# ❌ NO HAY PETICIONES A /api/sts
```

**Prueba manual del endpoint:**
```bash
# 1. Obtener OAuth token
OAUTH_TOKEN=$(curl -s -X POST \
  "http://dim-wallet-proxy.../oauth/token" \
  -d "grant_type=client_credentials&client_id=BPNL00000000MASS&client_secret=client-secret" \
  | jq -r '.access_token')

echo "OAuth Token: ${OAUTH_TOKEN:0:50}..."
# ✅ Funciona

# 2. Intentar token exchange
curl -v -X POST "http://dim-wallet-proxy.../api/sts" \
  -H "Content-Type: application/json" \
  -d "{
    \"grant_type\": \"urn:ietf:params:oauth:grant-type:token-exchange\",
    \"audience\": \"did:web:ssi-dim-wallet-stub...:BPNL00000002IKLN\",
    \"subject_token\": \"$OAUTH_TOKEN\",
    \"subject_token_type\": \"urn:ietf:params:oauth:token-type:access_token\"
  }"

# ❌ Respuesta: HTTP 400 Bad Request
# "Invalid serialized unsecured/JWS/JWE object: Missing part delimiters"
```

### Conclusión

**El dim-wallet-proxy desplegado NO implementa funcionalidad completa de STS:**

| Endpoint | Estado | Funcionalidad |
|----------|--------|---------------|
| `/oauth/token` | ✅ Implementado | OAuth authentication |
| `/api/presentations/query` | ✅ Implementado | VC queries |
| `/api` (Credential Service) | ✅ Parcial | VC metadata |
| **`/api/sts`** | ❌ **Incompleto** | **Token exchange falta** |

**Por qué falla:**
- El proxy puede interceptar requests OAuth y agregar VCs a responses
- Pero **NO puede generar SI Tokens firmados** que requieren:
  - Gestión de claves privadas por BPN
  - Firma JWT con clave del BPN emisor
  - Construcción de payload con VCs embebidos
  - Validación de audience/scope

**Evidencia en logs MASS:**
```
"Unable to obtain credentials: Empty optional"
```

MASS llama a STS, pero la respuesta está vacía porque el endpoint no genera el SI Token correctamente.

#### Opción 1: Implementar STS en dim-wallet-proxy ⭐ Recomendado

**Características necesarias:**
```javascript
// Pseudocódigo para /api/sts endpoint

app.post('/api/sts', async (req, res) => {
  const { grant_type, subject_token, audience } = req.body;
  
  // 1. Validar OAuth token
  const claims = verifyJWT(subject_token);
  const bpn = claims.sub; // BPNL00000000MASS
  
  // 2. Obtener VCs del BPN
  const vcs = await getCredentials(bpn);
  
  // 3. Crear SI Token payload
  const payload = {
    iss: `did:web:...${bpn}`,
    sub: `did:web:...${bpn}`,
    aud: audience,
    exp: Date.now() + 3600,
    vcs: vcs  // [MembershipCredential, BpnCredential, ...]
  };
  
  // 4. Firmar con clave privada del BPN
  const privateKey = await getPrivateKey(bpn);
  const siToken = signJWT(payload, privateKey);
  
  // 5. Retornar SI Token
  res.json({
    access_token: siToken,
    token_type: "Bearer",
    expires_in: 3600
  });
});
```

### Lecciones Aprendidas

**Arquitectura multi-nivel:**
- **Portal** (global network) ≠ **EDC** (individual connector)
- Ambos niveles necesitan configuración independiente
- No hay sincronización automática entre ellos

**IATP es complejo:**
- Requiere STS completo con token exchange
- VCs deben estar correctamente embebidos en SI Tokens
- OAuth tokens NO son suficientes para DSP protocol

**Testing incremental es clave:**
- Empezar con policies simples (BPN-only)
- Validar cada capa antes de agregar complejidad
- Logs detallados son esenciales para debugging
