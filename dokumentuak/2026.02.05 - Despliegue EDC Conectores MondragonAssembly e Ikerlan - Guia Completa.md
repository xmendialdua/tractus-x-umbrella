## Conceptos Fundamentales

### ¿Qué es un Conector EDC?

Un **EDC (Eclipse Dataspace Connector)** es el componente que permite a las empresas participar en el intercambio de datos del dataspace Catena-X. Es como un "embajador digital" de cada empresa.

**Cada conector tiene 2 componentes:**

1. **Control Plane** (Plano de Control):
   - Negocia contratos
   - Valida políticas de acceso
   - Gestiona identidades (BPN, DIDs)
   - Coordina transferencias

2. **Data Plane** (Plano de Datos):
   - Transfiere los datos reales
   - Aplica transformaciones si es necesario
   - Gestiona la seguridad del transporte

### ¿Por qué cada partner necesita su propio conector?

```
┌─────────────────────────────────────────────────────────────┐
│               Portal Catena-X (Central)                      │
│                                                              │
│  - Gestión de partners                                       │
│  - Registro de conectores                                    │
│  - Catálogo centralizado                                     │
└─────────────────────────────────────────────────────────────┘
                          ↓ ↓ ↓
        ┌─────────────────┴─┴─┴──────────────────┐
        │                                          │
        ▼                                          ▼
┌──────────────────────────┐        ┌──────────────────────────┐
│  EDC MondragonAssembly   │◄──────►│      EDC Ikerlan         │
│  BPNL00000000MASS        │ Datos  │  BPNL00000002IKLN        │
│                          │◄──────►│                          │
│  - Control Plane         │        │  - Control Plane         │
│  - Data Plane            │        │  - Data Plane            │
│                          │        │                          │
│  Backend MondragonAssembly│       │  Backend Ikerlan        │
│  (Sistema interno)       │        │  (Sistema interno)       │
└──────────────────────────┘        └──────────────────────────┘
```

**Razones:**
- ✅ **Autonomía**: Cada empresa controla sus propios datos y políticas
- ✅ **Seguridad**: Los datos nunca pasan por un punto central
- ✅ **Trazabilidad**: Cada empresa sabe exactamente quién accede a qué
- ✅ **Descentralización**: No hay un único punto de fallo

### Roles en el Dataspace

Aunque hablaremos de "provider" y "consumer", en realidad **cada partner puede ser ambos**:

- **Provider (Proveedor)**: Empresa que publica/ofrece datos
- **Consumer (Consumidor)**: Empresa que consume/solicita datos

**En nuestro caso:**
- MondragonAssembly será **provider** cuando ofrezca datos a Ikerlan
- MondragonAssembly será **consumer** cuando consuma datos de Ikerlan
- Ikerlan será **provider** cuando ofrezca datos a MondragonAssembly
- Ikerlan será **consumer** cuando consuma datos de MondragonAssembly

### Diagrama de Flujo: Intercambio de Datos

```
┌──────────────────────────────────────────────────────────────┐
│                 FASE 1: Descubrimiento                        │
└──────────────────────────────────────────────────────────────┘

Ikerlan busca proveedores de datos → BDRS → Encuentra MondragonAssembly
                                              (BPN → DID → URL del EDC)

┌──────────────────────────────────────────────────────────────┐
│                 FASE 2: Negociación                           │
└──────────────────────────────────────────────────────────────┘

EDC Ikerlan           →  Solicitud de catálogo  →  EDC MondragonAssembly
(Control Plane)       ←  Catálogo con ofertas  ←   (Control Plane)
                      →  Solicitud contrato    →
                      ←  Validación políticas  ←
                      ←  Contrato firmado      ←

┌──────────────────────────────────────────────────────────────┐
│                 FASE 3: Validación de Identidad              │
└──────────────────────────────────────────────────────────────┘

EDC MondragonAssembly →  Verificar DID Ikerlan  →  DIM Wallet Stub
                       ←  Credencial válida      ←
                       ←  Políticas OK           ←

┌──────────────────────────────────────────────────────────────┐
│                 FASE 4: Transferencia de Datos               │
└──────────────────────────────────────────────────────────────┘

EDC Ikerlan           →  Iniciar transferencia  →  EDC MondragonAssembly
(Data Plane)          ←  Stream de datos        ←   (Data Plane)
                                                     ↓
                                                Backend MondragonAssembly
```

### 2.2. Crear Archivo de Configuración de EDCs

Crear el archivo: `charts/values-ovh-data-exchange-mass-ikln.yaml`

```yaml
###############################################################
# Configuración EDC Conectores
# MondragonAssembly (BPNL00000000MASS) e Ikerlan (BPNL00000002IKLN)
# Fecha: 2026-02-05
###############################################################

# Configuración adicional del wallet stub
identity-and-trust-bundle:
  ssi-dim-wallet-stub:
    server:
      trustedIssuers:
        # Solo confiamos en credenciales emitidas por CX-Operator
        - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK

# ============================================================
# EDC para MondragonAssembly
# ============================================================
dataconsumerOne:
  enabled: true
  dataspace-connector-bundle:
    # Deshabilitar Vault embebido (usamos el del sistema)
    vault:
      enabled: false
    
    tractusx-connector:
      # Identificación del participante
      participant:
        id: "BPNL00000000MASS"
      
      # IATP: Identity and Trust Protocol
      iatp:
        id: did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS
        trustedIssuers:
          - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK
        sts:
          dim:
            url: http://portal-ssi-dim-wallet-stub/api/sts
          oauth:
            token_url: http://portal-ssi-dim-wallet-stub/oauth/token
      
      # Control Plane
      controlplane:
        env:
          TX_IAM_IATP_CREDENTIALSERVICE_URL: http://portal-ssi-dim-wallet-stub/api
        bdrs:
          server:
            url: http://bdrs-server:8080/api/v1/directory
        
        # Ingress para acceso externo
        ingresses:
          - enabled: true
            hostname: "edc-mass-control.51.178.94.25.nip.io"
            endpoints:
              - protocol
              - management
            tls:
              enabled: false
      
      # Data Plane
      dataplane:
        env:
          TX_IAM_IATP_CREDENTIALSERVICE_URL: http://portal-ssi-dim-wallet-stub/api
        
        # Ingress para acceso externo
        ingresses:
          - enabled: true
            hostname: "edc-mass-data.51.178.94.25.nip.io"
            endpoints:
              - public
            tls:
              enabled: false

# ============================================================
# EDC para Ikerlan
# ============================================================
tx-data-provider:
  enabled: true
  dataspace-connector-bundle:
    # Deshabilitar Vault embebido
    vault:
      enabled: false
    
    tractusx-connector:
      # Identificación del participante
      participant:
        id: "BPNL00000002IKLN"
      
      # IATP: Identity and Trust Protocol
      iatp:
        id: did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000002IKLN
        trustedIssuers:
          - did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK
        sts:
          dim:
            url: http://portal-ssi-dim-wallet-stub/api/sts
          oauth:
            token_url: http://portal-ssi-dim-wallet-stub/oauth/token
      
      # Control Plane
      controlplane:
        env:
          TX_IAM_IATP_CREDENTIALSERVICE_URL: http://portal-ssi-dim-wallet-stub/api
        bdrs:
          server:
            url: http://bdrs-server:8080/api/v1/directory
        
        # Ingress para acceso externo
        ingresses:
          - enabled: true
            hostname: "edc-ikln-control.51.178.94.25.nip.io"

              enabled: false
```

## PASO 4: Despliegue con Helm

### 4.1. Pre-requisitos

```bash
# 1. Asegurar que estamos en el directorio correcto
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella/charts/umbrella

# 2. Verificar que los archivos de configuración existen
ls -la values-adopter-portal-for-onboarding.yaml
ls -la values-ovh-hosts-portal.yaml
ls -la ../values-ovh-data-exchange-mass-ikln.yaml
```

### 4.2. Vista Previa del Merge (Opcional)

Antes de desplegar, podemos ver cómo Helm mergeará los valores:

```bash
helm template portal . \
  -f values-adopter-portal-for-onboarding.yaml \
  -f values-ovh-hosts-portal.yaml \
  -f ../values-ovh-data-exchange-mass-ikln.yaml \
  -n portal | grep -A 20 "kind: Deployment" | head -100
```

### 4.3. Comando de Despliegue

```bash
# Actualizar release existente del portal
helm upgrade portal . \
  -f values-adopter-portal-for-onboarding.yaml \
  -f values-ovh-hosts-portal.yaml \
  -f ../values-ovh-data-exchange-mass-ikln.yaml \
  -n portal \
  --timeout 20m \
  --wait
```

**Explicación del comando:**
- `helm upgrade portal .` - Actualiza el release llamado "portal"
- `-f <archivo>` - Aplica archivos de valores (se mergean en orden)
- `-n portal` - Namespace de Kubernetes
- `--timeout 20m` - Espera hasta 20 minutos
- `--wait` - Espera a que todos los pods estén Ready

### 4.4. Seguimiento del Despliegue

En otra terminal, monitorear el progreso:

```bash
# Ver todos los pods en tiempo real
watch -n 2 'kubectl get pods -n portal'

# Ver eventos del namespace
kubectl get events -n portal --sort-by='.lastTimestamp' -w

# Ver logs de un EDC específico (cuando aparezca)
kubectl logs -f -n portal -l app.kubernetes.io/component=controlplane
```

### 4.5. Tiempo Estimado

- **Actualización completa**: 10-15 minutos
- **EDCs ready**: 5-8 minutos después del inicio

## PASO 7: Configuración de Data Assets

Ahora que los conectores están registrados, cada partner debe configurar qué datos quiere compartir.

### 7.1. Conceptos: Assets, Policies y Contract Definitions

#### Asset (Activo de Datos)
Define **QUÉ** datos se comparten:
- ID del asset
- Descripción
- URL del backend donde están los datos
- Tipo de dato (API, archivo, base de datos, etc.)

#### Policy (Política)
Define **QUIÉN** puede acceder y **BAJO QUÉ CONDICIONES**:
- BPN específico
- Rol o credencial requerida
- Tiempo de validez
- Restricciones de uso

#### Contract Definition (Definición de Contrato)
Une un **Asset** con una **Policy**:
- Para este asset...
- ... aplica esta política de acceso

## PASO 8: Probar Intercambio de Datos

### 8.1. Flujo de Prueba: Ikerlan Consume Datos de MondragonAssembly

#### 8.1.1. Ikerlan - Descubrir Catálogo de MondragonAssembly

```bash
# URL del EDC de Ikerlan
IKLN_EDC_MGMT="http://edc-ikln-control.51.178.94.25.nip.io/management"

# URL del EDC de MondragonAssembly (protocolo DSP)
MASS_EDC_DSP="http://edc-mass-control.51.178.94.25.nip.io/protocol"

# Solicitar catálogo
curl -X POST "${IKLN_EDC_MGMT}/v2/catalog/request" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: password" \
  -d "{
    \"@context\": {},
    \"protocol\": \"dataspace-protocol-http\",
    \"counterPartyAddress\": \"${MASS_EDC_DSP}\",
    \"querySpec\": {}
  }"
```

**Respuesta esperada:**
```json
{
  "@id": "catalog-id",
  "dcat:dataset": [
    {
      "@id": "mass-production-data-001",
      "odrl:hasPolicy": {
        "@id": "...",
        "odrl:permission": [...]
      },
      "dcat:distribution": [...]
    }
  ]
}
```

#### 8.1.2. Ikerlan - Iniciar Negociación de Contrato

```bash
# Copiar el offer ID del catálogo anterior
OFFER_ID="mass-production-data-001"

# Iniciar negociación
curl -X POST "${IKLN_EDC_MGMT}/v2/contractnegotiations" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: password" \
  -d "{
    \"@context\": {},
    \"counterPartyAddress\": \"${MASS_EDC_DSP}\",
    \"protocol\": \"dataspace-protocol-http\",
    \"offer\": {
      \"offerId\": \"${OFFER_ID}\",
      \"assetId\": \"mass-production-data-001\",
      \"policy\": {
        \"@type\": \"Set\",
        \"permission\": []
      }
    }
  }"
```

**Respuesta:**
```json
{
  "@id": "negotiation-123abc",
  "state": "REQUESTED"
}
```

#### 8.1.3. Verificar Estado de la Negociación

```bash
NEGOTIATION_ID="negotiation-123abc"

# Consultar estado
curl "${IKLN_EDC_MGMT}/v2/contractnegotiations/${NEGOTIATION_ID}" \
  -H "X-Api-Key: password"
```

Esperar hasta que el estado sea `FINALIZED`. Entonces obtendrás un `agreementId`.

#### 8.1.4. Iniciar Transferencia de Datos

```bash
AGREEMENT_ID="agreement-456def"

curl -X POST "${IKLN_EDC_MGMT}/v2/transferprocesses" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: password" \
  -d "{
    \"@context\": {},
    \"assetId\": \"mass-production-data-001\",
    \"contractId\": \"${AGREEMENT_ID}\",
    \"counterPartyAddress\": \"${MASS_EDC_DSP}\",
    \"protocol\": \"dataspace-protocol-http\",
    \"transferType\": \"HttpData-PULL\",
    \"dataDestination\": {
      \"type\": \"HttpProxy\"
    }
  }"
```

**Respuesta:**
```json
{
  "@id": "transfer-789ghi",
  "state": "STARTED"
}
```

#### 8.1.5. Obtener Endpoint de Datos

```bash
TRANSFER_ID="transfer-789ghi"

# Esperar a que el estado sea STARTED
curl "${IKLN_EDC_MGMT}/v2/transferprocesses/${TRANSFER_ID}" \
  -H "X-Api-Key: password"
```

La respuesta incluirá un `dataAddress` con el endpoint temporal para descargar los datos.

#### 8.1.6. Descargar Datos

```bash
# Usar el endpoint proporcionado en dataAddress
DATA_ENDPOINT="http://edc-ikln-data.51.178.94.25.nip.io/public/..."
AUTH_TOKEN="<token-from-response>"

curl "${DATA_ENDPOINT}" \
  -H "Authorization: ${AUTH_TOKEN}"
```

**¡Éxito!** Ikerlan ha consumido datos de MondragonAssembly a través de los EDC connectors.

### 8.2. Prueba Inversa: MondragonAssembly Consume Datos de Ikerlan

Repetir el mismo proceso pero invirtiendo los roles:
- MondragonAssembly consulta el catálogo de Ikerlan

## Troubleshooting

### Problema 1: EDC Pod no arranca (CrashLoopBackOff)

**Síntomas:**
```bash
kubectl get pods -n portal | grep dataconsumer
# portal-dataconsumer-one-...-controlplane-xxx   0/1   CrashLoopBackOff
```

**Diagnóstico:**
```bash
kubectl logs -n portal <pod-name> --tail=100
```

**Causas comunes:**
1. **Wallet Stub no disponible**
   - Verificar: `kubectl get pods -n portal | grep wallet`
   - Solución: Habilitar wallet stub en configuración

2. **BDRS no accesible**
   - Verificar: `kubectl get svc -n portal | grep bdrs`
   - Solución: Verificar URL en configuración del EDC

3. **Configuración IATP incorrecta**
   - Revisar logs: `"Failed to initialize IATP"`
   - Solución: Verificar DIDs y trustedIssuers

### Problema 2: Conector no aparece como "Online" en el Portal

**Síntomas:**
- Conector registrado pero estado: Offline

**Diagnóstico:**
```bash
# Verificar salud del EDC
curl http://edc-mass-control.51.178.94.25.nip.io/api/check/health

# Verificar ingress
kubectl get ingress -n portal | grep edc-mass
```

**Soluciones:**
1. Verificar que el hostname del ingress sea correcto
2. Verificar que el EDC esté escuchando en el puerto correcto
3. Revisar logs del controlplane: `kubectl logs -n portal <controlplane-pod>`

### Problema 3: Catálogo vacío al consultar

**Síntomas:**
```bash
curl ... /v2/catalog/request
# Respuesta: {"dcat:dataset": []}
```

**Causas:**
1. **No hay assets publicados** en el EDC provider
2. **Política no permite acceso** al consumer
3. **BPN incorrecto** en la política

**Solución:**
```bash
# Verificar assets en el provider
curl "${MASS_EDC_MGMT}/v3/assets" -H "X-Api-Key: password"

# Verificar policies
curl "${MASS_EDC_MGMT}/v2/policydefinitions" -H "X-Api-Key: password"

# Verificar que el BPN del consumer esté en la política
```

### Problema 4: Negociación de Contrato Falla

**Síntomas:**
```bash
# Estado de negociación: TERMINATED
curl "${IKLN_EDC_MGMT}/v2/contractnegotiations/${NEGOTIATION_ID}"
# "state": "TERMINATED"
```

**Diagnóstico:**
```bash
# Ver logs del controlplane del provider
kubectl logs -n portal <mass-controlplane-pod> | grep -i "negotiation"

# Buscar errores de validación de credenciales
kubectl logs -n portal <mass-controlplane-pod> | grep -i "credential"
```

**Causas comunes:**
1. **Credencial del consumer no válida**
   - Verificar que el DID del consumer esté en trustedIssuers
2. **Política no satisfecha**
   - Verificar que el BPN del consumer coincida con la política
3. **Wallet no responde**
   - Verificar salud del wallet: `kubectl logs -n portal <wallet-pod>`

### Problema 5: Transferencia Iniciada pero no completa

**Síntomas:**
```bash
# Estado: STARTED pero no progresa
curl "${IKLN_EDC_MGMT}/v2/transferprocesses/${TRANSFER_ID}"
# "state": "STARTED" (no cambia a COMPLETED)
```

**Diagnóstico:**
```bash
# Ver logs del dataplane del provider
kubectl logs -n portal <mass-dataplane-pod> --tail=200

# Ver logs del dataplane del consumer
kubectl logs -n portal <ikln-dataplane-pod> --tail=200
```

**Causas:**
1. **Backend no accesible**
   - El dataplane no puede alcanzar la URL del backend
2. **Error de autenticación** en el backend
3. **Timeout** en la conexión

**Soluciones:**
1. Verificar conectividad del dataplane al backend
2. Añadir credenciales si el backend las requiere
3. Aumentar timeouts en configuración del EDC

## Anexo B: Glosario

| Término | Significado |
|---------|-------------|
| **BPN** | Business Partner Number - Identificador único de empresa en Catena-X |
| **DID** | Decentralized Identifier - Identificador descentralizado (did:web:...) |
| **EDC** | Eclipse Dataspace Connector - Conector para intercambio de datos |
| **IATP** | Identity and Trust Protocol - Protocolo de identidad y confianza |
| **BDRS** | BPN-DID Resolution Service - Servicio que resuelve BPNs a DIDs |
| **Control Plane** | Componente del EDC que gestiona negociaciones y políticas |
| **Data Plane** | Componente del EDC que transfiere los datos reales |
| **Asset** | Recurso de datos que se comparte (dataset, API, archivo) |
| **Policy** | Regla que define quién puede acceder a un asset |
| **Contract** | Acuerdo negociado entre provider y consumer para acceder a datos |
| **DSP** | Dataspace Protocol - Protocolo de comunicación entre EDCs |
