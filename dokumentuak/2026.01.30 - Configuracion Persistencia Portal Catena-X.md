## Contexto y Motivación

### Problema Identificado

Durante el proceso de onboarding de business partners (TestCompany1 e Ikerlan), se perdieron los datos almacenados en Keycloak Central IDP al reiniciar los pods. Esto incluyó:
- Usuarios de compañía creados manualmente
- Configuraciones de autenticación
- Tokens y sesiones activas

**Causa raíz:** Las bases de datos PostgreSQL de los componentes del Portal estaban configuradas sin persistencia, utilizando `emptyDir` (almacenamiento efímero).

### Solución

Habilitar **Persistent Volume Claims (PVCs)** para todas las bases de datos PostgreSQL del Portal, garantizando que los datos sobrevivan a reinicios de pods y redeploys.

## ¿Qué es la Persistencia en Kubernetes?

### Tipos de Almacenamiento

#### 1. **emptyDir** (Efímero)
```yaml
volumes:
  - name: data
    emptyDir: {}
```

**Características:**
- ❌ Los datos se pierden cuando el pod se elimina
- ✅ Rápido y sin configuración adicional
- ✅ Útil para datos temporales o caché
- ⚠️ **NO recomendado para bases de datos**

#### 2. **PersistentVolumeClaim (PVC)** (Persistente)
```yaml
postgresql:
  primary:
    persistence:
      enabled: true
      size: 5Gi
      storageClass: "csi-cinder-high-speed"
```

**Características:**
- ✅ Los datos sobreviven a reinicios de pods
- ✅ Los datos sobreviven a eliminación de pods
- ✅ Permite redeploys sin pérdida de datos
- ✅ Soporta expansión de tamaño (sin downtime)
- ❌ Requiere provisioning de almacenamiento
- ❌ Tiene coste asociado

### Ciclo de Vida de un PVC

```
┌─────────────────────────────────────────────────────────┐
│  1. Helm crea PVC                                       │
│     └─ name: data-portal-postgresql-primary-0          │
│     └─ size: 5Gi                                        │
│     └─ storageClass: csi-cinder-high-speed             │
└────────────────┬────────────────────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────────────────────┐
│  2. StorageClass provisiona PersistentVolume (PV)      │
│     └─ Crea volumen en backend de OVH (Cinder)        │
│     └─ Asigna automáticamente al PVC                   │
└────────────────┬────────────────────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────────────────────┐
│  3. Pod monta el PV                                     │
│     └─ PostgreSQL escribe datos en /bitnami/postgresql │
│     └─ Datos almacenados en volumen persistente        │
└────────────────┬────────────────────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────────────────────┐
│  4. Pod se reinicia                                     │
│     └─ Nuevo pod monta el MISMO PV                     │
│     └─ Todos los datos siguen disponibles              │
└─────────────────────────────────────────────────────────┘
```

## StorageClasses en OVH

OVH Kubernetes ofrece dos tipos de almacenamiento basados en OpenStack Cinder:

### 1. **csi-cinder-high-speed** (SSD) ⚡

**Características:**
- Almacenamiento SSD de alto rendimiento
- **Velocidad:** Alta IOPS (Input/Output Operations Per Second)
- **Precio:** 0.08€/GB/mes
- **Uso recomendado:** Producción, bases de datos con alta carga

```yaml
postgresql:
  primary:
    persistence:
      enabled: true
      size: 5Gi
      # storageClass no especificado = usa cluster default (SSD)
```

### 2. **csi-cinder-classic** (HDD) 💾

**Características:**
- Almacenamiento HDD estándar
- **Velocidad:** IOPS moderado
- **Precio:** 0.04€/GB/mes (50% más económico)
- **Uso recomendado:** Desarrollo, testing, datos de baja frecuencia

```yaml
postgresql:
  primary:
    persistence:
      enabled: true
      size: 5Gi
      storageClass: "csi-cinder-classic"  # HDD explícito
```

### Comparativa de Rendimiento

| Métrica | SSD (high-speed) | HDD (classic) |
|---------|------------------|---------------|
| IOPS (lectura) | ~3000 | ~100 |
| IOPS (escritura) | ~1500 | ~50 |
| Latencia | <1ms | 5-10ms |
| Throughput | ~500 MB/s | ~100 MB/s |
| Precio/GB/mes | 0.08€ | 0.04€ |

### Configuración del Cluster Default

```bash
# Ver StorageClass por defecto
kubectl get storageclass

# Output típico en OVH:
NAME                            PROVISIONER                RECLAIMPOLICY   VOLUMEBINDINGMODE
csi-cinder-classic              cinder.csi.openstack.org   Delete          Immediate
csi-cinder-high-speed (default) cinder.csi.openstack.org   Delete          Immediate
```

**Nota:** Si no se especifica `storageClass` en el PVC, se usa `csi-cinder-high-speed` (SSD).

### Decisión sobre StorageClass

Inicialmente se consideró especificar `storageClass: "csi-cinder-classic"` (HDD) para reducir costes en entorno de desarrollo:

```yaml
# Opción considerada pero NO implementada
postgresql:
  primary:
    persistence:
      enabled: true
      size: 5Gi
      storageClass: "csi-cinder-classic"  # HDD para dev
```

**Decisión final:** Omitir `storageClass` para usar el default del cluster (SSD):

**Ventajas:**
- ✅ Mejor rendimiento (importante para Keycloak y Portal)
- ✅ Simplicidad: menos configuración explícita
- ✅ Consistencia: todos los componentes usan mismo tipo de storage
- ✅ Menor latencia en operaciones de BD

**Desventajas:**
- ❌ Coste: ~2.08€/mes en lugar de ~1.04€/mes (diferencia: 1€/mes)

**Conclusión:** La diferencia de 1€/mes no justifica la complejidad adicional ni la posible degradación de rendimiento en entorno de desarrollo/testing.

## Despliegue con Persistencia

### Comando de Despliegue

**Nota:** Este despliegue NO incluye conectores EDC. Se despliega solo el Portal con todos sus servicios base habilitados con persistencia.

```bash
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella/charts/umbrella

helm upgrade portal . \
  -f values-adopter-portal-for-onboarding-with-persistence.yaml \
  -f values-ovh-hosts-portal.yaml \
  -n portal
```

### Orden de Archivos de Valores

El orden de los archivos `-f` es **crítico** debido al deep merge de Helm:

1. **`values-adopter-portal-for-onboarding-with-persistence.yaml`** (base)
   - Habilita componentes
   - Configura persistencia
   - Define tamaños de PVCs

2. **`values-ovh-hosts-portal.yaml`** (overlay específico de OVH)
   - URLs con IP del LoadBalancer
   - Configuración de Ingress
   - Configuración de aplicaciones (authServerUrl, baseUrl, etc.)

**Nota importante:** `values-ovh-hosts-portal.yaml` NO contiene configuración de persistencia, por lo que no sobreescribe los valores del primer archivo.

### Qué Cambia en el Despliegue

#### Antes (sin persistencia):
```yaml
# Implicit en charts por defecto
postgresql:
  primary:
    persistence:
      enabled: false  # Usa emptyDir
```

**Resultado:**
```bash
kubectl get pvc -n portal
# No resources found in portal namespace.
```

#### Después (con persistencia):
```yaml
# Explicit en values-adopter-portal-for-onboarding-with-persistence.yaml
postgresql:
  primary:
    persistence:
      enabled: true
      size: 5Gi
```

**Resultado:**
```bash
kubectl get pvc -n portal
# NAME                                    STATUS   VOLUME                 CAPACITY   STORAGECLASS
# data-portal-postgresql-primary-0        Bound    pvc-a1b2c3d4           5Gi        csi-cinder-high-speed
# data-centralidp-postgresql-primary-0    Bound    pvc-e5f6g7h8           3Gi        csi-cinder-high-speed
# data-sharedidp-postgresql-primary-0     Bound    pvc-i9j0k1l2           2Gi        csi-cinder-high-speed
# ...
```

### Tiempo de Despliegue

El primer despliegue con persistencia toma **más tiempo** debido al provisioning de volúmenes:

| Fase | Sin Persistencia | Con Persistencia |
|------|------------------|------------------|
| Provisioning PVCs | 0s | 30-60s |
| Creación de Pods | 2-3 min | 2-3 min |
| Inicialización BDs | 1-2 min | 1-2 min |
| **Total** | **3-5 min** | **4-7 min** |

## Gestión de PVCs

### Expansión de Volúmenes

Los PVCs con StorageClass de OVH soportan **expansión sin downtime**:

```bash
# 1. Editar el PVC (aumentar size)
kubectl edit pvc data-portal-postgresql-primary-0 -n portal

# Cambiar:
spec:
  resources:
    requests:
      storage: 5Gi  # ← Cambiar a 10Gi

# 2. El controlador CSI expande automáticamente el volumen
# 3. Verificar expansión
kubectl get pvc data-portal-postgresql-primary-0 -n portal
```

**⚠️ Limitaciones:**
- ✅ Puedes AUMENTAR el tamaño
- ❌ NO puedes DISMINUIR el tamaño
- ✅ La expansión es automática (sin reinicio de pod necesario en OVH)

### Backup de Datos

```bash
# Backup de PostgreSQL del Portal
kubectl exec -n portal portal-postgresql-primary-0 -- \
  pg_dump -U postgres portaldb > portal-backup-$(date +%Y%m%d).sql

# Backup de Central IDP
kubectl exec -n portal portal-centralidp-postgresql-0 -- \
  pg_dump -U postgres iamcentralidp > centralidp-backup-$(date +%Y%m%d).sql
```

### Restauración de Datos

```bash
# Restaurar Portal
cat portal-backup-20260130.sql | \
  kubectl exec -i -n portal portal-postgresql-primary-0 -- \
  psql -U postgres portaldb

# Restaurar Central IDP
cat centralidp-backup-20260130.sql | \
  kubectl exec -i -n portal portal-centralidp-postgresql-0 -- \
  psql -U postgres iamcentralidp
```

### Eliminación de PVCs

```bash
# Ver PVCs
kubectl get pvc -n portal

# Eliminar un PVC específico (CUIDADO: elimina datos permanentemente)
kubectl delete pvc data-portal-postgresql-primary-0 -n portal

# Eliminar todos los PVCs del namespace (PELIGROSO)
# kubectl delete pvc --all -n portal  # ← NO ejecutar sin backup
```

**⚠️ ADVERTENCIA:** 
- Eliminar un PVC elimina el PV asociado (si RECLAIM POLICY es `Delete`)
- Los datos se pierden permanentemente
- Hacer backup antes de eliminar

### Consideraciones de Producción

Para un entorno de **producción** se recomienda:

1. **Aumentar tamaños de PVCs:**
   - Portal: 10-20Gi (crecimiento de datos de usuarios)
   - Central IDP: 5-10Gi (más realms, usuarios, tokens)
   - BPDM: 10Gi cada uno (más business partners)

2. **Usar SSD exclusivamente:**
   - Keycloak requiere baja latencia para autenticación
   - Portal con alta concurrencia necesita IOPS elevado

3. **Implementar backups automáticos:**
   - CronJobs de Kubernetes para pg_dump diario
   - Retención de 7-30 días según requisitos

4. **Monitorización de uso:**
   - Alertas cuando PVCs superen 80% de capacidad
   - Crecimiento proyectado para planificar expansiones

**Coste estimado producción:**
```
~60Gi × 0.08€/GB = 4.80€/mes (~58€/año)
```

## Troubleshooting

### Problema 1: PVC en estado `Pending`

**Síntoma:**
```bash
kubectl get pvc -n portal
# NAME                              STATUS    VOLUME   CAPACITY   STORAGECLASS
# data-portal-postgresql-primary-0  Pending            0                       csi-cinder-high-speed
```

**Causas posibles:**

1. **StorageClass no existe**
   ```bash
   kubectl get storageclass
   # Verificar que csi-cinder-high-speed existe
   ```

2. **Cuota de almacenamiento superada en OVH**
   - Revisar panel de OVH → Kubernetes → Storage Quotas

3. **CSI driver no funciona**
   ```bash
   kubectl get pods -n kube-system | grep csi
   # Verificar que pods CSI están running
   ```

**Solución:**
```bash
# Describir PVC para ver eventos
kubectl describe pvc data-portal-postgresql-primary-0 -n portal

# Ver logs del provisioner
kubectl logs -n kube-system -l app=csi-cinder-controllerplugin
```

### Problema 2: Pod no puede montar PVC

**Síntoma:**
```bash
kubectl describe pod portal-postgresql-primary-0 -n portal
# Events:
#   Warning  FailedMount  Unable to attach or mount volumes: timed out waiting for the condition
```

**Causas posibles:**

1. **PVC y Pod en diferentes zonas de disponibilidad**
   - OVH Cinder volumes son zonales

2. **Volumen ya montado en otro nodo**
   - Solo RWO (ReadWriteOnce) está soportado

**Solución:**
```bash
# Forzar recreación del pod
kubectl delete pod portal-postgresql-primary-0 -n portal

# Si persiste, eliminar y recrear el StatefulSet
kubectl delete sts portal-postgresql -n portal
# Helm recreará automáticamente
```

### Problema 3: Datos no persisten después de reinicio

**Síntoma:**
- El pod se reinicia
- Los datos insertados previamente no existen

**Verificación:**
```bash
# 1. Verificar que el PVC está bound
kubectl get pvc -n portal | grep portal-postgresql

# 2. Verificar montaje en el pod
kubectl exec -n portal portal-postgresql-primary-0 -- mount | grep postgresql

# 3. Verificar que NO es emptyDir
kubectl get pod portal-postgresql-primary-0 -n portal -o yaml | grep -A 5 "volumes:"
```

**Solución:**
- Verificar que `persistence.enabled: true` en values
- Redesplegar con helm upgrade

### Problema 4: Espacio insuficiente

**Síntoma:**
```bash
kubectl logs -n portal portal-postgresql-primary-0
# FATAL: could not write to file: No space left on device
```

**Verificación:**
```bash
kubectl exec -n portal portal-postgresql-primary-0 -- df -h
```

**Solución:**
```bash
# Expandir PVC (edit spec.resources.requests.storage)
kubectl edit pvc data-portal-postgresql-primary-0 -n portal

# O via Helm values (aumentar size) y redeploy
```

### Problema 5: PVC no se elimina

**Síntoma:**
```bash
kubectl delete pvc data-portal-postgresql-primary-0 -n portal
# PVC stuck in "Terminating" state
```

**Causa:** Finalizers o pod aún usando el PVC

**Solución:**
```bash
# 1. Eliminar pod primero
kubectl delete pod portal-postgresql-primary-0 -n portal --force --grace-period=0

# 2. Eliminar finalizers si persiste
kubectl patch pvc data-portal-postgresql-primary-0 -n portal \
  -p '{"metadata":{"finalizers":null}}'
```
