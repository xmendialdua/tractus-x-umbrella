# 2026-02-03 - Corrección Redirect URIs y Script Desbloqueo Aplicaciones

## Contexto
Durante el proceso de onboarding de partners (MondragonAssembly en idp1 e Ikerlan en idp2), se detectaron dos problemas principales:
1. Error "Invalid parameter: redirect_uri" al seleccionar compañías en el Portal
2. Error "Invalid redirect uri" al hacer Sign Out de partners
3. Aplicaciones bloqueadas después de asignación manual de BPN

## Problemas Detectados

### 1. Error al Seleccionar Compañía en Portal

**Síntoma:**
```
Invalid parameter: redirect_uri
URL: http://sharedidp.51.178.94.25.nip.io/auth/realms/idp1/protocol/openid-connect/auth?...
     &redirect_uri=http%3A%2F%2Fcentralidp.51.178.94.25.nip.io%2Fauth%2Frealms%2FCX-Central%2Fbroker%2Fidp1%2Fendpoint
```

**Causa:**
El cliente `central-idp` en los realms de partners (idp1, idp2) tenía configurado un redirect URI incorrecto:
```
http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/CX-Operator/endpoint/*
```

Pero el sistema intentaba usar:
```
http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/idp1/endpoint
```

**Diagnóstico:**
```bash
kubectl exec -n portal portal-sharedidp-0 -- bash -c \
  'cd /tmp && /opt/bitnami/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080/auth --realm master \
  --user admin --password adminconsolepwsharedidp \
  --config /tmp/kcadm.config'

kubectl exec -n portal portal-sharedidp-0 -- bash -c \
  'cd /tmp && /opt/bitnami/keycloak/bin/kcadm.sh get clients -r idp1 \
  --config /tmp/kcadm.config -q clientId=central-idp \
  --fields clientId,redirectUris'
```

**Resultado:**
```json
{
  "clientId" : "central-idp",
  "redirectUris" : [ "http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/CX-Operator/endpoint/*" ]
}
```

### 2. Error al Cerrar Sesión (Sign Out)

**Síntoma:**
```
Invalid redirect uri
URL: http://sharedidp.51.178.94.25.nip.io/auth/realms/idp1/protocol/openid-connect/logout?...
     &post_logout_redirect_uri=http%3A%2F%2Fcentralidp.51.178.94.25.nip.io%2Fauth%2Frealms%2FCX-Central%2Fbroker%2Fidp1%2Fendpoint%2Flogout_response
```

**Causa:**
El redirect URI configurado no incluía el sufijo `/logout_response`:
- URI configurado: `http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/idp1/endpoint`
- URI necesario: `http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/idp1/endpoint/logout_response`

### Análisis de Fallos Comunes

#### Fallo 1: CREATE_BUSINESS_PARTNER_NUMBER_PUSH → FAILED

**Causa Raíz:**
- BPDM Ingress mal configurado (host: business-partners.tx.test en lugar de business-partners.51.178.94.25.nip.io)
- Portal Backend intentaba llamar a URL externa que no existía
- Error HTTP 404 al intentar POST a /gate/v6/input/business-partners

**Impacto:**
- BPN no se crea automáticamente
- Los steps siguientes que dependen del BPN fallan en cascada

**Solución:**
1. Cambiar configuración del Portal Backend para usar URLs internas de BPDM
2. Corregir Ingress de BPDM con script `fix-bpdm-ingress-ovh.sh`
3. Si ya falló, asignar BPN manualmente

**Causa Raíz:**
- El step anterior (CREATE_BUSINESS_PARTNER_NUMBER_PUSH) falló

**Query para encontrar process_id:**
```sql
SELECT 
    p.id as process_id,
    p.process_type_id,
    COUNT(ps.id) as num_steps
FROM portal.processes p
LEFT JOIN portal.process_steps ps ON p.id = ps.process_id
WHERE p.process_type_id = 1  -- APPLICATION_CHECKLIST
GROUP BY p.id, p.process_type_id
ORDER BY p.id;
```

## Lecciones Aprendidas

### 1. Realm Seeding y Redirect URIs
**Problema:** El init-container que hace realm-seeding crea los clientes con redirect URIs hardcodeados que no coinciden con el nombre del realm.

**Solución:** Script post-despliegue que corrige automáticamente los redirect URIs para todos los realms idp*.

**Implicación:** Después de cada despliegue que cree nuevos realms, ejecutar `fix-centralidp-redirect-uri.sh`.

### 2. Wildcard en Redirect URIs
**Importante:** Usar wildcard `/*` en los redirect URIs para permitir múltiples endpoints:
- `/endpoint` (para login)
- `/endpoint/logout_response` (para logout)

### 3. Process Steps y Estado Bloqueado
**Problema:** Cuando un step falla (como `ASSIGN_BPN_TO_USERS`), el proceso puede quedar bloqueado incluso después de corregir el problema subyacente.

**Solución:** 
- Marcar el step RETRIGGER como DONE
- Insertar el step FINISH_APPLICATION_ACTIVATION si no existe
- Forzar ejecución inmediata con Job manual del processes-worker

### 4. Separación de Responsabilidades
**Beneficio:** Separar scripts por función (BPDM, Self-Description, Redirect URIs, Desbloqueo) facilita:
- Debugging específico
- Ejecución selectiva
- Mantenimiento independiente

### 5. Búsqueda de Process ID
**Desafío:** No existe relación directa entre realm name y process_id en la BD.

**Solución Implementada:**
1. Buscar en mensajes de process_steps
2. Si no encuentra, usar orden de creación (asumiendo idp1=primero, idp2=segundo)
3. Fallback a búsqueda por nombre de compañía
