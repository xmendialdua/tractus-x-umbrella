# Migración del Portal Catena-X a Persistencia - Proceso Completo

**Fecha:** 30 de enero de 2026  
**Objetivo:** Habilitar persistencia en todos los componentes del Portal para prevenir pérdida de datos  
**Estado:** ⚠️ Con problemas - Algunos componentes seguían usando emptyDir (in-memory)

---

## 1. Contexto y Motivación

### Problema Original
- **Pérdida de datos en Keycloak**: Los usuarios y configuraciones se perdían al reiniciar los pods de PostgreSQL
- **Causa raíz**: Los pods usaban `emptyDir` (almacenamiento efímero) en lugar de PersistentVolumeClaims
- **Impacto**: Necesidad de re-ejecutar onboarding de TestCompany1 e Ikerlan tras cada reinicio

### Decisión
Habilitar persistencia en todos los componentes que usan PostgreSQL para garantizar la durabilidad de:
- Usuarios y configuraciones de Keycloak (Central IDP, Shared IDP)
- Datos del Portal (aplicaciones, suscripciones, notificaciones)
- Información de Business Partners (BPDM Pool, Gate)
- Registros de BPN Discovery y Discovery Finder
- Credenciales y DIDs del SSI Issuer

## 2. Análisis de Almacenamiento en OVH

### StorageClasses Disponibles

| StorageClass | Tipo | Rendimiento | Costo (€/GB/mes) | Uso Recomendado |
|--------------|------|-------------|------------------|-----------------|
| `csi-cinder-high-speed` | SSD | Alto | 0.08 | Producción, bases de datos (DEFAULT) |
| `csi-cinder-classic` | HDD | Estándar | 0.04 | Desarrollo, archivos estáticos |

### Decisión de StorageClass
- **Selección**: Usar StorageClass por defecto del cluster (`csi-cinder-high-speed` - SSD)
- **Justificación**:
  - Mejor rendimiento para bases de datos PostgreSQL
  - Diferencia de costo insignificante (~1€/mes para 26GB)
  - Simplificación de configuración (no especificar storageClass)
  - Coherencia con estándares del cluster

## 5. Proceso de Migración

### 5.1. Problema Encontrado: StatefulSet Immutability

**Error al intentar `helm upgrade` inicial:**
```
Error: UPGRADE FAILED: cannot patch "portal-centralidp-postgresql" with kind StatefulSet: 
spec: Forbidden: updates to statefulset spec for fields other than 'replicas', 'ordinals', 
'template', 'updateStrategy', 'persistentVolumeClaimRetentionPolicy' and 'minReadySeconds' 
are forbidden
```

**Causa raíz:**
- Los StatefulSets existentes tenían `volumeClaimTemplates` configurados para `emptyDir`
- Kubernetes NO permite modificar `volumeClaimTemplates` en StatefulSets existentes
- Es un campo inmutable por diseño de Kubernetes

### 5.2. Solución Implementada

**Paso 1: Identificar StatefulSets afectados**
```bash
kubectl get statefulset -n portal | grep postgresql
```

**Resultado:**
```
portal-bpndiscovery-postgresql       1/1     2m
portal-centralidp-postgresql         1/1     2m
portal-discoveryfinder-postgresql    1/1     2m
portal-issuer-postgresql             1/1     2m
portal-portal-backend-postgresql     1/1     2m
portal-sharedidp-postgresql          1/1     2m
```

**Paso 2: Borrar StatefulSets (permite recreación con nueva configuración)**
```bash
kubectl delete statefulset -n portal \
  portal-bpndiscovery-postgresql \
  portal-centralidp-postgresql \
  portal-discoveryfinder-postgresql \
  portal-portal-backend-postgresql \
  portal-sharedidp-postgresql \
  portal-issuer-postgresql
```

**Paso 3: Ejecutar helm upgrade**
```bash
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella/charts/umbrella

helm upgrade portal . \
  -f values-adopter-portal-for-onboarding-with-persistence.yaml \
  -f values-ovh-hosts-portal.yaml \
  -n portal
```

**Resultado:** ✅ Deployment exitoso

### 13.9. Lecciones Aprendidas

#### Problema 1: Confusión entre archivos de valores

**Error cometido:**
- Usar `values-adopter-portal-for-onboarding.yaml` (sin persistencia)
- En lugar de `values-adopter-portal-for-onboarding-with-persistence.yaml`

**Solución:**
- Siempre verificar qué archivo de valores se está usando
- Los archivos con `-with-persistence` DEBEN usarse después de la migración
- Documentar claramente cuál es el archivo correcto para cada escenario

#### Problema 2: StatefulSets no se actualizan automáticamente

**Problema:**
- Kubernetes NO actualiza volumeClaimTemplates de StatefulSets existentes
- Helm upgrade NO fuerza recreación de StatefulSets que no cambian en otros aspectos
- StatefulSets antiguos pueden persistir con configuración obsoleta

**Solución:**
- Al cambiar configuración de persistencia, **SIEMPRE borrar StatefulSets manualmente** antes de helm upgrade
- Verificar TODOS los StatefulSets, no solo los obvios
- Comando útil:
  ```bash
  kubectl get statefulset -n portal -o custom-columns=NAME:.metadata.name,AGE:.metadata.creationTimestamp
  ```

#### Problema 3: Arquitectura de BPDM poco clara

**Confusión:**
- Se esperaban 3 PVCs (pool, gate, orchestrator)
- En realidad solo hay 1 StatefulSet compartido

**Solución:**
- Documentar arquitecturas de bases de datos compartidas
- BPDM: 1 PostgreSQL, múltiples schemas
- No esperar 1:1 entre componente y StatefulSet

#### Problema 4: Datos inconsistentes dificultan diagnóstico

**Problema:**
- Datos de diferentes épocas en diferentes componentes
- Difícil saber qué está persistido y qué no
- Estado del sistema unclear

**Solución para futuros despliegues:**
1. Después de migración a persistencia, verificar **TODOS los PVCs esperados**
2. Verificar edad de **TODOS los StatefulSets** (deben ser recientes)
3. Hacer "smoke test" de datos: verificar que bases de datos están vacías/limpias
4. NO proceder con onboarding hasta verificar persistencia completa
