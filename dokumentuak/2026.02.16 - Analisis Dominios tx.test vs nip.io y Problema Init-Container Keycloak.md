## 1. Consulta Inicial

### Pregunta

> "En el fichero `/home/xmendialdua/projects/assembly/tractus-x-umbrella/docs/user/linux/README.md` se indica que debo usar dominios como `portal.tx.test`, `centralidp.tx.test`, etc., modificando `/etc/hosts` en mi máquina local.
>
> Sin embargo, en mi despliegue de OVH con IP `51.178.94.25`, estoy usando `portal.51.178.94.25.nip.io`. Me he visto obligado a modificar todos los valores en `values.yaml` y hacer cambios en las bases de datos de Keycloak.
>
> ¿Debo usar `*.tx.test` incluso en OVH? ¿Cómo debería haberlo hecho?"

### Contexto del Usuario

- Despliegue en OVH Kubernetes (no local)
- IP pública del LoadBalancer: `51.178.94.25`
- Usando dominios `*.51.178.94.25.nip.io`
- Ha tenido que:
  - Modificar `values.yaml` antes del despliegue
  - Ejecutar scripts SQL post-despliegue para corregir URLs en Keycloak
  - Actualizar múltiples configuraciones manualmente

## 2. Análisis del Problema

### Documentación Ambigua

La documentación en `/docs/user/linux/README.md` está escrita **exclusivamente para despliegues locales con Minikube**, pero no lo especifica claramente.

**Indicadores en la documentación:**

```markdown
# Línea 26-28: Start Minikube
minikube start --cpus=4 --memory=6gb

# Línea 88: DNS Resolution Setup
Proper DNS resolution is required to map local domain names to the Minikube IP address.

# Líneas 95-115: Hosts File Configuration
<MINIKUBE_IP>    portal.tx.test
<MINIKUBE_IP>    centralidp.tx.test
...
```

**Problema:** No hay un aviso claro de que esta configuración NO aplica para despliegues remotos (OVH, AWS, GCP, Azure).

## 3. Escenarios de Despliegue

### Escenario A: Despliegue LOCAL con Minikube

**Características:**
- Cluster corre en **tu máquina local** (laptop/desktop)
- IP privada local (ej: `192.168.49.2`)
- Solo accesible desde tu máquina

**Configuración DNS:**
```bash
# /etc/hosts en TU MÁQUINA LOCAL
192.168.49.2    portal.tx.test
192.168.49.2    centralidp.tx.test
192.168.49.2    sharedidp.tx.test
```

**¿Por qué funciona `*.tx.test`?**
- Solo tú accedes al sistema
- La resolución DNS es local (tu /etc/hosts)
- No necesita DNS público

**✅ Aplica la documentación de `/docs/user/linux/README.md`**

---

### Escenario B: Despliegue REMOTO (OVH, AWS, GCP, Azure)

**Características:**
- Cluster en **servidor remoto** (cloud)
- IP pública (ej: `51.178.94.25`)
- Accesible desde internet o múltiples máquinas

**Problema con `*.tx.test`:**
```
❌ Los dominios *.tx.test NO están registrados en DNS público
❌ No se pueden resolver desde internet
❌ No funcionan para acceso remoto
❌ Solo funcionarían si CADA usuario modifica su /etc/hosts local
```

**Soluciones para despliegues remotos:**

#### Opción 1: nip.io (servicios DNS wildcard) ⭐ RECOMENDADO para desarrollo

```yaml
# Uso actual del usuario - CORRECTO
portal.51.178.94.25.nip.io
centralidp.51.178.94.25.nip.io
sharedidp.51.178.94.25.nip.io
```

**Ventajas:**
- ✅ Funciona automáticamente, sin configuración DNS
- ✅ Accesible desde cualquier máquina
- ✅ Ideal para desarrollo y testing
- ✅ Cambio rápido de IPs

**Cómo funciona nip.io:**
```
portal.51.178.94.25.nip.io  →  resuelve automáticamente a → 51.178.94.25
```

#### Opción 2: Dominio Real (para producción)

```yaml
portal.catena-x.net
centralidp.catena-x.net
sharedidp.catena-x.net
```

**Requisitos:**
- Dominio registrado (ej: catena-x.net)
- Configurar registros DNS tipo A:
  ```
  portal.catena-x.net        A  51.178.94.25
  *.catena-x.net             A  51.178.94.25
  ```
- Certificados TLS/SSL (Let's Encrypt con cert-manager)

**❌ NO aplica la documentación de `/docs/user/linux/README.md`**

## 4. Decisión sobre Dominios

### ✅ Evaluación de la Decisión del Usuario

**Decisión tomada:** Usar `*.51.178.94.25.nip.io` en lugar de `*.tx.test`

**Veredicto:** **100% CORRECTA**

**Justificación:**
1. ✅ Es la única solución viable para despliegues remotos sin dominio propio
2. ✅ No requiere modificación de `/etc/hosts` en cada máquina cliente
3. ✅ Accesible desde cualquier ubicación con internet
4. ✅ Permite colaboración entre múltiples usuarios
5. ✅ Funciona con cualquier IP del LoadBalancer

### ⚠️ Proceso de Implementación

**Problema:** El usuario cambió los dominios **DESPUÉS** del despliegue inicial, lo que causó:
- Datos inconsistentes en PostgreSQL (Keycloak)
- Necesidad de scripts SQL manuales
- Tiempo adicional de corrección

**Proceso correcto:**

```bash
# 1. ANTES del despliegue - Obtener IP
export LB_IP=51.178.94.25
export DNS_SUFFIX=nip.io

# 2. ANTES del despliegue - Generar valores
./generate_values_hosts_file_from_template.sh

# 3. Desplegar con valores correctos desde inicio
helm install -f values-adopter-portal.yaml -f values-hosts.yaml ...

# 4. No se necesitan scripts post-despliegue
```

**Lo que el usuario hizo:**
```bash
# 1. Desplegó con valores por defecto (*.tx.test)
# 2. Se dio cuenta del problema
# 3. Modificó values.yaml
# 4. Redesplegar / Upgrade
# 5. Ejecutar scripts SQL para corregir BD
```

## 5. Problema Persistente con Keycloak

### Descripción del Problema

**Situación reportada:**
> "He actualizado los ficheros values.yaml antes de iniciar el despliegue, eliminado todos los namespaces, PVCs, etc. (despliegue 100% limpio). Aún así, hay URLs que no se almacenan correctamente en las bases de datos de Keycloak. Necesito ejecutar un script para actualizar la base de datos después del despliegue."

### URLs Problemáticas Encontradas

**En Central IDP (11 URLs con `.tx.test`):**
```
portal.tx.test - 4 ocurrencias
sharedidp.tx.test - 4 ocurrencias
partners-gate.tx.test - 1 ocurrencia
partners-pool.tx.test - 1 ocurrencia
managed-identity-wallets.tx.test - 1 ocurrencia
```

**En Shared IDP (2 URLs con `.tx.test`):**
```
centralidp.tx.test - 2 ocurrencias
```

### Script de Corrección POST-Despliegue

**Ubicación:** `/charts/umbrella/fix-keycloak-urls.sh`

**Ejemplo de correcciones necesarias:**
```sql
-- 1. Corregir client.root_url
UPDATE client 
SET root_url = 'http://portal.51.178.94.25.nip.io/home' 
WHERE client_id = 'Cl2-CX-Portal';

-- 2. Corregir redirect_uris
UPDATE redirect_uris 
SET value = 'http://portal.51.178.94.25.nip.io/*' 
WHERE client_id IN (
  SELECT id FROM client WHERE client_id IN ('Cl1-CX-Registration', 'Cl2-CX-Portal', 'Cl3-CX-Semantic')
);

-- 3. Corregir identity_provider_config
UPDATE identity_provider_config 
SET value = REPLACE(value, 'sharedidp.tx.test', 'sharedidp.51.178.94.25.nip.io')
WHERE value LIKE '%sharedidp.tx.test%';
```

**Pregunta clave:** ¿Por qué siguen apareciendo estas URLs incorrectas incluso en despliegues limpios?

## 6. Causa Raíz: Init-Container

### El Problema Real

El problema NO es la configuración en `values.yaml`. El problema es el **Init-Container de Keycloak**.

### Orden de Ejecución

```
┌─────────────────────────────────────────────────────────────┐
│ FASE 1: Init-Container                                      │
├─────────────────────────────────────────────────────────────┤
│ 1. Se ejecuta ANTES del realm seeding                       │
│ 2. Copia archivos JSON del init-container al pod            │
│ 3. Keycloak importa estos JSON a PostgreSQL                 │
│ 4. URLs hardcodeadas "*.tx.test" quedan en la BD           │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│ FASE 2: Realm Seeding (desde values.yaml)                  │
├─────────────────────────────────────────────────────────────┤
│ 1. Keycloak ve que el realm YA EXISTE                       │
│ 2. Realm seeding es IDEMPOTENTE                             │
│ 3. NO sobrescribe datos existentes                          │
│ 4. Ignora las URLs correctas de values.yaml                │
└─────────────────────────────────────────────────────────────┘
                          ↓
                   ⚠️ URLs incorrectas permanecen en BD
```

### Init-Container Problemático

**Imagen por defecto:**
```yaml
docker.io/tractusx/umbrella-init-container:2.3.0-init
```

**Contenido del init-container:**
```
/tmp/realm-config/
├── CX-Central-realm.json      ← Contiene URLs hardcodeadas
├── CX-Central-users-0.json
├── CX-Operator-realm.json     ← Contiene URLs hardcodeadas
└── master-realm.json
```

**Ejemplo de contenido problemático** (`CX-Central-realm.json`):

```json
{
  "clients": [
    {
      "clientId": "Cl2-CX-Portal",
      "rootUrl": "http://portal.tx.test/home",      // ❌ HARDCODEADO
      "redirectUris": [
        "http://portal.tx.test/*"                   // ❌ HARDCODEADO
      ]
    },
    {
      "clientId": "Cl1-CX-Registration",
      "redirectUris": [
        "http://portal.tx.test/*"                   // ❌ HARDCODEADO
      ]
    }
  ],
  "identityProviders": [
    {
      "alias": "CX-Operator",
      "config": {
        "tokenUrl": "http://sharedidp.tx.test/auth/...",        // ❌ HARDCODEADO
        "authorizationUrl": "http://sharedidp.tx.test/auth/..." // ❌ HARDCODEADO
      }
    }
  ]
}
```

### ¿Por qué el Realm Seeding no lo corrige?

**Realm Seeding es IDEMPOTENTE:**

```yaml
# Tu values.yaml tiene URLs correctas:
centralidp:
  keycloak:
    realmSeeding:
      clients:
        portal:
          rootUrl: "http://portal.51.178.94.25.nip.io/home"  # ✅ CORRECTO
          redirects:
            - "http://portal.51.178.94.25.nip.io/*"          # ✅ CORRECTO
```

**Pero:**
- ✅ Si el realm NO existe → crea todo con tus valores (correcto)
- ❌ Si el realm YA existe → NO actualiza valores existentes
- ❌ Init-container crea el realm PRIMERO → Realm seeding no actualiza

**Documentación oficial:**
> "El realm-seeding en Keycloak es IDEMPOTENTE, lo que significa que NO sobrescribe configuraciones existentes."

## 7. Soluciones Disponibles

### Solución 1: Deshabilitar el Init-Container ⭐ RECOMENDADA

**Implementación:**

Añadir a `values-ovh-hosts.yaml` o archivo similar:

```yaml
centralidp:
  keycloak:
    realmSeeding:
      initContainer:
        image:
          name: ""  # ← Deshabilita el init-container
      # ... resto de configuración realm seeding
      clients:
        portal:
          rootUrl: "http://portal.51.178.94.25.nip.io/home"
          redirects:
            - "http://portal.51.178.94.25.nip.io/*"

sharedidp:
  keycloak:
    realmSeeding:
      initContainer:
        image:
          name: ""  # ← Deshabilita el init-container
      # ... resto de configuración realm seeding
      realms:
        cxOperator:
          clients:
            central:
              redirects:
                - "http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/CX-Operator/endpoint/*"
```

**Ventajas:**
- ✅ **Simple:** Solo una línea por IdP (`name: ""`)
- ✅ **Efectivo:** Las URLs del values.yaml se aplican desde el inicio
- ✅ **Sin scripts:** No necesitas ejecutar fix-keycloak-urls.sh
- ✅ **Flexible:** Funciona con cualquier IP o dominio
- ✅ **Mantenible:** Cambios centralizados en values.yaml

**Limitación:**
- ⚠️ Pierdes configuración avanzada del init-container (si existe)
- ⚠️ Debes asegurarte de que el realm seeding tiene toda la config necesaria

**Proceso de despliegue limpio:**

```bash
# 1. Eliminar release anterior (si existe)
helm uninstall portal -n portal

# 2. Eliminar PVCs
kubectl delete pvc -n portal --all

# 3. Desplegar con init-container deshabilitado
helm install portal . \
  -f values-adopter-portal.yaml \
  -f values-hosts.yaml \
  -n portal --create-namespace

# 4. ✅ Las URLs correctas se aplican desde el inicio
# 5. ✅ No se necesita ejecutar fix-keycloak-urls.sh
```

---

### Solución 2: Usar Script Post-Despliegue (Método Actual)

**Descripción:** Mantener el init-container y ejecutar `fix-keycloak-urls.sh` después de cada despliegue.

**Script:** `/charts/umbrella/fix-keycloak-urls.sh`

**Uso:**
```bash
# Después del despliegue
export EXTERNAL_IP="51.178.94.25"
export DNS_SUFFIX="nip.io"
./fix-keycloak-urls.sh
```

**Ventajas:**
- ✅ Mantiene toda la configuración del init-container
- ✅ Ya lo tienes implementado y funcionando
- ✅ No requiere modificar helm charts

**Desventajas:**
- ❌ Paso manual adicional después de cada despliegue
- ❌ Ventana de tiempo con URLs incorrectas
- ❌ Propenso a olvidos
- ❌ Requiere acceso a kubectl y permisos de ejecución

---

### Solución 3: Imagen Custom del Init-Container

**Descripción:** Crear una imagen custom del init-container con templates dinámicos.

**Documentación:** `/init-container/EXPLICACION-IMAGEN-PERSONALIZADA.md`

**Implementación:**

```bash
# 1. Crear script de generación de JSONs
cd init-container/
./generate-realm-config.sh 51.178.94.25 nip.io

# 2. Construir imagen custom
docker build -t xmendialdua/catena-x-init:v2 .

# 3. Push a registry
docker push xmendialdua/catena-x-init:v2

# 4. Usar en values.yaml
centralidp:
  keycloak:
    realmSeeding:
      initContainer:
        image:
          name: "docker.io/xmendialdua/catena-x-init:v2"
```

**Ventajas:**
- ✅ Mantiene configuración completa del init-container
- ✅ URLs correctas desde el inicio
- ✅ Sin scripts post-despliegue
- ✅ Reutilizable en múltiples despliegues

**Desventajas:**
- ⚠️ Requiere construir y mantener imagen custom
- ⚠️ Requiere registry de Docker (Docker Hub, etc.)
- ⚠️ Más complejo de mantener
- ⚠️ Nueva imagen por cada cambio de IP (o usar plantillas + ConfigMap)

---

### Solución 4: ConfigMap con JSONs Generados

**Descripción:** Generar JSONs dinámicamente y montarlos como ConfigMap.

**Implementación:**

```bash
# 1. Generar JSONs con script
./generate-keycloak-realms.sh 51.178.94.25 nip.io

# 2. Crear ConfigMap
kubectl create configmap centralidp-realm-config \
  --from-file=./generated-realms/ \
  -n portal

# 3. Configurar en values.yaml para montar el ConfigMap
centralidp:
  keycloak:
    realmSeeding:
      initContainer:
        volumes:
          - name: realm-config
            configMap:
              name: centralidp-realm-config
```

**Ventajas:**
- ✅ No requiere imagen custom
- ✅ Cambios rápidos con kubectl apply
- ✅ URLs correctas desde el inicio

**Desventajas:**
- ⚠️ Requiere modificar templates del helm chart
- ⚠️ Más complejo de implementar
- ⚠️ Necesitas generar JSONs cada vez que cambias IP

## 📝 Notas Adicionales

### Idempotencia del Realm Seeding

Como se documenta en varios archivos del proyecto:

> "El realm-seeding en Keycloak es IDEMPOTENTE, lo que significa:
> - ✅ Puedes ejecutarlo en cualquier momento
> - ✅ NO elimina partners existentes
> - ✅ Solo añade lo que falta
> - ❌ NO sobrescribe configuraciones existentes"

Esta es la razón clave por la que el init-container causa problemas: una vez que importa los JSONs con `*.tx.test`, el realm seeding posterior no puede corregir esos valores.

### Servicios DNS Wildcard Disponibles

Para despliegues de desarrollo/testing:

| Servicio | Formato | Ejemplo |
|----------|---------|---------|
| **nip.io** | `<host>.<ip>.nip.io` | `portal.51.178.94.25.nip.io` |
| **sslip.io** | `<host>.<ip>.sslip.io` | `portal.51-178-94-25.sslip.io` |
| **traefik.me** | `<ip>.traefik.me` | `51-178-94-25.traefik.me` |

**Recomendación:** Usar **nip.io** por su simplicidad y fiabilidad.
