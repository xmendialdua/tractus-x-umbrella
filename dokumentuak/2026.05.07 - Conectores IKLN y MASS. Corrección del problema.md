# Corrección del problema de conectores IKLN y MASS

**Fecha:** 07 de Mayo de 2026

## Contexto del problema

Este documento describe el proceso para corregir el error que se produce cuando desde el conector de IKLN se trata de acceder al catálogo del conector de MASS.

### Error observado

Al consultar el catálogo de MASS desde IKLN, se produce el siguiente error:

```
[07:53:41] 🔍 Consultando catálogo de MASS desde IKLN...
[07:53:41] Counter Party: BPNL00000000MASS
[07:53:41] DSP URL: https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp
[07:53:43] ❌ Error: Server error '502 Bad Gateway' for url 'https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request'
For more information check: https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/502
```

### Estado del sistema

La instalación Helm para el conector de IKLN-EDC está en estado **FAILED**.

### 2. Diagnóstico del problema

Después de la verificación exhaustiva, encontramos:

1. **Release de Helm en estado `failed`**: Probablemente debido a un timeout durante el último despliegue (revisión 17), pero todos los recursos se desplegaron correctamente.

2. **Pods funcionando correctamente**: Todos los pods están en estado Running y los logs no muestran errores.

3. **Ingress respondiendo**: El ingress está accesible y responde correctamente.

4. **Error 502 temporal**: El error reportado en el mensaje inicial probablemente fue temporal, posiblemente durante un reinicio de pod o durante el despliegue fallido.

### 3. Solución propuesta

Para resolver el estado `failed` de la release de Helm y asegurar que el conector funcione correctamente:

#### Preparación: Optimización de recursos

**Problema identificado:** El cluster está al 99% de utilización de CPU requests, lo que causaba que los pods quedaran en estado `pending` durante despliegues anteriores.

**Estado del cluster:**
```bash
kubectl top nodes
```
```
NAME                             CPU(cores)   CPU(%)   MEMORY(bytes)   MEMORY(%)
tractus-x-umbrella-node-2d15eb   467m         12%      4852Mi          35%      
tractus-x-umbrella-node-980643   214m         5%       4165Mi          30%
```

**Recursos asignados:**
- Nodo 1: CPU requests 3824m (99%), Limits 9100m (237%)
- Nodo 2: CPU requests 3782m (98%), Limits 11060m (288%)

**Solución aplicada:** Reducir los recursos configurados en el values-ikln-connector.yaml:

```yaml
# Control plane - Reducido de requests: 100m/256Mi y limits: 1500m/1Gi
resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 50m
    memory: 128Mi

# Data plane - Reducido de requests: 100m/256Mi y limits: 1500m/1Gi
resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 50m
    memory: 128Mi

# PostgreSQL - Reducido de requests: 100m/128Mi
primary:
  resources:
    limits:
      cpu: 150m
      memory: 192Mi
      ephemeral-storage: 1Gi
    requests:
      cpu: 50m
      memory: 96Mi
      ephemeral-storage: 50Mi
```

**Ahorro de CPU requests:** 100m → 50m por pod = 50m x 3 pods = **150m liberados**

✅ Esto proporciona margen suficiente para que el upgrade funcione sin pods pending.

#### Opción 1: Upgrade de la release (Recomendado)

Hacer un upgrade de la release con los valores actuales para marcarla como `deployed`:

```bash
helm upgrade ikln-edc charts/dataspace-connector-bundle \
  --namespace umbrella \
  --values charts/dataspace-connector-bundle/values-ikln-connector.yaml \
  --timeout 10m
```

Este comando:
- Mantiene todos los recursos existentes
- Actualiza el estado de la release de `failed` a `deployed`
- Aplica los nuevos límites de recursos optimizados
- No causa downtime significativo

#### Opción 2: Rollback (Si se necesita volver a una versión anterior)

```bash

```

Dado que los pods están funcionando correctamente, podemos simplemente probar la conectividad entre IKLN y MASS sin modificar nada.
