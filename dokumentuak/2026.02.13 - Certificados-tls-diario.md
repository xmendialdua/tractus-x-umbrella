# Diario de resolución de problemas de certificados TLS

**Fecha:** 2026-02-13

## Contexto
- Proyecto desplegado en OVH con IP pública: 51.178.94.25.nip.io
- Uso de conectores EDC (IKLN y MASS) con endpoints expuestos en subdominios nip.io
- Necesidad de obtener certificados TLS válidos para eliminar advertencias SSL y evitar el uso de `-k` en curl

## Acciones realizadas

### 1. Revisión de scripts existentes
- Se revisó `create-connector-tls-certs-self.sh`: genera certificados auto-firmados para los conectores, válidos solo para desarrollo/testing.
- Se revisó `get-new-certs.bash`: automatiza la obtención de certificados Let's Encrypt para subdominios, deshabilitando temporalmente el ingress de Kubernetes y copiando los certificados generados.
- Se revisó `create-kubernetes-certificate-secrets.bash`: importa los certificados obtenidos como secretos TLS en Kubernetes.

### 2. Intento de obtención de certificados Let's Encrypt
- Se intentó ejecutar `./get-new-certs.bash edc-ikln-control`.
- Primer error: `sudo: certbot: command not found`. Se identificó que certbot no estaba instalado.
- Solución propuesta: instalar certbot con `sudo apt update && sudo apt install certbot`.

### 3. Límite de certificados en nip.io
- Segundo error: "too many certificates (100000) already issued for 'nip.io' in the last 168h0m0s".
- Se identificó que Let's Encrypt ha alcanzado el límite global de certificados para nip.io, impidiendo la emisión de nuevos certificados para cualquier usuario.
- Opciones propuestas:
  - Esperar a que se reinicie el contador de rate limit.
  - Usar otro dominio dinámico (xip.io, sslip.io) o registrar un dominio propio.
  - Continuar temporalmente con certificados auto-firmados.

### 4. Explicación de nip.io
- nip.io es un servicio DNS wildcard que permite mapear subdominios a IPs públicas automáticamente, facilitando el acceso a servicios en la nube sin registrar dominios propios.
- Limitación: el uso masivo provoca restricciones globales en la emisión de certificados por parte de Let's Encrypt.

### 5. Decisión: Desplegar cert-manager con CA interna
- Dado el límite de Let's Encrypt para nip.io, se decidió implementar cert-manager con una CA interna.
- Esta solución permite emitir certificados válidos firmados por una CA propia, eliminando advertencias SSL en clientes que confíen en la CA raíz.
- Es adecuada para entornos controlados donde se puede distribuir el certificado raíz a todos los clientes.

## Proceso de despliegue completado

### 6. Instalación de cert-manager en Kubernetes
```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.0/cert-manager.yaml
```

Verificación:
```bash
kubectl get pods -n cert-manager
```

Resultado: 3 pods en estado Running (cert-manager, cert-manager-webhook, cert-manager-cainjector).

### 7. Configuración de ClusterIssuers y CA raíz
Archivos creados/modificados:
- `crts/cluster-issuer-ovh.yaml`: Define dos ClusterIssuers:
  - `selfsigned-issuer`: Para crear el certificado raíz auto-firmado.
  - `my-ca-issuer`: Para emitir certificados firmados por la CA raíz.
- Certificate `my-selfsigned-ca`: Genera el certificado raíz con CN=51.178.94.25.nip.io y lo almacena en el secret `root-secret`.

Comando aplicado:
```bash
kubectl apply -f crts/cluster-issuer-ovh.yaml
```

**Problema encontrado:** El ClusterIssuer `my-ca-issuer` estaba en estado False porque no encontraba el secret `root-secret`.

**Solución:** Los ClusterIssuers buscan secrets en el namespace `cert-manager` por defecto. Se copió el secret:
```bash
kubectl get secret root-secret -n umbrella -o yaml | sed 's/namespace: umbrella/namespace: cert-manager/' | kubectl apply -f -
```

Resultado: Ambos ClusterIssuers en estado Ready=True.

### 8. Creación de certificados para los endpoints EDC
Archivo creado: `crts/certificates-edc.yaml`

Certificados generados para el namespace `umbrella` (donde están desplegados ambos conectores):
- `edc-mass-control-tls` → edc-mass-control.51.178.94.25.nip.io
- `edc-mass-data-tls` → edc-mass-data.51.178.94.25.nip.io
- `edc-ikln-control-tls` → edc-ikln-control.51.178.94.25.nip.io
- `edc-ikln-data-tls` → edc-ikln-data.51.178.94.25.nip.io

Comando aplicado:
```bash
kubectl apply -f crts/certificates-edc.yaml
```

Verificación:
```bash
kubectl get certificate -n umbrella
kubectl get secrets -n umbrella | grep tls
```

Resultado: Los 4 certificados en estado Ready=True y sus secrets TLS creados automáticamente.

### 9. Configuración de Ingress en los conectores
Los archivos values ya tenían configurados correctamente los secretNames:
- `charts/dataspace-connector-bundle/values-ikln-connector.yaml`
- `charts/dataspace-connector-bundle/values-mass-connector.yaml`

Configuración TLS en ambos valores:
```yaml
tls:
  enabled: true
  secretName: "edc-[conector]-[plano]-tls"
```

**Nota importante:** No se añadió la anotación `cert-manager.io/cluster-issuer: my-ca-issuer` en los ingresses. 
⚠️ **IMPORTANTE:** Agregar esta anotación permitiría la renovación automática de certificados por cert-manager. Sin ella, los certificados funcionan pero no se renuevan automáticamente.

### 10. Redespliegue de conectores
Se ejecutaron los scripts de despliegue para aplicar los cambios:
```bash
./deploy-mass-connector.sh
./deploy-ikln-connector.sh
```

### 11. Verificación de certificados TLS
```bash
# Ver detalles del certificado servido
echo | openssl s_client -servername edc-mass-control.51.178.94.25.nip.io -connect edc-mass-control.51.178.94.25.nip.io:443 2>/dev/null | openssl x509 -noout -text | grep -A 2 "Subject:"
```

Resultado:
```
Subject: O = Tractus-X, CN = edc-mass-control.51.178.94.25.nip.io
```

Prueba con `-k`:
```bash
curl -k https://edc-mass-control.51.178.94.25.nip.io/api/check/health
```
✅ Funciona correctamente.

Prueba sin `-k`:
```bash
curl https://edc-mass-control.51.178.94.25.nip.io/api/check/health
```
❌ Falla con "SSL certificate problem: unable to get local issuer certificate" (esperado, CA no instalada).

### 12. Instalación del certificado raíz en el sistema local
```bash
# Exportar el certificado raíz
kubectl get secret root-secret -n umbrella -o jsonpath='{.data.ca\.crt}' | base64 -d > ~/tractus-x-ca-root.crt

# Verificar el certificado exportado
openssl x509 -in ~/tractus-x-ca-root.crt -text -noout | grep -A 2 "Subject:"
```

Resultado:
```
Subject: C = DE, ST = Some-State, O = CX, CN = 51.178.94.25.nip.io
```

Instalación en el sistema Linux:
```bash
# Copiar al directorio de CAs de confianza
sudo cp ~/tractus-x-ca-root.crt /usr/local/share/ca-certificates/tractus-x-ca-root.crt

# Actualizar almacén de certificados
sudo update-ca-certificates
```

Resultado: 1 certificado añadido.

### 13. Verificación final
```bash
curl https://edc-mass-control.51.178.94.25.nip.io/api/check/health
```

Resultado:
```json
{"componentResults":[{"failure":null,"component":"Hashicorp Vault Health","isHealthy":true},{"failure":null,"component":"BaseRuntime","isHealthy":true}],"isSystemHealthy":true}
```

✅ **Funciona sin `-k` y sin advertencias SSL.**

## Conclusiones y recomendaciones

### ✅ Logros:
1. Cert-manager desplegado y funcional en el clúster.
2. CA interna creada y certificados TLS emitidos para todos los endpoints EDC.
3. HTTPS funcional sin advertencias SSL en clientes con el CA raíz instalado.
4. No se requiere el flag `-k` en curl después de instalar el CA raíz.

### ⚠️ Limitaciones:
1. Los certificados solo son confiables en sistemas que tengan instalado el CA raíz.
2. Para clientes externos (navegadores, APIs de terceros), seguirán viendo advertencias SSL a menos que instalen el CA raíz.
3. Sin la anotación `cert-manager.io/cluster-issuer` en los ingresses, los certificados no se renuevan automáticamente.

### 📋 Recomendaciones:
1. **Para renovación automática:** Añadir la anotación `cert-manager.io/cluster-issuer: my-ca-issuer` en los ingresses de los valores de Helm.
2. **Para producción abierta:** Considerar registrar un dominio propio y usar Let's Encrypt cuando el rate limit se reinicie.
3. **Distribución del CA raíz:** Proporcionar instrucciones claras para que otros usuarios instalen el CA raíz en sus sistemas.
4. **Monitoreo:** Configurar alertas para certificados próximos a expirar (aunque cert-manager renueva automáticamente si está correctamente anotado).

### 📝 Distribución del CA raíz a otros sistemas:

#### Linux:
```bash
sudo cp tractus-x-ca-root.crt /usr/local/share/ca-certificates/
sudo update-ca-certificates
```

#### Windows:
1. Doble clic en el archivo `.crt`
2. "Install Certificate" → "Local Machine"
3. "Place all certificates in the following store" → "Trusted Root Certification Authorities"

#### macOS:
```bash
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain tractus-x-ca-root.crt
```

#### Navegadores (si no usan el almacén del sistema):
- Firefox: Preferences → Privacy & Security → Certificates → View Certificates → Authorities → Import
