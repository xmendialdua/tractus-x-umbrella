## Contexto y Objetivo

### Situación Inicial

**Problema identificado:**
- Conectores EDC desplegados con HTTP (sin TLS)
- Conectores registrados directamente en base de datos (bypass del proceso normal)
- Conectores en estado PENDING, no se activan automáticamente
- Portal UI requiere HTTPS para registrar conectores

**Objetivo:**
Habilitar el registro de conectores a través del Portal UI siguiendo el proceso estándar que incluye:
1. Validación de URL HTTPS en frontend
2. Creación automática del proceso de Self-Description
3. Activación automática del conector (PENDING → ACTIVE)

### Componentes Involucrados

**Conectores EDC:**
- **MondragonAssembly (MASS)**
  - BPN: `BPNL00000000MASS`
  - Namespace: `mass-connector`
  - Control Plane: `edc-mass-control.51.178.94.25.nip.io`
  - Data Plane: `edc-mass-data.51.178.94.25.nip.io`

- **Ikerlan (IKLN)**
  - BPN: `BPNL00000002IKLN`
  - Namespace: `ikln-connector`
  - Control Plane: `edc-ikln-control.51.178.94.25.nip.io`
  - Data Plane: `edc-ikln-data.51.178.94.25.nip.io`

**Portal Catena-X:**
- Namespace: `portal`
- URL: `http://portal.51.178.94.25.nip.io`
- Backend: `http://portal-backend.51.178.94.25.nip.io`

### 📝 Proceso Normal de Registro

**Flujo estándar según código del Portal Backend:**

```
1. Usuario registra conector en Portal UI
   ↓
2. Frontend valida URL (debe ser HTTPS)
   ↓
3. Backend crea conector en estado PENDING
   ↓
4. Backend llama automáticamente a sdFactoryBusinessLogic.RegisterConnectorAsync()
   ↓
5. Se crea proceso SELF_DESCRIPTION_CREATION
   ↓
6. Process worker ejecuta:
   - SELF_DESCRIPTION_CONNECTOR_CREATION
   - AWAIT_SELF_DESCRIPTION_CONNECTOR_RESPONSE
   ↓
7. SD Factory responde con documento
   ↓
8. Conector actualizado a estado ACTIVE
```

**Conclusión:** Necesitamos seguir el proceso estándar, que requiere HTTPS.

## Decisión Técnica: TLS Solo en Conectores

### Pregunta Clave

> "¿Puedo habilitar HTTPS solo en los conectores pero mantener el Portal en HTTP?"

### Respuesta: ✅ SÍ, es válido

**Razones técnicas:**

1. **Separación de componentes:**
   - Conectores: namespaces `mass-connector` y `ikln-connector`
   - Portal: namespace `portal`
   - No hay dependencia técnica entre protocolos

2. **Validación del Portal:**
   - Frontend valida URL del conector (debe ser `https://`)
   - Backend puede comunicarse con endpoints HTTPS externos
   - Portal puede estar en HTTP mientras conectores están en HTTPS

3. **Simplicidad para POC:**
   - Habilitar TLS en Portal requiere más configuración
   - Solo necesitamos TLS en conectores para cumplir validación del Portal

### Arquitectura Resultante

## Resolución de Problemas

### Problema 1: Error "Location SP does not exist"

**Síntoma:**

```
POST /api/administration/connectors/managed
400 Bad Request
{
  "title": "Connector Argument Validation",
  "errors": {
    "location": ["Location SP does not exist"]
  }
}
```

**Causa:**

Código de país inválido. Portal valida contra tabla `portal.countries` que usa **códigos ISO 3166-1 alpha-2**.

**Solución:**

1. **Verificar códigos válidos:**

```bash
kubectl exec -n portal portal-portal-backend-postgresql-0 -- \
  env PGPASSWORD=dbpasswordportal psql -U portal -d postgres -c \
  "SELECT alpha2code, country_name_en FROM portal.countries WHERE country_name_en LIKE '%Spa%';"
```

Output:
```
 alpha2code | country_name_en 
------------+-----------------
 ES         | Spain
```

2. **Usar código correcto:**
   - ❌ SP
   - ✅ **ES**

3. **Volver a registrar** con Location = ES

### Problema 2: Conector queda en PENDING permanentemente

**Síntoma:**

Conector aparece como PENDING después de 10+ minutos.

**Diagnóstico:**

```bash
# Ver proceso de self-description

   FROM portal.processes p 
   JOIN portal.process_steps ps ON p.id = ps.process_id 
   WHERE p.process_type_id = 10 
   ORDER BY p.date_created DESC LIMIT 3;"
```

**Buscar:**
- `process_step_status_id = 3` (FAILED)
- `message` con detalles del error

```bash

kubectl rollout status deployment -n portal portal-selfdescription
```

**B. Process worker no se ejecuta**

```bash
# Ver cronjobs
kubectl get cronjobs -n portal | grep process

# Ver ejecuciones recientes
kubectl get jobs -n portal | grep process | head -5

# Ver logs del último job
LAST_JOB=$(kubectl get jobs -n portal -l app=portal-processes-worker --sort-by=.metadata.creationTimestamp -o name | tail -1)
```

**Solución:**
Forzar ejecución manual:

```bash
kubectl create job -n portal manual-process-worker-$(date +%s) \
```

Verificar que el DNS funciona y el ingress está accesible.

## Resolución de Problemas

### Error Inicial: "Location SP does not exist"

#### Síntoma

Al registrar el conector, el Portal respondía:
```
Something went wrong
Something went wrong. Please try it later again or contact your administrator.
```

#### Diagnóstico

**Logs del Administration Service:**

```bash
kubectl logs -n portal portal-administration-service-xxx --tail=50 --since=2m
```

**Error encontrado:**

```json
{
  "Level": "Information",
  "Message": "GeneralErrorHandler caught \"ControllerArgumentException\" with errorId: \"a94b0ebe-8575-4454-bcb7-ad964a0e5855\" resulting in response status code 400, message '\"Location SP does not exist\"'",
  "Exception": "Org.Eclipse.TractusX.Portal.Backend.Framework.ErrorHandling.ControllerArgumentException: CONNECTOR_ARGUMENT_LOCATION_NOT_EXIST\n   at Org.Eclipse.TractusX.Portal.Backend.Administration.Service.BusinessLogic.ConnectorsBusinessLogic.CheckLocationExists(String location) in /src/administration/Administration.Service/BusinessLogic/ConnectorsBusinessLogic.cs:line 194"
}
```

**Código que falla (ConnectorsBusinessLogic.cs:194):**

```csharp
private void CheckLocationExists(string location)
{
    if (!_portalRepositories.GetInstance<ICountryRepository>().CheckCountryExistsByAlpha2CodeAsync(location).Result)
    {
        throw ControllerArgumentException.Create(AdministrationConnectorErrors.CONNECTOR_ARGUMENT_LOCATION_NOT_EXIST, 
            new ErrorParameter[] { new("location", location) });
    }
}
```

#### Causa Raíz

- Usuario introdujo código de país: **"SP"** (Spain - incorrecto)
- Tabla `portal.countries` usa códigos ISO 3166-1 alpha-2
- Código correcto para España: **"ES"**

#### Solución

**Cambiar Location de "SP" a "ES"**

**Validación de códigos disponibles:**

```sql
SELECT alpha2code, country_name_de 
FROM portal.countries 
WHERE alpha2code IN ('SP', 'ES');
```

**Resultado:**
```
alpha2code | country_name_de
-----------+------------------
ES         | Spanien
```

✅ **"SP" no existe**, **"ES" es el código correcto**

#### Resultado

Al usar **"ES"** como Location:
- ✅ Validación pasada
- ✅ Conector creado exitosamente
- ✅ Proceso de SD iniciado
- ✅ Conector activado automáticamente
