# Factibilidad de Configuración TLS Mixta en Catena-X

**Fecha:** 2026-02-10  
**Sistema:** Tractus-X Umbrella - OVH Deployment  
**Pregunta:** ¿Es factible tener conectores con seguridad (HTTPS) y portal sin TLS (HTTP)?

---

## 📋 Resumen Ejecutivo

**Para DESARROLLO: ✅ SÍ, es completamente factible y NO tiene inconvenientes técnicos.**  
**Para PRODUCCIÓN: ⚠️ NO recomendable, aunque técnicamente funcional.**

---

## 🔍 Análisis de Factibilidad Técnica

### ✅ ES FACTIBLE porque:

1. **Servicios Independientes**
   - Portal y conectores EDC son componentes separados
   - No se comunican directamente en runtime normal
   - Cada uno tiene su propio ingress controller

2. **Comunicación Interna HTTP Cluster-Local**
   - Los servicios dentro del cluster se comunican via HTTP interno
   - Las URLs internas NO dependen del TLS del ingress externo
   - La configuración TLS del ingress NO afecta las comunicaciones inter-pod

3. **No Hay Dependencia de Seguridad Cruzada**
   - La configuración TLS de los conectores NO afecta al portal
   - La configuración TLS del portal NO afecta a los conectores
   - Son dominios diferentes con certificados independientes

## 🔬 Verificación de Inconvenientes Técnicos

### Análisis Exhaustivo

| Aspecto a Verificar | ¿Hay Problema? | Explicación Detallada |
|---------------------|----------------|----------------------|
| **Conectores → BDRS** | ❌ NO | URL interna: `http://bdrs-server.portal.svc.cluster.local:8082` - No usa ingress |
| **Conectores → dim-wallet-proxy** | ❌ NO | URL interna: `http://dim-wallet-proxy.portal.svc.cluster.local:8080` - Comunicación cluster-local |
| **Conectores → Keycloak** | ❌ NO | Keycloak usa servicio interno `centralidp.portal.svc.cluster.local:8080` |
| **Obtención de VCs** | ❌ NO | dim-wallet-proxy responde por HTTP interno independiente del ingress |
| **Contract Negotiation** | ❌ NO | Conectores se comunican entre sí via DSP (no involucra portal) |
| **Catalog Requests** | ❌ NO | Protocolo DSP directo entre conectores (MASS ↔ IKLN) |
| **Transfer Process** | ❌ NO | Data plane usa su propio ingress, independiente del portal |
| **Users Login Portal** | ⚠️ MENOR | Passwords viajan sin cifrar (solo relevante si hay tráfico externo malicioso) |
| **Configuración DNS** | ❌ NO | Dominios independientes: `portal.*.nip.io` vs `edc-mass-control.*.nip.io` |
| **Certificados SSL** | ❌ NO | Cada ingress maneja sus propios certificados |

**Resultado:** **CERO inconvenientes técnicos** para comunicación y funcionalidad.

## 🛡️ Análisis de Riesgos - Portal sin TLS

### Riesgos en Desarrollo (Bajo Impacto)

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| **Password sniffing** | BAJA* | Medio | *Solo si hay tráfico externo malicioso en red de desarrollo |
| **Session hijacking** | BAJA | Medio | Limitar acceso por IP/VPN |
| **MITM attacks** | MUY BAJA | Alto | Red OVH interna es confiable |
| **Credential leakage** | BAJA | Bajo | Usar passwords triviales en dev |

**Conclusión desarrollo:** Riesgo ACEPTABLE si:
- Entorno no expuesto públicamente
- Credentials de desarrollo (no producción)
- Red de desarrollo confiable

### Riesgos en Producción (Alto Impacto)

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| **Password sniffing** | ALTA | CRÍTICO | ❌ No mitigable - Requiere TLS |
| **Session hijacking** | ALTA | CRÍTICO | ❌ No mitigable - Requiere TLS |
| **MITM attacks** | MEDIA | CRÍTICO | ❌ No mitigable - Requiere TLS |
| **Compliance violations** | ALTA | CRÍTICO | Regulaciones requieren cifrado |
| **Reputational damage** | ALTA | CRÍTICO | Breach de portal = pérdida confianza |

**Conclusión producción:** Riesgo INACEPTABLE - TLS obligatorio.

## 🔧 Alternativas para Habilitar TLS en Conectores

### Alternativa 1: Certificados Self-Signed (Generación Automática)

**Descripción:**  
Kubernetes ingress-nginx puede generar certificados self-signed automáticamente cuando TLS está habilitado sin especificar un secret.

**Configuración:**
```yaml
# charts/values-mass-connector.yaml
tractusx-connector:
  controlplane:
    ingresses:
      - enabled: true
        hostname: "edc-mass-control.51.178.94.25.nip.io"
        tls:
          enabled: true
          secretName: ""  # ← Vacío = auto-genera self-signed
```

**Comando para aplicar:**
```bash
# Actualizar MASS connector
helm upgrade mass-edc tractusx-edc/tractusx-connector \
  -n mass-connector \
  -f charts/values-mass-connector.yaml

# Actualizar IKLN connector
helm upgrade ikln-edc tractusx-edc/tractusx-connector \
  -n ikln-connector \
  -f charts/values-ikln-connector.yaml
```

**Ventajas:**
- ✅ **Tiempo de implementación:** 5 minutos
- ✅ **Complejidad:** Muy baja
- ✅ **Instalaciones adicionales:** Ninguna
- ✅ **Funciona offline:** Sí
- ✅ **Renovación:** Manual (certificado válido 365 días)
- ✅ **Costo:** Gratis

**Desventajas:**
- ⚠️ Navegadores muestran advertencia "No seguro"
- ⚠️ Requiere `-k` en curl/Postman
- ⚠️ No válido para producción
- ⚠️ Cada pod genera su propio certificado (posibles inconsistencias)

**Validación:**
```bash
# Test conectividad HTTPS
curl -k https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp

# Ver detalles del certificado
openssl s_client -connect edc-mass-control.51.178.94.25.nip.io:443 -servername edc-mass-control.51.178.94.25.nip.io < /dev/null 2>/dev/null | openssl x509 -text -noout | grep -A2 "Validity"
```

**Viabilidad:** ✅ **ALTA** - Recomendado para desarrollo

### Alternativa 2: Let's Encrypt + cert-manager (Certificados Públicos Válidos)

**Descripción:**  
cert-manager automatiza la obtención y renovación de certificados de Let's Encrypt (certificados públicamente confiables y gratuitos).

**Pre-requisitos:**
- Dominio debe ser accesible desde Internet público
- Puerto 80 debe estar abierto para validación ACME HTTP-01
- DNS debe resolver correctamente

**Instalación de cert-manager:**
```bash
# 1. Agregar repo de Helm
helm repo add jetstack https://charts.jetstack.io
helm repo update

# 2. Instalar cert-manager con CRDs
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --version v1.13.3 \
  --set installCRDs=true

# 3. Verificar instalación
kubectl get pods -n cert-manager
# Debe mostrar: cert-manager, cert-manager-webhook, cert-manager-cainjector
```

**Configuración de Let's Encrypt ClusterIssuer:**
```yaml
# letsencrypt-prod-issuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # Servidor de producción de Let's Encrypt
    server: https://acme-v02.api.letsencrypt.org/directory
    
    # Email para notificaciones (renovaciones, expiraciones)
    email: admin@mondragonassembly.com
    
    # Secret donde se guardará la clave privada del account
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    
    # Solver para validación de dominio (HTTP-01)
    solvers:
    - http01:
        ingress:
          class: nginx  # Debe coincidir con tu ingress class
```

```bash
# Aplicar ClusterIssuer
kubectl apply -f letsencrypt-prod-issuer.yaml

# Verificar que está listo
kubectl get clusterissuer letsencrypt-prod
# Status debe ser: Ready=True
```

**Configuración de conectores:**
```yaml
# charts/values-mass-connector.yaml
tractusx-connector:
  controlplane:
    ingresses:
      - enabled: true
        hostname: "edc-mass-control.51.178.94.25.nip.io"
        className: "nginx"
        tls:
          enabled: true
          secretName: "edc-mass-tls"  # cert-manager lo creará
        annotations:
          # Anotación mágica: cert-manager detecta y solicita certificado
          cert-manager.io/cluster-issuer: "letsencrypt-prod"
```

**Proceso automático:**
```
Usuario: helm upgrade con valores actualizados
   ↓
Ingress creado con anotación cert-manager
   ↓
cert-manager detecta anotación
   ↓
Crea Certificate resource
   ↓
Crea Challenge (validación ACME)
   ↓
Let's Encrypt hace HTTP request a: http://edc-mass-control.51.178.94.25.nip.io/.well-known/acme-challenge/TOKEN
   ↓
cert-manager responde con challenge proof
   ↓
Let's Encrypt valida y emite certificado
   ↓
cert-manager guarda certificado en Secret "edc-mass-tls"
   ↓
Ingress usa el Secret para TLS
   ↓
Cada 60 días: cert-manager auto-renueva
```

**Troubleshooting:**
```bash
# Ver estado del Certificate
kubectl get certificate -n mass-connector

# Ver detalles de validación
kubectl describe certificate edc-mass-tls -n mass-connector

# Ver challenges (si hay problemas)
kubectl get challenges -n mass-connector

# Logs de cert-manager
kubectl logs -n cert-manager -l app=cert-manager -f
```

**Ventajas:**
- ✅ **Certificados públicamente confiables:** Navegadores no muestran advertencias
- ✅ **Renovación automática:** Cada 60-90 días sin intervención
- ✅ **Similar a producción:** Mismo proceso que en prod
- ✅ **Gratis:** Let's Encrypt es gratuito
- ✅ **No requiere `-k` en curl:** Certificados válidos

**Desventajas:**
- ⏱️ **Tiempo de implementación:** 20-30 minutos (instalación + configuración)
- 🔧 **Complejidad:** Media-alta
- 🌐 **Requiere acceso público:** Dominio debe ser alcanzable desde Internet
- 📝 **Debugging complejo:** Errores ACME pueden ser crípticos
- ⚠️ **Rate limits:** Let's Encrypt tiene límites (50 certs/semana por dominio)
- 🐛 **nip.io puede tener problemas:** Let's Encrypt a veces bloquea servicios DNS dinámicos

**Problemas potenciales con nip.io:**
```bash
# Let's Encrypt puede rechazar nip.io por:
1. Rate limiting (muchos usuarios de nip.io)
2. DNS propagation lenta
3. Shared domain abuse prevention

# Solución: Usar dominio real (*.mondragonassembly.com)
```

**Viabilidad:** ⚠️ **MEDIA** para nip.io, ✅ **ALTA** para dominio real

### Alternativa 3: Certificados Manuales (Pre-existentes o Comprados)

**Descripción:**  
Usar certificados que ya tienes (comprados a CA comercial, generados por PKI corporativa, etc.)

**Escenarios:**
1. Certificados comprados (DigiCert, GlobalSign, etc.)
2. Certificados de PKI corporativa interna
3. Certificados wildcard existentes

**Generación manual (si no los tienes):**
```bash
# 1. Generar clave privada
openssl genrsa -out edc-mass.key 2048

# 2. Generar Certificate Signing Request (CSR)
openssl req -new -key edc-mass.key -out edc-mass.csr \
  -subj "/CN=edc-mass-control.51.178.94.25.nip.io/O=Mondragon Assembly/C=ES"

# 3. Opción A: Auto-firmado (para testing)
openssl x509 -req -days 365 -in edc-mass.csr -signkey edc-mass.key -out edc-mass.crt

# 3. Opción B: Enviar CSR a CA comercial o PKI corporativa
# Recibirás: edc-mass.crt (certificado firmado)
```

**Crear Secret en Kubernetes:**
```bash
# Crear secret TLS con tus certificados
kubectl create secret tls edc-mass-tls \
  --cert=edc-mass.crt \
  --key=edc-mass.key \
  -n mass-connector

# Verificar secret creado
kubectl get secret edc-mass-tls -n mass-connector
kubectl describe secret edc-mass-tls -n mass-connector
```

**Configuración de conectores:**
```yaml
# charts/values-mass-connector.yaml
tractusx-connector:
  controlplane:
    ingresses:
      - enabled: true
        hostname: "edc-mass-control.51.178.94.25.nip.io"
        tls:
          enabled: true
          secretName: "edc-mass-tls"  # Referencia al secret manual
        # NO incluir anotación de cert-manager
```

**Renovación:**
```bash
# Cuando el certificado esté por expirar (ej: cada año):

# 1. Generar nuevo certificado (repetir proceso)
# 2. Actualizar secret
kubectl create secret tls edc-mass-tls \
  --cert=edc-mass-new.crt \
  --key=edc-mass-new.key \
  --dry-run=client -o yaml | kubectl apply -f -

# 3. Reiniciar ingress (opcional, suele detectar cambios)
kubectl rollout restart deployment ingress-nginx-controller -n ingress-nginx
```

**Ventajas:**
- ✅ **Control total:** Decides qué CA usar, validez, etc.
- ✅ **Funciona offline:** No depende de validación externa
- ✅ **Certificados wildcard:** Un cert para todos los subdominios
- ✅ **Sin rate limits:** No hay restricciones de Let's Encrypt
- ✅ **PKI corporativa:** Puede integrarse con infraestructura existente

**Desventajas:**
- ⏱️ **Tiempo:** 10-15 minutos (si ya tienes certs), días (si hay que comprarlos)
- 💰 **Costo:** Variable (gratis con PKI interna, €50-500/año comercial)
- 🔄 **Renovación manual:** Hay que recordar renovar antes de expiración
- 🔧 **Gestión de secretos:** Debes guardar claves privadas de forma segura
- ⚠️ **Self-signed no confiable:** Si autofirmas, navegadores dan advertencia

**Viabilidad:** ✅ **ALTA** - Especialmente si ya tienes PKI corporativa

### Alternativa 4: Cloudflare Tunnel (Proxy Externo)

**Descripción:**  
Usar Cloudflare como proxy que maneja TLS, conectando con tu cluster via túnel.

**Arquitectura:**
```
Internet → Cloudflare (HTTPS) → Cloudflare Tunnel → Cluster (HTTP)
```

**Configuración básica:**
```bash
# 1. Instalar cloudflared en cluster
kubectl apply -f https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared.yaml

# 2. Crear túnel en Cloudflare dashboard
# 3. Configurar rutas
edc-mass-control.tudominio.com → http://mass-edc-tractusx-connector-controlplane:8084
```

**Ventajas:**
- ✅ Cloudflare maneja certificados
- ✅ CDN + DDoS protection incluido
- ✅ No modifica configuración interna del cluster

**Desventajas:**
- ⚠️ Dependencia de servicio externo
- ⚠️ Latencia adicional
- ⚠️ Requiere dominio en Cloudflare

**Viabilidad:** ⚠️ **MEDIA** - Solo si ya usas Cloudflare

## 🎓 Lecciones Aprendidas

1. **Comunicación interna vs externa:** El TLS del ingress NO afecta la comunicación cluster-local (siempre HTTP)

2. **Independencia de componentes:** Portal y conectores pueden tener configuraciones TLS diferentes sin problemas técnicos

3. **Self-signed es suficiente para desarrollo:** No necesitas complejidad de cert-manager para validar funcionalidad

4. **nip.io tiene limitaciones con Let's Encrypt:** Puede haber rate limiting, mejor usar dominio real para pre-prod/prod

5. **Gradualidad es válida:** Puedes habilitar TLS en conectores primero y portal después (o viceversa)
