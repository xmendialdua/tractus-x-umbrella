# Post-Upgrade Fixes - Portal Catena-X

**Fecha:** 5 de Febrero de 2026  
**Namespace:** portal  
**Cluster:** OVH (51.178.94.25.nip.io)

## Resumen

Después de cada `helm upgrade` del Portal de Catena-X, es necesario aplicar correcciones manuales para resolver problemas de configuración que no se pueden establecer mediante Helm values.

---

## Problema 1: Redirect URI incorrecto en realms de SharedIDP

### Síntoma
Al seleccionar un tenant (idp1, idp2) en el portal, aparece el error:
```
Invalid parameter: redirect_uri
```

### Causa
El cliente `central-idp` en cada realm de SharedIDP se crea con un `redirectUri` genérico para el broker "CX-Operator", pero cuando se usa un tenant específico, el broker se llama igual que el realm (idp1, idp2).

**URI incorrecto creado por defecto:**
```
http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/CX-Operator/endpoint/*
```

**URI correcto necesario:**
```
http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/idp1/endpoint/*
http://centralidp.51.178.94.25.nip.io/auth/realms/CX-Central/broker/idp2/endpoint/*
```

### Solución

Ejecutar el script `fix-centralidp-redirect-uri.sh`:

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella
bash fix-centralidp-redirect-uri.sh
```

El script:
1. Se conecta al pod de SharedIDP (`portal-sharedidp-0`)
2. Para cada realm (idp1, idp2), actualiza el cliente `central-idp`
3. Establece el `redirectUri` correcto con el nombre del broker correspondiente

## Problema 2: Error de cookies por requisito HTTPS

### Síntoma
Después de autenticarse correctamente, aparece el error:
```
We are sorry...
Cookie not found. Please make sure cookies are enabled in your browser.
```

### Causa
Los realms de Keycloak (tanto CentralIDP como SharedIDP) tienen la configuración `sslRequired` establecida en valores que requieren HTTPS, pero el cluster está configurado para usar HTTP.

Esto hace que las cookies de sesión no se puedan establecer correctamente porque Keycloak las marca como "secure" (solo HTTPS).

### Solución

#### Paso 1: Corregir SharedIDP (realms idp1, idp2)

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella

# Corregir idp1
bash fix-realm-https.sh idp1

# Corregir idp2
bash fix-realm-https.sh idp2
```

#### Paso 2: Corregir CentralIDP (realm CX-Central)

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
bash fix-centralidp-https.sh
```

## Problema 3: Partner Network URLs incorrectas en base de datos

### Síntoma
La aplicación Partner Network no es accesible o muestra URLs incorrectas.

### Causa
Las URLs almacenadas en la base de datos del portal usan valores por defecto de `tx.test` en lugar del dominio real `51.178.94.25.nip.io`.

### Solución

Ejecutar el script `unblock-application-after-bpn.sh`:

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella
bash unblock-application-after-bpn.sh
```

El script actualiza las URLs en la base de datos del portal para usar el dominio correcto.

## Notas técnicas

### ¿Por qué ocurren estos problemas?

1. **Redirect URIs:** El realm seeding de Catena-X crea clientes con configuración genérica que asume el nombre del broker "CX-Operator". Los realms de partners (idp1, idp2) necesitan sus propios redirect URIs.

2. **HTTPS Requirement:** Keycloak por defecto asume despliegues en producción con HTTPS. En entornos de desarrollo/test con HTTP, esto causa problemas con cookies de sesión que se marcan como "secure".

3. **URLs en DB:** Los charts de Catena-X usan valores por defecto de `tx.test` que deben actualizarse para el dominio real del cluster.

### ¿Por qué no se pueden corregir con Helm values?

- **Redirect URIs y SSL:** Son configuraciones de Keycloak que se almacenan en su base de datos interna durante el realm-seeding. Los values de Helm controlan el deployment, pero no modifican configuraciones existentes en la DB de Keycloak.

- **URLs en Portal DB:** Son datos insertados por jobs de inicialización que usan valores del momento del primer despliegue.

### Persistencia de las correcciones

Las correcciones son **persistentes** mientras no se eliminen las bases de datos:
- PostgreSQL de CentralIDP (`portal-centralidp-postgresql`)
- PostgreSQL de SharedIDP (`portal-sharedidp-postgresql`)
- PostgreSQL de Portal (`portal-postgresql`)

Un `helm upgrade` **NO** elimina estas bases de datos si tienen persistencia habilitada, por lo que las correcciones se mantienen.

Sin embargo, si se ejecutan nuevos jobs de seeding (cambio de REVISION mayor o re-seeding forzado), será necesario volver a aplicar las correcciones.

## Verificación del estado actual

Para verificar si las correcciones ya están aplicadas:

### Verificar Redirect URIs
```bash
kubectl exec -n portal portal-sharedidp-0 -- bash -c \
  "cd /tmp && /opt/bitnami/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080/auth --realm master \
  --user admin --password \$(cat /opt/bitnami/keycloak/conf/admin-password) \
  --config /tmp/kcadm.config && \
  /opt/bitnami/keycloak/bin/kcadm.sh get clients -r idp1 \
  --config /tmp/kcadm.config -q clientId=central-idp" | \
  grep -A 5 redirectUris
```

### Verificar SSL Requirement
```bash
# SharedIDP
curl -s "http://sharedidp.51.178.94.25.nip.io/auth/admin/realms/idp1" \
  -H "Authorization: Bearer <TOKEN>" | jq .sslRequired

# CentralIDP
curl -s "http://centralidp.51.178.94.25.nip.io/auth/admin/realms/CX-Central" \
  -H "Authorization: Bearer <TOKEN>" | jq .sslRequired
```

Ambos deben devolver `"none"` o `"NONE"`.
