## 2. Problemas Encontrados y Soluciones

### 2.1 Problema #1: Vault Secrets Faltantes

**Síntoma:**
```bash
curl -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request"
# Error: "Unable to obtain credentials: Failure in DID resolution: 
# Failed to fetch client secret from the vault with alias: edc-wallet-secret"
```

**Log del controlplane:**
```
[Hashicorp Vault] Secret not found
DIM Token expired, need to refresh
```

**Diagnóstico:**
- El conector intentaba obtener `edc-wallet-secret` del Vault para autenticarse con DIM Wallet
- El Vault estaba completamente vacío (sin secrets)
- Verificamos con: `kubectl exec -n ikln-connector ikln-edc-vault-0 -- vault kv list secret`
  - Resultado: `No value found at secret/metadata`

**Causa Raíz:**
Los archivos de configuración usados (`values-ikln-connector.yaml` y `values-mass-connector.yaml`) **no incluyen la sección `secrets:`** necesaria para que el chart de Helm cree automáticamente los secrets en el Vault durante el despliegue.

Comparación de formatos:
```yaml
# Archivo FULL (con sección secrets) - NO USADO
ikerlan-connector-1:
  enabled: true
  secrets:
    edc-wallet-secret: changeme  # <-- Define el valor del secret
  tractusx-connector:
    iatp:
      sts:
        oauth:
          client:
            secret_alias: edc-wallet-secret  # <-- Referencia al secret

# Archivo actual (sin sección secrets) - EN USO
tractusx-connector:
  iatp:
    sts:
      oauth:
        client:
          secret_alias: edc-wallet-secret  # <-- Solo referencia, sin definición
```

**Solución Implementada:**
Creación manual de todos los secrets necesarios en ambos Vaults:

```bash
# IKLN Connector
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

kubectl exec -n ikln-connector ikln-edc-vault-0 -- \
  vault kv put secret/edc-wallet-secret content=changeme

kubectl exec -n ikln-connector ikln-edc-vault-0 -- \
  vault kv put secret/tokenSignerPrivateKey content=changeme

kubectl exec -n ikln-connector ikln-edc-vault-0 -- \
  vault kv put secret/tokenSignerPublicKey content=changeme

kubectl exec -n ikln-connector ikln-edc-vault-0 -- \
  vault kv put secret/tokenEncryptionAesKey content=changeme

# MASS Connector (mismo proceso)
kubectl exec -n mass-connector mass-edc-vault-0 -- \
  vault kv put secret/edc-wallet-secret content=changeme
# ... (resto de secrets)
```

**Verificación:**
```bash
kubectl exec -n ikln-connector ikln-edc-vault-0 -- vault kv list secret
# Keys
# ----
# edc-wallet-secret
# tokenEncryptionAesKey
# tokenSignerPrivateKey
# tokenSignerPublicKey
```

**Resultado:** ✅ Secrets creados correctamente

### 2.2 Problema #2: URLs HTTPS de DIM Wallet con Certificados Self-Signed

**Síntoma:**
Después de crear los secrets, el error cambió a:
```
HTTP client exception caught for request 
[POST, https://ssi-dim-wallet-stub.51.178.94.25.nip.io/oauth/token]
```

**Log completo:**
```json
{
  "message": "Unable to obtain credentials: Failure in DID resolution: 
  (certificate_unknown) PKIX path building failed: 
  sun.security.provider.certpath.SunCertPathBuilderException: 
  unable to find valid certification path to requested target",
  "type": "BadGateway"
}
```

**Diagnóstico:**
- Los conectores estaban configurados para usar URLs **HTTPS externas** del DIM Wallet y BDRS
- Estas URLs usan certificados self-signed que Java no confía
- Configuración problemática en `values-ikln-connector.yaml`:
  ```yaml
  sts:
    dim:
      url: https://ssi-dim-wallet-stub.51.178.94.25.nip.io/api/sts
    oauth:
      token_url: https://ssi-dim-wallet-stub.51.178.94.25.nip.io/oauth/token
  controlplane:
    env:
      TX_IAM_IATP_CREDENTIALSERVICE_URL: https://ssi-dim-wallet-stub.51.178.94.25.nip.io/api
  bdrs:
    server:
      url: https://ssi-dim-wallet-stub.51.178.94.25.nip.io/api/v1/directory
  ```

**Causa Raíz:**
1. Las URLs externas (nip.io) usan certificados self-signed generados por nginx
2. El cliente HTTP de Java en los EDCs rechaza estos certificados por defecto
3. Además, la URL de BDRS estaba usando el path incorrecto (`/api/v1/directory` en lugar de `/api/directory`)

**Solución Implementada:**
Cambiar todas las URLs a **HTTP con servicios internos de Kubernetes**:

```yaml
# Cambios en values-ikln-connector.yaml y values-mass-connector.yaml
sts:
  dim:
    url: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api/sts
  oauth:
    token_url: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/oauth/token

controlplane:
  env:
    TX_IAM_IATP_CREDENTIALSERVICE_URL: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api

bdrs:
  server:
    url: http://bdrs-server.portal.svc.cluster.local:8082/api/directory
    #                                            ^^^^ Puerto correcto
    #                                                 ^^^^^^^^^^^^^^ Path correcto

dataplane:
  env:
    TX_IAM_IATP_CREDENTIALSERVICE_URL: http://ssi-dim-wallet-service.portal.svc.cluster.local:8080/api
```

**Puntos clave corregidos:**
- ✅ HTTPS → HTTP (evita problema de certificados)
- ✅ URLs externas → URLs internas de Kubernetes (comunicación dentro del cluster)
- ✅ Puerto 8080 explícito para DIM Wallet
- ✅ Puerto 8082 para BDRS (Directory API)
- ✅ Path correcto `/api/directory` en lugar de `/api/v1/directory`

**Redespliegue:**
```bash
./deploy-mass-connector.sh  # Revision 1 → 2
./deploy-ikln-connector.sh  # Revision 3 → 4
```

**Resultado:** ✅ Conectores redesplegados exitosamente

### 2.3 Problema #3: URL DSP Externa con Certificados Self-Signed

**Síntoma:**
Intento de catalog discovery con URL externa HTTPS:
```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -H "X-Api-Key: ikln-api-key-change-in-production" \
  -d '{
    "counterPartyAddress": "https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS"
  }'

# Error: certificate_unknown - PKIX path building failed
```

**Diagnóstico:**
- Aunque DIM Wallet y BDRS ahora usan HTTP interno
- La URL DSP del provider (MASS) sigue usando HTTPS externo
- Los ingress tienen certificados self-signed en secrets:
  - `edc-ikln-control-tls`
  - `edc-mass-control-tls`
  - `edc-ikln-data-tls`
  - `edc-mass-data-tls`

**Solución Temporal:**
Usar URL interna HTTP de Kubernetes para comunicación DSP:

```bash
# En lugar de: https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp
# Usar: http://mass-edc-controlplane.mass-connector.svc.cluster.local:8084/api/v1/dsp

curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -H "X-Api-Key: ikln-api-key-change-in-production" \
  -H "Content-Type: application/json" \
  -d '{
    "@context": {"@vocab": "https://w3id.org/edc/v0.0.1/ns/"},
    "counterPartyAddress": "http://mass-edc-controlplane.mass-connector.svc.cluster.local:8084/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS",
    "protocol": "dataspace-protocol-http"
  }'
```

**Resultado:** ✅ **Catalog discovery exitoso!**

## 7. Problemas Pendientes de Resolver

### 7.1 Certificados SSL/TLS Self-Signed en Ingress

**Problema:**
Las URLs externas HTTPS (`https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp`) no funcionan para comunicación DSP entre conectores debido a certificados self-signed.

**Impacto:**
- ❌ No se puede usar la URL externa desde UI EDC para catalog discovery
- ❌ Conectores externos fuera del cluster no pueden comunicarse vía HTTPS
- ✅ Workaround actual: Usar URLs internas HTTP (solo funciona dentro del cluster)

**Opciones de solución:**

#### Opción 1: Certificados Válidos con Let's Encrypt (Ideal)
**Requisito:** Dominio accesible desde internet público
- **Problema:** `51.178.94.25.nip.io` no es accesible públicamente
- **Alternativa:** Let's Encrypt con DNS-01 challenge (requiere API OVH)

```yaml
# Instalar cert-manager
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --set installCRDs=true

# Crear ClusterIssuer con DNS-01
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    email: admin@company.com
    server: https://acme-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - dns01:
          ovh:
            endpoint: ovh-eu
            applicationKey: <OVH_APP_KEY>
            applicationSecret:
              name: ovh-credentials
              key: applicationSecret
            consumerKey:
              name: ovh-credentials
              key: consumerKey
```

#### Opción 2: CA Interno (Recomendada para desarrollo)
**Pasos:**
1. Generar Certificate Authority raíz propio
2. Firmar certificados para cada dominio con el CA
3. Crear secret con certificados firmados
4. Importar CA raíz en Java trust store de los pods EDC

```bash
# 1. Crear CA
openssl genrsa -out ca-key.pem 4096
openssl req -x509 -new -nodes -key ca-key.pem -sha256 -days 3650 \
  -out ca-cert.pem -subj "/CN=CatenaX Dev CA"

# 2. Crear certificado para cada servicio
openssl genrsa -out edc-mass-control.key 2048
openssl req -new -key edc-mass-control.key -out edc-mass-control.csr \
  -subj "/CN=edc-mass-control.51.178.94.25.nip.io"
openssl x509 -req -in edc-mass-control.csr -CA ca-cert.pem -CAkey ca-key.pem \
  -CAcreateserial -out edc-mass-control.crt -days 365 -sha256

# 3. Crear secret
kubectl create secret tls edc-mass-control-tls \
  --cert=edc-mass-control.crt \
  --key=edc-mass-control.key \
  -n mass-connector

# 4. Importar CA en pods EDC
kubectl create configmap java-cacerts \
  --from-file=cacerts=/tmp/custom-truststore \
  -n ikln-connector
```

```yaml
# values-ikln-connector.yaml
controlplane:
  volumes:
    - name: truststore
      configMap:
        name: java-cacerts
  volumeMounts:
    - name: truststore
      mountPath: /opt/truststore
  env:
    JAVA_TOOL_OPTIONS: >-
      -Djavax.net.ssl.trustStore=/opt/truststore/cacerts
      -Djavax.net.ssl.trustStorePassword=changeit
```

#### Opción 3: Deshabilitar TLS en Ingress (Solo desarrollo)

## 8. Conclusiones

### 8.1 Lecciones Aprendidas

#### Sobre Secrets en Vault

**❌ Forma Incorrecta (implementada hoy por urgencia):**
```bash
# Creación manual de secrets - NO ESCALABLE
kubectl exec -n ikln-connector ikln-edc-vault-0 -- \
  vault kv put secret/edc-wallet-secret content=changeme
```

**✅ Forma Correcta (pendiente de implementar):**

**Opción A: Incluir sección `secrets:` en el values file**
```yaml
# Requiere modificar estructura del chart
ikerlan-connector-1:
  enabled: true
  secrets:
    edc-wallet-secret: changeme
  tractusx-connector:
    # ...resto configuración
```

**Problema identificado:** El formato simplificado actual de `values-ikln-connector.yaml` no soporta la sección `secrets:` porque no tiene el wrapper de nivel superior (`ikerlan-connector-1:`). 

**Soluciones posibles:**
1. Usar el archivo `values-ikln-connector FULL.yaml` que sí tiene la estructura completa
2. Modificar el chart `dataspace-connector-bundle` para soportar `secrets:` en el nivel raíz
3. Usar Helm post-install hooks para crear secrets automáticamente

**Opción B: Helm post-install hook (mejor práctica)**
```yaml
# templates/post-install-vault-setup.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-vault-setup
  annotations:
    helm.sh/hook: post-install,post-upgrade
    helm.sh/hook-weight: "5"
    helm.sh/hook-delete-policy: hook-succeeded
spec:
  template:
    spec:
      containers:
        - name: vault-setup
          image: hashicorp/vault:latest
          command:
            - /bin/sh
            - -c
            - |
              vault login {{ .Values.vault.token }}
              vault kv put secret/edc-wallet-secret content={{ .Values.secrets.walletSecret }}
              vault kv put secret/tokenSignerPrivateKey content={{ .Values.secrets.tokenSignerPrivateKey }}
              # ...resto secrets
```

**Opción C: External Secrets Operator (enterprise)**
```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: edc-vault-secrets
spec:
  secretStoreRef:
    name: vault-backend
  target:
    name: edc-secrets
  data:
    - secretKey: edc-wallet-secret
      remoteRef:
        key: secret/data/edc-wallet-secret
```

#### Sobre Estructura de Values Files

  ```yaml
  tractusx-connector:

  ```
  
- `values-ikln-connector FULL.yaml`: Formato con wrapper completo

#### Sobre URLs y Comunicación

**✅ Best Practice identificada:**
- **URLs internas HTTP:** Para comunicación entre servicios dentro del cluster
  - `http://service-name.namespace.svc.cluster.local:port`
  - Sin overhead de TLS
  - Sin problemas de certificados
  - Mejor rendimiento
  
- **URLs externas HTTPS:** Solo para acceso desde fuera del cluster
  - Management API para administradores externos
  - Public data plane endpoints
  - Requiere certificados válidos

**Configuración híbrida ideal:**
```yaml
# Servicios internos: HTTP
```

#### Sobre Arquitectura de Puertos BDRS

**Importante conocer:**
```
BDRS tiene 3 puertos con propósitos diferentes:
- Puerto 8080: /api          → Default API (observability)
- Puerto 8081: /api/management → Admin operations (POST con x-api-key)
- Puerto 8082: /api/directory  → Public queries (GET por EDCs) ✅ USAR ESTE
```

**Error común:** Usar puerto 8080 con path `/api/v1/directory` (path de versión anterior).

#### Sobre Persistencia de Datos

**Confirmado durante sesión:**
- PostgreSQL mantiene datos de assets, policies y contracts a través de redeployments
- Vault mantiene secrets mientras el pod StatefulSet esté running
- Solo se reinician controlplane y dataplane pods al cambiar su configuración
- Vault y PostgreSQL son StatefulSets que persisten datos

## 9. Pasos Futuros

### 9.1 Prioridad Alta

#### 1. Resolver Problema de Certificados SSL/TLS
**Objetivo:** Permitir comunicación HTTPS entre conectores usando URLs externas

**Opciones ordenadas por recomendación:**

**A. Certificados Let's Encrypt con DNS-01 (Producción)**
- Ventajas: Certificados válidos, renovación automática, trusted por todos
- Requisitos: Acceso a API DNS de OVH, dominio propio
- Esfuerzo: Medio
- Tiempo estimado: 2-4 horas

**B. CA Interno (Desarrollo/Staging)**
- Ventajas: Control total, no requiere dominio público
- Desventajas: Requiere distribuir CA raíz a todos los clientes
- Esfuerzo: Medio
- Tiempo estimado: 3-5 horas

**C. Deshabilitar TLS (Solo pruebas locales)**
- Ventajas: Rápido, sin complejidad
- Desventajas: No apto para producción
- Esfuerzo: Bajo
- Tiempo estimado: 30 minutos

**Recomendación:** Empezar con opción B (CA Interno) para validar que todo funciona, luego migrar a opción A (Let's Encrypt) para producción.
