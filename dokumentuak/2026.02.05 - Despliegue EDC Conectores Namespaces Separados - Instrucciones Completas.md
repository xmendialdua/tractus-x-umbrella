## Resumen de la Arquitectura

### Distribución de Namespaces

```
┌────────────────────────────────────────────────────────────┐
│                  Namespace: portal                         │
│                                                            │
│  ✅ Portal (Frontend + Backend)                            │
│  ✅ Keycloak (Central IDP + Shared IDP)                    │
│  ✅ BPDM (Pool, Gate, Orchestrator)                        │
│  ✅ BDRS (BPN-DID Resolution Service)                      │
│  ✅ DIM Wallet Stub                                        │
│  ✅ Discovery Services                                     │
│  ✅ SSI Credential Issuer                                  │
└────────────────────────────────────────────────────────────┘
                         ↑ ↑ ↑
         ┌───────────────┘ │ └─────────────────┐
         │                 │                   │
┌────────┴────────────┐    │        ┌──────────┴──────────┐
│ Namespace:          │    │        │  Namespace:         │
│ mass-connector      │    │        │  ikln-connector     │
│                     │    │        │                     │
│ 🆕 EDC MASS         │    │        │  🆕 EDC IKLN        │
│  - Control Plane    │◄───┼───────►│   - Control Plane   │
│  - Data Plane       │    │        │   - Data Plane      │
│  - PostgreSQL       │    │        │   - PostgreSQL      │
│  - Vault            │    │        │   - Vault           │
└─────────────────────┘    │        └─────────────────────┘
                           │
          Comunicación via FQDN
          (nombre.namespace.svc.cluster.local)
```

### Ventajas de esta Arquitectura

| Aspecto | Beneficio |
|---------|-----------|
| **Aislamiento** | Cada partner tiene su propio espacio aislado |
| **Gestión** | Puedes eliminar/actualizar conectores independientemente |
| **Seguridad** | RBAC por namespace, fallo en un EDC no afecta a otros |
| **Escalabilidad** | Fácil añadir nuevos partners sin tocar los existentes |
| **Recursos** | Resource quotas y limits por partner |
| **Monitorización** | Métricas y logs separados por partner |

## Prerequisitos

### 1. Verificar que el Portal está Desplegado

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

# Verificar pods del portal
kubectl get pods -n portal

# Debe mostrar estos servicios corriendo:
# - portal-*
# - portal-centralidp-*
# - portal-sharedidp-*
# - bdrs-server-*
# - portal-ssi-dim-wallet-stub-* (IMPORTANTE)
```

### 2. Verificar DIM Wallet Stub

**⚠️ CRÍTICO:** El Wallet Stub debe estar desplegado en el namespace `portal`.

```bash
kubectl get pods -n portal | grep wallet

# Debe mostrar:
# portal-ssi-dim-wallet-stub-xxxxx   1/1   Running
```

Si NO existe, primero debes desplegarlo:

```bash
cd /home/xmendialdua/projects/assembly/tractus-x-umbrella/charts/umbrella

# Verificar que está habilitado en values-ovh-hosts-portal.yaml
grep -A 5 "ssi-dim-wallet-stub:" values-ovh-hosts-portal.yaml

# Si enabled: true, redesplegar el portal:
helm upgrade portal . \
  -f values-adopter-portal-for-onboarding-with-persistence.yaml \
  -f values-ovh-hosts-portal.yaml \
  -n portal \
  --timeout 20m
```

### 3. Verificar BDRS

```bash
kubectl get pods -n portal | grep bdrs

# Debe mostrar:
# bdrs-server-xxxxx   1/1   Running
```

### 4. Verificar que los BPNs están en el BDRS

El BDRS debe conocer los BPNs de MondragonAssembly e Ikerlan. Esto se configura en `values-ovh-hosts-portal.yaml`:

```yaml
bdrs-server-memory:
  bdrs:
    bpnDirectory:
      - bpn: "BPNL00000003CRHK"
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000003CRHK"
      - bpn: "BPNL00000000MASS"
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000000MASS"
      - bpn: "BPNL00000002IKLN"
        did: "did:web:ssi-dim-wallet-stub.51.178.94.25.nip.io:BPNL00000002IKLN"
```

```bash
# MondragonAssembly
helm status mass-edc -n mass-connector

helm status ikln-edc -n ikln-connector
```

### Actualizar un Conector

```bash
# Editar el archivo de configuración
nano charts/values-mass-connector.yaml

# Actualizar con Helm
helm upgrade mass-edc tractusx-dev/dataspace-connector-bundle \
  --namespace mass-connector \
  --values charts/values-mass-connector.yaml \
  --timeout 15m
```

### Eliminar un Conector (sin afectar al otro)

```bash
# Eliminar solo MondragonAssembly
helm uninstall mass-edc -n mass-connector
kubectl delete namespace mass-connector

# Eliminar solo Ikerlan
helm uninstall ikln-edc -n ikln-connector
kubectl delete namespace ikln-connector

# El portal y el otro conector siguen funcionando ✅
```

### Escalar Recursos

```bash
# Editar el deployment
kubectl edit deployment -n mass-connector mass-edc-tractusx-connector-controlplane

# O ajustar replicas vía Helm (si el chart lo soporta)
helm upgrade mass-edc tractusx-dev/dataspace-connector-bundle \
  --namespace mass-connector \
  --values charts/values-mass-connector.yaml \
  --set tractusx-connector.controlplane.replicaCount=2
```

## Troubleshooting

### Problema 1: Pods en CrashLoopBackOff

**Síntomas:**
```bash
kubectl get pods -n mass-connector
# mass-edc-tractusx-connector-controlplane-xxx   0/1   CrashLoopBackOff
```

**Diagnóstico:**
```bash
# Ver logs
kubectl logs -n mass-connector <pod-name> --tail=100

# Ver eventos
kubectl describe pod -n mass-connector <pod-name>
```

**Causas comunes:**
1. **Wallet Stub no accesible:** Verificar que está corriendo en namespace `portal`
2. **BDRS no accesible:** Verificar URL `http://bdrs-server.portal.svc.cluster.local:8080`
3. **Problemas de red:** NetworkPolicies bloqueando tráfico entre namespaces

**Solución - NetworkPolicies:**

Si hay NetworkPolicies estrictas, crear política para permitir tráfico desde conectores al portal:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-to-portal
  namespace: mass-connector
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: portal
EOF
```

Aplicar lo mismo para `ikln-connector`.

### Problema 2: Ingress no funciona

**Síntomas:**
```bash
curl http://edc-mass-control.51.178.94.25.nip.io/api/check/health
# Connection refused o timeout
```

**Diagnóstico:**
```bash
# Verificar ingress
kubectl get ingress -n mass-connector

# Describir ingress
kubectl describe ingress -n mass-connector <ingress-name>

# Verificar ingress controller
kubectl get pods -n ingress-nginx
```

**Solución:**
- Verificar que nginx-ingress-controller está corriendo
- Verificar que el hostname está resolviendo a la IP correcta
- Revisar logs del ingress controller

### Problema 3: PostgreSQL no inicia

**Síntomas:**
```bash
kubectl get pods -n mass-connector
# mass-edc-postgresql-0   0/1   Pending
```

**Diagnóstico:**
```bash
kubectl describe pod -n mass-connector mass-edc-postgresql-0
```

**Causas comunes:**
- No hay PersistentVolume disponible
- Storage class no existe

**Solución:**
```bash
# Ver storage classes disponibles
kubectl get sc

# Si no hay storage class, usar emptyDir (solo para testing):
# Editar values-mass-connector.yaml:
# postgresql:
#   primary:
#     persistence:
#       enabled: false
```

### Problema 4: Vault no accesible

**Síntomas:**
```bash
# En logs del EDC:
# Failed to connect to vault at http://mass-edc-vault:8200
```

**Solución:**
```bash
# Verificar que vault está corriendo
kubectl get pods -n mass-connector | grep vault

# Verificar servicio de vault
kubectl get svc -n mass-connector | grep vault

# Reiniciar vault si es necesario
kubectl delete pod -n mass-connector mass-edc-vault-0
```
